# Мастер шаблонов

Ключевой элемент проекта: создание и сопровождение шаблонов документов не должно быть ручной разметкой каждой строки и каждого правила автозаполнения.

## 1. Проблема

В текущем Документообороте шаблон — это карточка справочника, файл, правила автозаполнения и связи. Даже простой шаблон требует:

- создать карточку;
- приложить файл;
- заполнить реквизиты;
- создать `ПравилаАвтозаполненияФайлов`;
- для каждой строки указать `ЗаменяемуюСтроку`, `ЗначениеЗамены`, тип, формат;
- настроить таблицы, списки, падежи;
- связать правила с шаблоном;
- проверить и опубликовать.

С ростом сложности шаблона ручная работа становится непомерно тяжёлой и плохо масштабируется.

## 2. Цель

Сделать конвейер, в котором человек утверждает смысл, а ИИ и детерминированные генераторы создают техническую разметку.

```text
DOCX / текст / описание словами
        │
        ▼
Извлечение текста и структуры
        │
        ▼
AI-анализ: разделы, списки, плейсхолдеры, типы, источники, падежи
        │
        ▼
Таблица на проверку человеку
        │
        ▼
Автогенерация правил и метаданных
        │
        ▼
Тестовое заполнение
        │
        ▼
Утверждение и публикация
        │
        ▼
Индексация RAG
```

## 3. Роли

| Роль | Ответственность |
|---|---|
| Методолог / юрист / HR | смысл, формулировки, обязательные разделы |
| Ответственный за шаблон | актуальность, версия, публикация |
| Администратор | источники, промпты, права, индексация |
| ИИ | черновая разметка, предложения, проверка |
| Детерминированный движок | вставка значений, сохранение вёрстки, нумерации и стилей |

## 4. Режимы создания

1. **Импорт существующего документа** — загрузить DOCX/ODT/TXT/HTML, получить черновик разметки.
2. **Описание словами** — «письмо-ответ на обращение, шапка, вводная часть, список поручений, подпись»; ИИ предлагает структуру и шаблон.
3. **Клонирование** — взять существующий шаблон и адаптировать под другой вид документа/должность.
4. **Ручной режим** — обычное создание в 1С, если нужно.

### 4.1. Автоматическое формирование шаблона из готового документа (реализовано 2026-10-26)

Отдельный от мастера вход: если внутренний документ создан без шаблона или на основе шаблона, но дополнен сверх него, расширение само формирует черновик переиспользуемого шаблона. Черновик получает статус `Черновик`; `Программист1С` выполняет техническое согласование (статус `Согласован`), после чего автор исходного документа окончательно утверждает шаблон (статус `Утверждён`). До утверждения автором шаблон не попадает в поиск.

- механизм: `АИС_Уведомления.ПроверитьНеобходимостьШаблона` + `АИС_ОбщегоНазначения.ВызватьИИ`/`СоздатьЧерновикШаблона`;
- промпт требует заменить изменяемые части плейсхолдерами в квадратных скобках и явно указать источник значения (например, `[ОКЛАД — определяет Главный бухгалтер]`);
- автошаблонизация — техническая функция расширения; черновик технически согласует `Программист1С`, а окончательно утверждает автор исходного документа; делопроизводитель к этому не привлекается;
- текущая реализация работает для `Справочник.ВнутренниеДокументы`; распространение на входящие/исходящие — по мере реализации соответствующих триггеров;
- прямой доступ к списку шаблонов — обработка `АИС_Шаблоны` в «АИС: Сервис»: единый список внутренних, входящих и исходящих шаблонов с текстом, полями статуса/текста и сохранением; редактирование доступно администратору и `Программист1С`.

## 5. Этапы мастера

1. Загрузить файл или выбрать существующий шаблон.
2. Извлечь текст и структуру: заголовки, абзацы, таблицы, списки, колонтитулы.
3. Выполнить AI-анализ:
   - кандидаты в плейсхолдеры;
   - повторяющиеся термины;
   - разделы;
   - списки и таблицы;
   - типы значений;
   - предполагаемые источники;
   - падеж и форма слова.
4. Показать таблицу проверки:
   - имя, тип, обязательность, источник, способ заполнения, падеж;
   - раздел/список;
   - маркер в файле;
   - предупреждения.
5. Человек правит и утверждает.
6. Сгенерировать:
   - `ПравилаАвтозаполненияФайлов`;
   - ТЧ `АИС_Плейсхолдеры` в трёх справочниках шаблонов;
   - маркеры/закладки в файле;
   - связи с полями и запросами.
7. Выполнить тестовое заполнение на демо-данных.
8. Опубликовать шаблон:
   - статус `Утвержден`;
   - версия;
   - активность;
   - индексация RAG.

## 6. Формат шаблона

Поддерживаются два уровня:

- **нативные средства**: поля Word, закладки, `ТермДляЗамены`, `ЗаменяемаяСтрока`;
- **маркеры проекта**:
  ```text
  {{ДатаДокумента}}
  {{ФИО.Дательный}}
  {{Организация.Родительный}}

  {{#Список:Поручения}}
    {{Номер}}. {{Текст}} — {{Ответственный.Дательный}}
  {{/Список:Поручения}}

  {{#Раздел:Обоснование}}
    ...
  {{/Раздел:Обоснование}}
  ```

Мастер сам создаёт правила под маркеры. `{{...}}` — соглашение проекта, а не формат 1С; оно отображается на `ЗаменяемуюСтроку` и `ЗначениеЗамены`.

## 7. Данные мастера

Штатные объекты:

- `ШаблоныВходящихДокументов`, `ШаблоныИсходящихДокументов`, `ШаблоныВнутреннихДокументов`;
- `Файлы`, `ВерсииФайлов`;
- `ПравилаАвтозаполненияФайлов`.

ИИ-специфичные объекты:

### ТЧ `АИС_Плейсхолдеры`

Добавляется в каждый из трёх справочников шаблонов (`ШаблоныВходящихДокументов`, `ШаблоныИсходящихДокументов`, `ШаблоныВнутреннихДокументов`). Строка — одно описание плейсхолдера.

Канонический состав полей — `docs/data-model.md` §14.1; здесь он не дублируется. Для мастера важны:

- `Вид`: `Значение`, `Список`, `Раздел`;
- `ИсточникДанных` — ссылка на штатный `ИсточникиДанных`; `СпособЗаполнения` — `EnumRef.АИС_СпособыЗаполнения`;
- `ПравилоАвтозаполнения` — ссылка на базовое правило; `ШаблонЗапроса` — утверждённый запрос для `ЗапросВБД`;
- `Статус` — статус разметки в мастере (принят, отклонён, требует проверки), не runtime-статус плейсхолдера.

### `АИС_СтатусыШаблонов`

- измерение `Шаблон`;
- `Версия`;
- `Статус`: `Черновик`, `НаПроверке`, `Утвержден`, `Устарел`, `Отклонен`;
- `Автор`, `Дата`, `Комментарий`;
- `РезультатАнализа`, `Ошибки`;
- `ДатаИндексации`.

### `АИС_СостоянияШаблонов`

Перечисление статусов шаблона.

## 8. AI-промпты

- `АнализШаблона` — структура, плейсхолдеры, списки, разделы;
- `ПредложитьИсточник` — сопоставить плейсхолдер с полем/запросом/ДЛ/API;
- `ПроверитьШаблон` — дубли, пропуски, неоднозначности;
- `СгенерироватьПравила` — предложить `ЗаменяемуюСтроку` и `ЗначениеЗамены`;
- `ТестовоеЗаполнение` — проверить на демо-данных.

Тексты промптов хранятся в `АИС_Промпты`, параметры модели — в `АИС_ПромптПараметры`; `ШаблоныТекстов` остаётся для штатных текстовых шаблонов документов.

## 9. DOCX и вёрстка

- Скалярные значения — через поля Word/закладки или текстовые маркеры.
- Списки — повторяемый блок с сохранением нумерации/маркеров.
- Разделы — повторяемый блок/границы раздела.
- Таблицы — штатные `ПравилаЗаполненияТаблиц` или повторяемые строки.
- Финальную вставку выполняет детерминированный движок, не LLM.
- После генерации выполняется проверка: обязательные разделы, порядок, версии, подтверждения.

## 10. Проверка и публикация

Шаблон нельзя опубликовать, если:

- есть незаполненные обязательные метаданные;
- есть дубли имён;
- не найден источник;
- не указан падеж для склоняемого значения;
- список/раздел не имеет границ;
- тестовое заполнение завершилось ошибкой.

Публикация:

- статус `Утвержден`;
- версия;
- активность;
- индексация RAG;
- старые версии переводятся в `Устарел`.

## 11. MVP

1. Один тип исходящего документа.
2. DOCX.
3. Скалярные плейсхолдеры.
4. Один простой маркированный список.
5. Один раздел.
6. Ручное подтверждение.
7. Автогенерация правил и тестовая генерация.

После MVP: таблицы, условия, несколько списков, падежи, несколько типов документов, клонирование.

## 12. Критерии приёмки

- Шаблон создаётся из DOCX без ручного создания каждого правила.
- Человек проверяет и утверждает таблицу плейсхолдеров.
- Правила `ПравилаАвтозаполненияФайлов` создаются автоматически.
- Тестовое заполнение проходит до публикации.
- Опубликованный шаблон индексируется в RAG.
- Изменение шаблона создаёт новую версию и переиндексацию.
- ИИ не публикует шаблон без подтверждения человека.

## 13. Риски

| Риск | Мера |
|---|---|
| ИИ неверно определил плейсхолдер | обязательная проверка человеком |
| Потеря вёрстки DOCX | детерминированный движок и тестовый рендер |
| Сложные списки/разделы | ограничить MVP, расширять постепенно |
| Нет источника данных | блокировать публикацию, предложить ручной ввод |
| Устаревшие шаблоны | версии, статусы, переиндексация |
| Слишком много шаблонов | фильтры по типу, должности, активности; RAG top-k |

## 14. Ручная корректировка и отклонение

Предложения ИИ — не приказ, а черновик. Пользователь должен иметь возможность отклонить как отдельный плейсхолдер, так и весь предложенный шаблон.

### 14.1. Редактор плейсхолдеров

Таблица с действиями по каждой строке:

- принять предложение;
- отклонить;
- изменить имя;
- изменить тип данных;
- изменить источник и способ заполнения;
- изменить обязательность, падеж, формат;
- удалить плейсхолдер;
- добавить новый вручную;
- объединить дубли;
- показать маркер в документе;
- посмотреть обоснование ИИ и confidence.

Дополнительно:

- поиск и фильтры;
- массовые действия;
- undo/redo;
- автосохранение черновика;
- подсветка ошибок и незаполненных обязательных полей;
- предпросмотр с тестовыми данными;
- добавление плейсхолдера выделением текста в предпросмотре;
- удаление маркера из файла с подтверждением, если он используется.

### 14.2. Отклонение всего шаблона

- «Отклонить и редактировать вручную» — ИИ-разметка отключается, черновик остаётся.
- «Отклонить полностью» — шаблон не создаётся; файл можно сохранить как черновик.
- «Вернуться к загрузке» — выбрать другой файл/описание.
- Ни одно правило не создаётся и не публикуется без подтверждения.

### 14.3. Принципы дружелюбности

- никаких длинных модальных цепочек;
- изменения видны сразу;
- ошибки объясняются человеческим языком;
- опасные действия подтверждаются;
- можно вернуться на шаг назад;
- ИИ не скрывает, что он предложил, а что подтвердил человек.

## 15. Сравнение шаблонов

Новый шаблон может быть почти таким же, как существующий. Плодить копии вредно: это ухудшает выбор в RAG и усложняет сопровождение.

### 15.1. Поток

1. Построить кандидат: текст, плейсхолдеры, разделы, списки, метаданные.
2. Найти похожие активные шаблоны:
   - по виду документа;
   - по должности/подразделению;
   - по RAG/эмбеддингам;
   - по точному совпадению реквизитов.
3. Сравнить кандидата с каждым кандидатом.
4. Показать side-by-side diff и оценку сходства.
5. Предложить действие:
   - обновить существующий;
   - объединить;
   - создать новый;
   - ручное решение.
6. Пользователь принимает решение.
7. Выполнить действие и записать аудит.

### 15.2. Решение по умолчанию

- высокая похожесть и только добавленные/удалённые плейсхолдеры → **обновить существующий**;
- средняя похожесть или изменения структуры → **объединить**;
- низкая похожесть или другой вид документа → **создать новый**;
- несколько близких кандидатов → **ручной выбор**.

Автоматического перезаписывания нет. Решение всегда за пользователем.

### 15.3. Последствия

- Обновление: новая версия, старая версия в `Устарел`, переиндексация RAG, уведомление ответственного.
- Объединение: новый шаблон на основе двух, слияние плейсхолдеров и правил, проверка конфликтов.
- Новый: обязательная причина, ссылка на ближайший шаблон, пометка варианта, чтобы не потерять связь.

## 16. Алгоритм сравнения

### 16.1. Признаки

| Признак | Как считается |
|---|---|
| Текст | cosine similarity эмбеддингов + нормализованный diff |
| Плейсхолдеры | множества имён, типов, источников, обязательности, падежей |
| Структура | разделы, списки, таблицы, порядок |
| Метаданные | вид документа, должность, организация, назначение |

### 16.2. Оценка

Пример весов (хранятся в `config/parameters.yaml`, не в коде):

- текст — 0.4;
- плейсхолдеры — 0.3;
- структура — 0.2;
- метаданные — 0.1.

Порог:

- `>= 0.90` и нет структурных изменений → обновить существующий;
- `0.70–0.90` или есть изменения плейсхолдеров → объединить;
- `< 0.70` → создать новый.

Пороги настраиваются.

### 16.3. Diff плейсхолдеров

Детерминированно сравниваются:

- добавленные;
- удалённые;
- переименованные;
- изменённые по типу;
- изменённые по источнику/способу заполнения;
- изменённые по обязательности/падежу/формату.

LLM может предложить сопоставление похожих имён, но пользователь подтверждает.

### 16.4. Роль LLM

- объяснить различия человеческим языком;
- предложить сопоставление плейсхолдеров;
- предложить план объединения;
- не принимать окончательное решение;
- не перезаписывать шаблон.

### 16.5. Данные сравнения

Регистр `АИС_СравненияШаблонов`:

- `ИсходныйШаблон`, `ЦелевойШаблон`, `Версия`;
- `ОценкаСходства`, `ТекстоваяОценка`, `ОценкаПлейсхолдеров`, `ОценкаСтруктуры`, `ОценкаМетаданных`;
- `РазличияJSON`;
- `Рекомендация`;
- `Решение`;
- `Пользователь`, `Дата`, `Комментарий`.

Перечисление `АИС_РекомендацииПоШаблонам`:

- `ОбновитьСуществующий`;
- `Объединить`;
- `СоздатьНовый`;
- `РучноеРешение`.

## 17. Что видит пользователь

- Текущий шаблон и предложенный кандидат рядом.
- Подсветка добавленных, удалённых и изменённых плейсхолдеров.
- Оценка сходства и рекомендация.
- Кнопки: «Обновить существующий», «Объединить», «Создать новый», «Отклонить и редактировать».
- Пояснение последствий: версия, индексация, статус старого шаблона, уведомления.

## 18. MVP и критерии

В MVP входят:

- ручное принятие/отклонение каждого плейсхолдера;
- ручное добавление/удаление/изменение параметров;
- сравнение с одним наиболее похожим шаблоном;
- простая оценка сходства и diff;
- решение пользователя: обновить, объединить, создать новый;
- аудит решения.

Критерии:

- пользователь может отклонить любой плейсхолдер без потери остальной разметки;
- можно добавить/удалить плейсхолдер вручную;
- при высокой похожести система предлагает обновление, а не создание копии;
- при низкой похожести создание нового требует явного подтверждения и причины;
- все решения и различия записаны в аудит.
