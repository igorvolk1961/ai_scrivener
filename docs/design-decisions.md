# Проектные решения

Статус: проектирование завершено, 2026-10-23; раздел §§14–19 обновлён 2026-10-23 по итогам `reviews/critical-review.md`. Документ фиксирует решения по вопросам, которые ранее были открыты.

## 1. Границы проекта

- Поставка — расширение `.cfe` для `ДокументооборотПРОФ 2.1.38.11`.
- Базовая конфигурация не изменяется.
- Пользовательские документы, задачи, файлы, права и бизнес-процессы остаются штатными.
- Новые объекты — только ИИ-специфичные, с префиксом `АИС_`.

## 2. Шаблоны

### 2.1. Где хранятся

- Штатные `ШаблоныВходящихДокументов`, `ШаблоныИсходящихДокументов`, `ШаблоныВнутреннихДокументов`.
- Файлы — `Файлы`/`ВерсииФайлов`.
- Правила замены — `ПравилаАвтозаполненияФайлов`.
- Метаданные плейсхолдеров — ТЧ `АИС_Плейсхолдеры` в трёх справочниках шаблонов.
- Отдельный `АИС_ШаблоныДокументов` не создаётся.

### 2.2. Формат

Принят формат маркеров проекта:

```text
{{ДатаДокумента}}
{{ФИО.Дательный}}
{{Организация.Родительный}}
{{#Список:Поручения}} ... {{/Список:Поручения}}
{{#Раздел:Обоснование}} ... {{/Раздел:Обоснование}}
```

- Маркеры отображаются на `ЗаменяемуюСтроку` и `ЗначениеЗамены`.
- Нативные поля Word/закладки поддерживаются как альтернатива.
- Финальную вставку выполняет детерминированный DOCX-движок; LLM не выполняет вёрстку.
- Для MVP — маркеры на уровне абзацев/строк; content controls — следующий этап.

### 2.3. Роли и статусы

- Создаёт и утверждает шаблон методолог/ответственный за шаблон.
- Администратор настраивает источники, промпты, права и индексацию, но не утверждает содержание.
- Статусы: `Черновик`, `НаПроверке`, `Утвержден`, `Устарел`, `Отклонен`.
- Публикация только после подтверждения человеком.

### 2.4. Сравнение

- Веса: текст 0.4, плейсхолдеры 0.3, структура 0.2, метаданные 0.1.
- Пороги: `>= 0.90` — обновить существующий; `0.70–0.90` — объединить; `< 0.70` — создать новый.
- Несколько кандидатов в пределах 0.05 — ручной выбор.
- Сопоставление плейсхолдеров: точное имя, затем семантическое предложение LLM; подтверждает человек.
- Конфликт типа/источника при объединении блокирует автоприменение.
- Создание нового требует причины; обновление создаёт версию и переиндексирует RAG.

## 3. Разделы документа

- Раздел — специализированный плейсхолдер (`ВидПлейсхолдера = Раздел`).
- `АИС_РазделыДокумента` — справочник (не регистр сведений), подчинён `ИсходящиеДокументы`: нужен ссылочный тип (`refType`), которого у регистра нет, а на раздел нужно ссылаться из `АИС_СостоянияПлейсхолдеров`/`АИС_ЛистОжидания`. Новая версия раздела — новый элемент справочника, старый → `Устарел`.
- Содержимое хранится в `Файлы`/`ВерсииФайлов`; `АИС_РазделыДокумента` хранит ссылку, версию, хеш, ответственного, задачу и подтверждение.
- Текст раздела не дублируется; для текстового раздела используется текстовый файл.
- Подтверждение привязано к версии и хешу; изменение файла переводит раздел в `Устарел`.
- Сборка блокируется, пока обязательные разделы не подтверждены.

## 4. Триггеры и события

- Для детектирования используются `ВидыБизнесСобытий`/`ДетекторыБизнесСобытий`, если покрывают событие. **Подтверждено инвентаризацией** импортированной базовой конфигурации `ДокументооборотПРОФ 2.1.38.11` (`Catalogs/ВидыБизнесСобытий`, `Catalogs/ДетекторыБизнесСобытий`, регламентные задания `ОбработкаДетекторовБизнесСобытий`/`ОбработкаПроизошедшихБизнесСобытий`) — подсистема присутствует в ПРОФ в достаточном объёме, принцип переиспользования технически обоснован.
- `АИС_ТипыТриггеров` остаётся классификатором для ИИ-специфичных триггеров: входящий документ, таймер, внешний ответ, расписание. **Уточнение:** для `Таймер`, `ПоступлениеОтветНаЗапрос`, `ИстечениеСрокаОжидания` `АИС_ТипыТриггеров` не «запасной вариант», а единственно возможный классификатор — эти состояния существуют только внутри расширения и не могут быть обнаружены штатным детектором бизнес-событий по построению. `raw_specification.md` §4.3.1 и `data-model.md` §7 формулируются соответственно: триггеры делятся на «потенциально штатные» (входящий документ, распоряжение) и «внутренние по построению» (таймер, ответ, истечение срока ожидания).
- Расписание — `АИС_РасписаниеТриггеров` + регламентное задание.
- **Механика:** периодическое/отложенное по времени требование из устного или письменного распоряжения начальника не действует автоматически — технически оно присоединяется к обязанностям ДЛ (§5) только после явной фиксации записи `АИС_РасписаниеТриггеров` со ссылкой на породившее её распоряжение. Само распоряжение расписание не создаёт.
- **Решение (2026-10-23, закрывает `reviews/critical-review.md` 2.10):** защита от молчаливой потери — при регистрации распоряжения промпт `ОпределениеПериодичностиРаспоряжения` анализирует текст на признаки периодичности. Если периодичность обнаружена, создание записи расписания становится **обязательным условием** закрытия базовой задачи по распоряжению (или явной отметки ДЛ, что текст распознан неверно) — не просто подсказкой. Если признаков периодичности нет, ничего дополнительно не запрашивается — разовые распоряжения не создают трения. Сочетает два из трёх вариантов, предложенных в `plans/remediation-plan.md` (обязательное условие + LLM-анализ текста), без отдельного регулярного отчёта.

## 5. Должности и обязанности

- ДЛ — `Пользователи` + `ФизическиеЛица`.
- Оргструктура — `СтруктураПредприятия`.
- **Решение (2026-10-23, отменяет и заменяет более ранние формулировки, включая первоначальное решение по §1.2 обзора):** `АИС_НазначенияДолжностей` как хранимый регистр не создаётся вообще — ни для постоянного назначения, ни для временного замещения. Один ДЛ может одновременно иметь одну постоянную должность и замещать одну или несколько других; обязанности всех действующих должностей объединяются, источник (постоянная/замещаемая) не важен для их применения.
  - Постоянная должность на дату — штатный периодический регистр `InformationRegisters.СведенияОПользователяхДокументооборот` (измерение `Пользователь`, ресурсы `Должность`, `Подразделение`).
  - Замещаемые должности на дату — штатный `Catalogs.ДелегированиеПрав` (`ОтКого`, `Кому`, `ДатаНачалаДействия`, `ДатаОкончанияДействия`, `Действует`): для получателя находятся активные записи, должность каждого `ОтКого` берётся через `СведенияОПользователяхДокументооборот`.
  - Действующие должности ДЛ на дату = {постоянная} ∪ {должности всех замещаемых на эту дату}. Вычисляется функцией общего модуля `АИС_ДолжностныеОбязанности.АктивныеДолжностиПользователя(Пользователь, Дата)`, результат не хранится отдельно.
  - Штатный `ПодчиненностьСотрудников` для этой задачи не используется (руководитель/подчинённый — другое понятие).
- `АИС_ДолжностныеОбязанности` — новый справочник; `Инструкции` не используются для обязанностей по должности. Резолвится по объединённому набору действующих должностей, а не по одной. Для триггера `Распоряжение` действие может браться прямо из текста распоряжения (письменного или устного, зафиксированного при регистрации), минуя каталог обязанностей — каталог не единственный источник требуемого действия.
- **Решение (2026-10-23):** пара (`ТипТриггера`, `ТипДействия`) недостаточна для выбора обязанности и документа, когда одна и та же пара покрывает разные ситуации (например, авария и рядовое обращение — оба `ВходящиеДокументы` + `ПодготовитьДоклад`). `АИС_ДолжностныеОбязанности` получает два опциональных поля: характеристику триггера (для входящих — `ВидВходящегоДокумента`) и требуемый вид документа. Обязанность с совпадающей характеристикой приоритетна над обязанностью без неё для той же пары; явный приоритет разрешает конфликт только между обязанностями одинаковой специфичности.
- **Назначение исполнителя** не оставляется неявным: вид триггера → наиболее специфичная обязанность → должность-владелец → действующий исполнитель этой должности на дату (функция выше). Ноль или более одного исполнителя — задача не создаётся без ручного решения. Детерминировано, без LLM.
- **Фильтрация кандидатов шаблона** — тоже детерминированная, в два шага перед запуском RAG: (1) `ТипДействия` выбирает нужный справочник шаблонов; (2) требуемый вид документа из найденной обязанности, если задан, сужает дальше. RAG/LLM ранжируют и выбирают только внутри уже отфильтрованного набора. Подробности — `docs/raw_specification.md` §4.1.4–4.1.5, `plans/implementation_plan.md` §6.2.

## 6. Сроки

- Срок пользовательской задачи — `Задача.ЗадачаИсполнителя`.
- `АИС_НормативыИИ` — только нормативное время ИИ-ответа.
- Сроки процессов — штатные шаблоны процессов.

## 7. Промпты и LLM

- Текст промптов — `ШаблоныТекстов`.
- Параметры (модель, температура, JSON-схема) — `АИС_ПромптПараметры`.
- DeepSeek — основной провайдер генерации.
- GigaChat — эмбеддинги.
- Локальная LLM — через OpenAI-совместимый endpoint; предпочтительна для вычитки и конфиденциальных документов.
- Провайдер и модель выбираются настройками, не кодом.
- При недоступности локальной LLM — очередь, внешний fallback или быстрая проверка.

## 8. Вычитка

- Два уровня: быстрая без LLM и глубокая LLM.
- Быстрая квоту не расходует; глубокая — по кнопке.
- Квота по умолчанию: 30 страниц в день на пользователя; настраивается по роли/подразделению.
- Оценка страницы: ~1800 символов; токены пишутся в аудит, пользователю не показываются.
- Замечания: цитата, позиция, тип, важность, сообщение, предложение, confidence.
- Цитата обязана существовать в тексте; confidence ниже порога отбрасывается.
- Автоприменения нет; accept/reject; принятые применяются детерминированно.
- Ошибка LLM не списывает квоту; частичная проверка списывает фактически проверенные страницы.
- Локальная LLM предпочтительна; внешняя — по политике организации.

## 9. Доступ

- Базовые документы и задачи — штатная модель прав.
- RLS на `АИС_*` — через ссылку на базовую задачу/документ.
- Администратор не видит содержание задач.
- Аудитор читает аудит и отчёты без изменения.
- Методолог/ответственный за шаблон управляет шаблонами.
- Квоты проверяются на сервере 1С.

## 10. Интерфейс

- Гибрид: команды и вкладки в штатных формах + отдельное рабочее место ДЛ.
- Мастер шаблонов — отдельная обработка.
- Панель замечаний — команда/форма в проекте документа.
- Админ-панель — настройки, промпты, квоты, индексация, health.
- Длительные операции — фоновые задания.

## 11. Развёртывание

- 1С-сервер + PostgreSQL.
- RAG-сервис + Qdrant в Docker.
- Локальная LLM — отдельный хост/GPU или локальный inference-сервер.
- Внешние DeepSeek/GigaChat — по политике и с TLS-проверкой.

## 12. Тестирование

- BSL-тесты: плейсхолдеры, состояния, склонения, разделы, квоты.
- RAG/LLM — mock/respx; локальный Qdrant.
- Шаблоны — фикстуры: identical, +1/-1 placeholder, renamed, changed type/source, different doc type.
- Вычитка — фикстуры с цитатами/без цитат, confidence, квоты, перегрузка.
- E2E: входящий документ → задача → RAG → LLM → проект → разделы → вычитка → подпись.
- Негативные: LLM down, RAG down, невалидный JSON, нет квоты, нет шаблона.

## 13. Что осталось за границами проектирования

- Точная модель локальной LLM и требования к GPU.
- Точные значения весов/порогов после прототипа (сейчас в конфиге).
- Юридическая значимость подтверждения раздела.
- Промышленная HA-топология.
- Коммерческая лицензия на Документооборот.
- Метрика «выбор шаблона ≥90% на 50 сценариях» — пилотная; порог и размер выборки пересматриваются при росте корпуса шаблонов после внедрения мастера шаблонов.
- Компаундирование ошибок по цепочке шагов (выбор шаблона → N заполнений → генерация) не оценивается отдельной формулой; вместо этого в критерии приёмки Этапа 7 добавляется составная метрика «доля документов, собранных полностью без ручного вмешательства» на выборке реальных сценариев — измеряется эмпирически, а не выводится из метрик по шагам.
- Включение FR-040 (RAG-извлечение значений из текста) и FR-041 (ACL-индексация документов) обусловлено предварительной реализацией гибридного поиска и reranking (см. §18) — до этого остаются вне MVP.
- Риск «рефлексивной хрупкости» эскалации (анализ срыва сроков сам зависит от LLM, который мог быть причиной срыва) принят как есть: детерминированный fallback-таймлайн уже предусмотрен (`raw_specification.md` §4.7.1), дополнительных мер не требуется.

Эти вопросы не блокируют реализацию и вынесены в эксплуатационные решения.

## 14. Контроль сроков и эскалация

- В базовой конфигурации есть штатный механизм напоминаний `ScheduledJobs.КонтрольСрокаЗадач` (`CommonModule.РаботаСУведомлениями.КонтрольСрокаЗадача`): уведомляет подписчиков о приближении и о просрочке срока задачи через `РегистрыСведений.ОчередьУведомлений`, с настраиваемой периодичностью на пользователя. Он не формирует документ, не анализирует причины и не адресует вышестоящему ДЛ — функция эскалации с LLM-анализом причин в базовой конфигурации отсутствует, дублирования нет.
- Решение: `АИС_ПроверкаСроковЗадач` может (не обязана в MVP) подписываться на событие `Перечисления.СобытияУведомлений.ПодошелСрокЗадачи`/просрочку из штатной очереди уведомлений как источник триггера, вместо независимого опроса сроков задач — снижает дублирование логики обнаружения просрочки. Решение по реализации — на Этапе 9.
- Последствие превышения `АИС_НормативыИИ` (нормативное время ИИ-ответа, НЕ срок задачи): запись события в `АИС_ИсторияДействийИИ` с типом «НормативПревышен» + отображение в отчёте `АИС_СтатистикаЗадач`. Автоматической эскалации только по превышению норматива ИИ нет — эскалация остаётся привязана к штатному `СрокИсполнения` задачи. Решение фиксируется в `raw_specification.md` §4.3.3.
- Доклад о срыве сроков получает обязательный шаг проверки перед отправкой — по аналогии с `ВерификацияДЛ` для обычных исходящих документов, а не прямую отправку сразу после генерации LLM. Доклад создаётся со статусом `Проект`; подтверждает и может отредактировать вышестоящее ДЛ (адресат доклада) либо исполнитель, роль подтверждения уточняется при реализации Этапа 9, но подтверждение обязательно в обоих случаях. Автоматическая отправка без подтверждения — запрещена. Фиксируется в `raw_specification.md` §4.7.1, `process-diagrams.md` §5.2, таблица переходов — `implementation_plan.md` §6.1.

## 15. Бюджет и защита ресурсов LLM

- Основной пайплайн оркестрации (выбор шаблона, классификация источника, формирование запроса, генерация, анализ срыва сроков) получает собственную квоту по аналогии с вычиткой: лимит токенов/стоимости на организацию в день и опционально на пользователя; при превышении — новые задачи переходят в режим только ручного выбора шаблона/ручного заполнения (не теряются, не блокируются полностью). Параметры — в `config/parameters.yaml`; новое требование фиксируется как NFR рядом с NFR-032.
- Вводится общий компонент ограничения скорости запросов к внешним LLM/эмбеддингам (условное имя `АИС_ОчередьЗапросовLLM`), разделяемый между оркестратором, мастером шаблонов и вычиткой. Приоритет по умолчанию: основной пайплайн оркестрации > мастер шаблонов > вычитка. Единый backoff вместо независимых ретраев каждой подсистемы. Проектируется и реализуется на Этапе 4, до включения конкурентной обработки 100 задач (Этап 7).
- Confidence выбора шаблона не принимается как самостоятельная калиброванная метрика. Перед фиксацией порога в `config/parameters.yaml` проводится калибровочный прогон `tools/llm_eval` на выборке сценариев: сравнивается заявленный confidence с фактической корректностью выбора; порог подбирается по результату, а не задаётся произвольно. Повторяется при существенном обновлении модели провайдера.

## 16. Данные и аудит

- Риск «утечка документов во внешний LLM» относится не только к вычитке, но и к основному пайплайну генерации (DeepSeek получает содержание входящих документов уже с Этапа 1 MVP). Требование «локальная LLM или политика организации» (ранее — только для вычитки, `raw_specification.md` §9) распространяется на весь пайплайн, с явной оговоркой: на демо-данных Этапов 1–7 ограничение не критично, обязательно — перед пилотом на реальных документах заказчика.
- `АИС_ИсторияДействийИИ` хранит полный промпт/ответ без срока хранения и без маскирования. Решение: срок хранения аудита ИИ-действий — не менее срока хранения связанной базовой задачи (штатная политика хранения Документооборота), автоматическое маскирование персональных данных в MVP не реализуется (технически ненадёжно для свободного текста), вместо этого доступ к `АИС_ИсторияДействийИИ` ограничивается ролью `АИС_Аудитор` и записывается в `NFR` как явное допущение о работе с ПДн. Пересмотр — при появлении требований конкретного заказчика.

## 17. Управленческие решения и экспертное мнение

Плейсхолдеры делятся на две категории по происхождению значения: **факт** (следует получить откуда-то — БД, API, расчёт, другое ДЛ как источник сведений) и **решение** (формулируется ДЛ как экспертное суждение — резолюция, оценка ситуации, формулировка поручения). Текущая модель `АИС_СпособыЗаполнения` не различает их; решено ввести различение без разрушения существующей модели:

- Добавляется новое значение перечисления `АИС_СпособыЗаполнения` — `РешениеДЛ` (по аналогии с существующими `ЗапросКДЛ`/`РучнойВвод`, которые остаются для простых фактов). Применяется на уровне ТЧ `АИС_Плейсхолдеры` (поле `СпособЗаполнения`).
- Взаимодействие для `РешениеДЛ` отличается от `ЗапросКДЛ`: задача показывает ДЛ релевантные прецеденты (RAG top-k по похожим прошлым решениям того же типа, без автозаполнения), позволяет зафиксировать рассмотренные и отклонённые варианты в комментарии к ответу задачи, не ограничивает ответ одной строкой. Реализация — обработка/форма ответа на задачу, без изменения модели `АИС_ЛистОжидания`.
- `АИС_НормативыИИ`/`СрокОжидания` для `РешениеДЛ` настраиваются отдельно от `ЗапросКДЛ` (по умолчанию дольше) и не ведут к автоматической эскалации по истечении — истечение срока для решения создаёт напоминание, а не доклад о срыве; реальная эскалация по решению требует дополнительно истечения штатного `СрокИсполнения` задачи. Исключает ситуацию, когда добросовестное обдумывание сложного решения трактуется как срыв срока (связано с §14).
- Промежуточная форма между скаляром и `АИС_РазделыДокумента` для `РешениеДЛ` не вводится в MVP: короткое суждение (1–2 предложения) хранится как обычное строковое значение плейсхолдера; полноценный `Раздел` используется только если решение действительно развёрнутое (структурированный блок документа). Решение пересматривается, если практика покажет недостаточность.
- Голосовой ввод/диктовка — явно вне границ MVP, зафиксировано как backlog (не как упущение). Канал ответа на задачу остаётся текстовым; распознавание речи может быть добавлено как клиентская функция поверх штатной формы задачи без изменения модели данных.
- Формулировка глоссария `docs/raw_specification.md` §2 уточнена: «другое ДЛ» разделяется на «источник сведений, которыми ДЛ обладает» и «ДЛ как лицо, принимающее решение» — второе описывается через `РешениеДЛ`, а не как просто ещё один источник данных.

## 18. Усиление RAG и мастера шаблонов

- Публикация/обновление шаблона в мастере шаблонов вызывает `upsert` в RAG-сервис синхронно в рамках операции публикации, а не ждёт очередного запуска регламентного задания индексации (которое остаётся как догоняющая/восстановительная синхронизация раз в 5 минут). Устраняет гонку «задача ищет шаблон раньше, чем он проиндексирован».
- Рекурсивное разрешение плейсхолдеров в MVP кэширует (мемоизирует) результат одного и того же под-значения в рамках задачи — простой словарь «подпись параметров → значение» на время жизни задачи, без построения полного графа зависимостей (граф — после MVP, уже зафиксировано в `implementation_plan.md` §6.3).
- Чанкинг RAG-сервиса меняется с фиксированной длины на чанкинг по структурным границам (абзац/пункт/элемент списка) с ограничением максимальной длины чанка; overlap сохраняется только на границе чанка, а не внутри структурной единицы. Выполняется как доработка RAG-сервиса после Этапа 3, не блокирует MVP (корпус из нескольких шаблонов устойчив и к текущему чанкингу).
- Гибридный поиск (dense + полнотекстовый/BM25) и шаг reranking перед top-k в `/v1/search` — обязательная предпосылка перед включением FR-040 (RAG-извлечение значений) и FR-041 (ACL-индексация документов), не требуется для MVP (выбор шаблона по текущему корпусу).
- Регулярный (не в CI, по стоимости) прогон `tools/llm_eval` на golden-наборе сценариев вводится на Этапе 7 как часть упрочнения — фиксирует метрики выбора шаблона и retrieval, чтобы заметить дрейф при обновлении моделей провайдерами.
