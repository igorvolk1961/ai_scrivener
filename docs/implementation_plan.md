# План реализации ai_scrivener как расширения 1С:Документооборот 2.1.38.11

## 1. Цель и границы

Создать расширение `.cfe` к 1С:Документооборот 2.1.38.11 с ИИ-помощником должностного лица и внешним stateless RAG-сервисом:

- 1С:Документооборот хранит доменные данные, документы, задачи, пользователей и права.
- Расширение добавляет ИИ-оркестрацию, состояния, плейсхолдеры, аудит и интерфейс помощника.
- 1С вызывает DeepSeek для генерации и GigaChat Embeddings через RAG-сервис.
- Qdrant хранит векторы шаблонов, должностных обязанностей и, позже, документов.
- MVP: сквозной сценарий «входящий документ → задача → выбор шаблона → заполнение плейсхолдеров → проект исходящего документа → проверка и подпись ДЛ».

Вне MVP: дообучение LLM, электронная подпись, email/телефония, промышленный HA, индексация конфиденциальных документов, мобильный клиент, коммерческая эксплуатация демо-стенда.

### 2.1. Почему не RAG для всех значений

Qdrant возвращает текстовые фрагменты, а не транзакционные значения полей. Точные значения (`номер`, `дата`, `срок`, `адресат`) берутся из 1С. RAG используется для выбора шаблона, нормативного контекста и позже — для извлечения значений из неструктурированных текстов с обязательной проверкой ДЛ.

### 2.2. Инженерные правила

- Источник истины требований — `docs/requirements/requirements.yaml`; Markdown-документы и матрица генерируются.
- Все настраиваемые числовые параметры хранятся в `config/parameters.yaml` и проверяются по `config/parameters.schema.json`.
- Новые объекты расширения получают префикс `АИС_`; штатные объекты Документооборота не дублируются.
- Перед реализацией metadata выполняется инвентаризация базы: фактические имена, реквизиты, режим совместимости.
- В коде запрещены хардкод числовых параметров, `TODO`, `FIXME`, `NotImplementedError` и несогласованные заглушки.
- Код покрывается поведенческими тестами; внешние сервисы изолируются mock/respx/локальным Qdrant.
- Пре-коммит запускает общие проверки, ruff, ruff-format, mypy, yamllint, валидацию конфига, проверку трассируемости, запрет заглушек и хардкода, BSL Language Server и быстрые тесты.
- Новые требования добавляются только после согласования и со статусом `approval: proposed`.
- Базовая конфигурация, `.dt`, `.cf`, `.cfe` и рабочая база в репозиторий не попадают.

## 3. Архитектура

```
1С:Документооборот 2.1.38.11 (базовая конфигурация)
  ├── Пользователи, Сотрудники, Должности, Подразделения
  ├── ВходящийДокумент, ИсходящийДокумент, ВнутреннийДокумент, Задача
  └── Файлы и штатная модель прав
        ▲
        │ расширение ai_scrivener (.cfe)
        │
  ┌─────┴──────────────────────────────────────────────┐
  │ АИС_ОркестраторЗадач                               │
  │ АИС_РазрешительПлейсхолдеров                       │
  │ АИС_ГенераторДокументов                            │
  │ АИС_РаботаСЛистомОжидания                          │
  │ АИС_АудитДействийИИ                                │
  │ АИС_ИнтеграцияСLLM ───────────────▶ DeepSeek API    │
  │ АИС_ИнтеграцияСRAG ───────────────▶ RAG-сервис      │
  └────────────────────────────────────────────────────┘
                                         │
                                         ▼
                                   RAG-сервис (FastAPI)
                                     ├── GigaChat OAuth + Embeddings
                                     └── Qdrant
```

Потоки:

1. Регистрация входящего документа в Документообороте создаёт задачу расширения в состоянии `Инициация` без вызова LLM в транзакции документа.
2. Оркестратор выбирает шаблон: RAG top-k → LLM `ВыборШаблонаДокумента` → валидация ID и confidence.
3. Разрешитель заполняет плейсхолдеры: прямое поле, утверждённый запрос к БД, запрос другому ДЛ, расчётный сервис, внешний API, RAG-контекст.
4. Генератор формирует текст и создаёт проект исходящего документа в штатном `ИсходящийДокумент`.
5. ДЛ проверяет, редактирует и подписывает; задача завершается.
6. Все шаги, промпты, ответы, RAG-кандидаты и переходы состояний пишутся в аудит расширения.

Развёртывание: 1С-сервер + PostgreSQL; RAG-сервис и Qdrant — Docker Compose на том же или отдельном хосте; Qdrant не публикуется наружу; RAG-сервис за TLS/reverse proxy и с service-token.

## 5. Метаданные расширения

### 5.1. Принцип переиспользования

Сначала инвентаризация базы, затем код. Для каждого объекта спецификации выбирается действие:

- `reuse` — используется штатный объект без изменений;
- `extend` — к штатному объекту добавляются реквизиты, табличные части, формы или команды;
- `new` — создаётся объект `АИС_*`, если аналога нет или структура базы не подходит.

| Объект спецификации | Кандидат в базе | Действие | Fallback |
|---|---|---|---|
| `ДолжностныеЛица` | `Справочник.Пользователи` + `Справочник.ФизическиеЛица` (ФИО через `ФизЛицо`) | reuse | расширить `Пользователи` |
| `Должности` | `Справочник.Должности` | reuse | `АИС_Должности` |
| `НазначенияДолжностей` | штатного регистра в ПРОФ нет | new | `АИС_НазначенияДолжностей` |
| `ДолжностныеОбязанности` | нет прямого аналога | new | `АИС_ДолжностныеОбязанности` |
| `ШаблоныДокументов` | `Справочник.ШаблоныВходящихДокументов`, `ШаблоныИсходящихДокументов`, `ШаблоныВнутреннихДокументов` | extend | `АИС_ШаблоныДокументов` |
| `ТипыДокументов` | `Справочник.ВидыВходящихДокументов`, `ВидыИсходящихДокументов`, `ВидыВнутреннихДокументов` | reuse | `АИС_ТипыДокументов` |
| `ВходящийДокумент` | `Справочник.ВходящиеДокументы` | extend | согласовать изменение модели |
| `ИсходящийДокумент` | `Справочник.ИсходящиеДокументы` | extend | согласовать изменение модели |
| `РаспоряжениеВходящее`, `РаспоряжениеИсходящее`, `Доклад` | `Справочник.ВнутренниеДокументы` + вид | extend | новые `АИС_*` документы |
| `ДокладОСрывеСроков` | `Справочник.ВнутренниеДокументы` + табличная часть | extend | `АИС_ДокладОСрывеСроков` |
| `Задача` | `Задача.ЗадачаИсполнителя` | reuse для поручений | `АИС_ЗадачиРеакции` — только ИИ-оркестрация |
| `Файлы` | `Справочник.Файлы` / `ВерсииФайлов` / `ТомаХраненияФайлов` | reuse | — |
| `КаналыСвязи` | `Справочник.КаналыОбсуждений` не подходит по смыслу | new | `АИС_КаналыСвязи` |
| `ЗапросКДЛ`, `РезультатВнешнегоЗапроса`, `РезультатВнешнегоДействия`, `РасписаниеТаймеров` | нет | new | `АИС_*` |
| Регистры задач, плейсхолдеров, ожидания, аудита, сроков | нет | new | `АИС_*` |

Правило: если объект базы отсутствует или его структура не подходит, создаётся `АИС_*`, но не дублируется существующий объект с тем же смыслом.

Фактическая база — ПРОФ 2.1.38.11. В ней нет `Справочник.Сотрудники` и `Справочник.Подразделения`: сотрудник представлен `Пользователи` + `ФизическиеЛица`, оргструктура — `СтруктураПредприятия`. Документы в 2.1 — это справочники (`ВходящиеДокументы`, `ИсходящиеДокументы`, `ВнутренниеДокументы`), а задачи — `Задача.ЗадачаИсполнителя`. Эти имена проверены по выгрузке `/tmp/kilo/docmng_xml`; при изменении версии базы маппинг повторно проверяется.

### 5.3. Справочники

| Объект | Ключевые реквизиты и дополнения |
|---|---|
| `Пользователи` (база) | используется для входа; содержит `ФизЛицо`, `Подразделение`, контактную информацию |
| `ФизическиеЛица` (база) | ФИО и персональные данные; ДЛ определяется через `Пользователи.ФизЛицо` |
| `Должности` (база) | иерархия и признак активности; связь с ДЛ — через `АИС_НазначенияДолжностей` |
| `СтруктураПредприятия` (база) | организационная структура; руководитель подразделения |
| `АИС_ДолжностныеОбязанности` | наименование, должность, текст, версия, дата утверждения; ТЧ `Правила`: тип триггера, тип действия, приоритет, шаблон по умолчанию |
| `ШаблоныВходящихДокументов`, `ШаблоныИсходящихДокументов`, `ШаблоныВнутреннихДокументов` (база) | расширяются ТЧ `АИС_Плейсхолдеры`; если структура не подходит — `АИС_ШаблоныДокументов` |
| `ВидыВходящихДокументов`, `ВидыИсходящихДокументов`, `ВидыВнутреннихДокументов` (база) | используются для типов документов; предопределённые значения не дублируются |
| `АИС_ТипыТриггеров` | 6 предопределённых + расширяемые |
| `АИС_ТипыДействий` | 6 предопределённых + расширяемые |
| `АИС_ИсточникиДанных` | тип источника, URL, таймаут, JSON-схема ответа, шаблон запроса, допустимые параметры, активность |
| `АИС_КаналыСвязи` | телефон, email, лично, мессенджер, другое; штатный `КаналыОбсуждений` не подходит по смыслу |
| `АИС_ПромптШаблоны` | код, текст, ожидаемая JSON-схема, модель, температура, максимум токенов, версия, активность |

ТЧ `Плейсхолдеры` (в штатном или новом справочнике шаблонов):

- `Имя`, `Описание`, `ТипДанных`, `Обязательность`.
- `ИсточникДанных`, `СпособЗаполнения`.
- `ВыражениеИсточника` — для прямого поля, например `Источник.РегистрационныйНомер`.
- `ШаблонЗапроса` — утверждённый запрос 1С с параметрами `&Параметр`.
- `ПараметрыИсточникаJSON`, `СхемаОтветаJSON`, `Порядок`.

`СпособыЗаполнения`: `ПрямоеПоле`, `ЗапросВБД`, `ЗапросКДЛ`, `РасчетныйСервис`, `ВнешнийAPI`, `RAGКонтекст`, `РучнойВвод`.

### 5.4. Документы

Штатные объекты Документооборота 2.1 (в ПРОФ это справочники):

- `Справочник.ВходящиеДокументы` — триггер; расширяется признаком обработки и ключом идемпотентности.
- `Справочник.ИсходящиеДокументы` — проект и результат; расширяется идентификатором задачи, ссылкой на шаблон и панелью источников.
- `Справочник.ВнутренниеДокументы` — распоряжения и доклады через вид документа; при необходимости расширяется табличной частью плана мероприятий.
- `Задача.ЗадачаИсполнителя` — пользовательские поручения; не используется как хранилище состояний ИИ-оркестрации.

Новые документы расширения:

- `АИС_ЗапросКДЛ` — ID запроса, задача, плейсхолдер, отправитель, получатель, текст, срок, состояние.
- `АИС_РезультатВнешнегоЗапроса` — ID запроса, ДЛ-ответивший, текст ответа, дата получения.
- `АИС_РезультатВнешнегоДействия` — задача, ДЛ, дата/время, канал связи, контакт, содержание, файлы.
- `АИС_РасписаниеТаймеров` — cron-подобное расписание, ДЛ/должность, тип действия, следующий запуск, активность.
- `АИС_ДокладОСрывеСроков` — причина срыва, план мероприятий (мероприятие, срок, ответственный, тип).

Задачи и плейсхолдеры не удалять: менять состояние. Для конкурентного доступа использовать `БлокировкаДанных` по задаче и поле `Версия`; после внешнего вызова перечитывать запись и отбрасывать устаревший результат.

- `АИС_ВышестоящееДолжностноеЛицо` — свои задачи и доклады, адресованные ему.
- `АИС_Аудитор` — чтение аудита и отчётов без изменения.
- `АИС_СервисныйПользователь` — права для регламентных/фоновых заданий и HTTP-сервисов, без интерактивного входа.

Правила:

- В `УстановкаПараметровСеанса` определяется `ТекущееДЛ` через `Пользователи` (при необходимости — `Пользователи.ФизЛицо`); при необходимости добавляется параметр `АИС_ТекущееДЛ`.
- RLS реализуется на новых объектах `АИС_*`: `ДЛИсполнитель = &ТекущееДЛ`, доступ к плейсхолдерам и листу ожидания — через задачу.
- Для штатных документов Документооборота используется его модель прав; расширение не дублирует RLS базовых объектов.
- Для вышестоящего ДЛ — доступ к докладам по адресату; иерархия должностей используется при выборе адресата эскалации.
- Обязательные негативные тесты: ДЛ не видит чужую задачу, администратор не видит задачи, аудитор не может изменить запись.

### 5.9. Ограничения расширения

- Нельзя изменять состав измерений и ресурсов базовых регистров; для новых измерений создаётся регистр `АИС_*`.
- К базовым объектам можно добавлять реквизиты, табличные части, формы и команды в пределах возможностей расширения.
- Режим совместимости расширения устанавливается равным режиму совместимости базы, а не «8.3.27 по умолчанию».
- Расширение не должно требовать изменения базовой конфигурации; применение и снятие `.cfe` проверяются на копии демо-базы.

## 6. Состояния и сценарии

### 6.1. Состояния задачи

`Инициация` → `ПоискШаблона` → `РазрешениеПлейсхолдеров` → (`Ожидание` ↔ `РазрешениеПлейсхолдеров`) → `Генерация` → `ВерификацияДЛ` → `Завершена`.

В любое состояние (кроме `Завершена`) может быть выполнена `Эскалация`.

Правила:

- Переходы только через `АИС_ОркестраторЗадач.ПеревестиСостояние` с проверкой допустимости, версии и записью в аудит.
- `Ожидание` снимается ответом из листа ожидания, истечением срока или ручным вмешательством.
- `Завершена` только после подписи/ручного завершения ДЛ; автоматического завершения нет.
- При ошибке LLM/сети задача остаётся в текущем состоянии; повтор по таймеру или вручную.

### 6.2. MVP-сценарий

1. ДЛ регистрирует и проводит `Справочник.ВходящиеДокументы`.
2. При проведении создаётся задача расширения с ключом идемпотентности; LLM не вызывается.
3. Регламентное задание `АИС_ОркестрацияАктивныхЗадач` переводит задачу в `ПоискШаблона`.
4. RAG-сервис возвращает top-10 шаблонов; DeepSeek выбирает один и возвращает JSON.
5. Проверяется, что ID входит в кандидаты, confidence выше порога; иначе — ручной выбор.
6. Создаются записи `АИС_СостоянияПлейсхолдеров`; для каждого плейсхолдера выполняется разрешение.
7. После заполнения всех обязательных плейсхолдеров — `Генерация`.
8. Детерминированная подстановка значений; при необходимости DeepSeek улучшает текст. Если LLM вернул текст без данных — используется детерминированный вариант.
9. Создаётся `Справочник.ИсходящиеДокументы` со статусом `Проект`; задача → `ВерификацияДЛ`.
10. ДЛ редактирует и подписывает; статус `Подписан`, задача → `Завершена`.
11. Все вызовы и переходы видны в `АИС_ЖурналЗадачи`.

### 6.3. Разрешение плейсхолдеров

- Парсер: regex `\{\{\s*([A-Za-zА-Яа-я0-9_]+)\s*\}\}`; синхронизация с ТЧ шаблона; ошибки при дублях, неизвестных именах, лишних описаниях.
- Лимиты: глубина 5, число запросов на задачу 50; при превышении — `Эскалация`.
- `ПрямоеПоле`: значение из источника триггера без LLM.
- `ЗапросВБД`: LLM выбирает утверждённый шаблон запроса и заполняет только параметры; параметры валидируются по именам и типам. Результат — 0 или >1 строки: плейсхолдер `НеМожетБытьЗаполнен`, ручное решение/эскалация.
- `ЗапросКДЛ`: создать `АИС_ЗапросКДЛ` и запись листа ожидания, плейсхолдер → `Ожидает`, задача → `Ожидание`.
- `РасчетныйСервис`: рекурсивно разрешить аргументы, вызвать HTTP-сервис, проверить JSON-схему.
- `ВнешнийAPI`: запрос по схеме источника, таймаут, валидация ответа.
- `RAGКонтекст`: только для свободного текста; LLM извлекает значение с цитатой и confidence; ниже порога — ручной ввод. В MVP не включать.
- `РучнойВвод`: плейсхолдер ждёт ДЛ.

#### Параллелизм разрешения плейсхолдеров

В MVP плейсхолдеры одной задачи разрешаются последовательно; параллелизм допускается на уровне задач — несколько фоновых заданий обрабатывают разные задачи одновременно.

Причины последовательного MVP:

- независимые плейсхолдеры могут зависеть друг от друга через параметры запросов и аргументы расчётных сервисов;
- общие счётчики задачи (`глубина`, `число запросов`) и переходы состояния требуют атомарного обновления;
- несколько одновременных запросов к DeepSeek/GigaChat проще уложить в rate limit;
- проще обеспечить воспроизводимый аудит и обработку ошибок.

Параллельное разрешение внутри задачи добавляется после MVP:

- строится граф зависимостей плейсхолдеров; выполняются топологические слои;
- параллелятся только независимые плейсхолдеры типов `ПрямоеПоле`, `ЗапросВБД`, `РасчетныйСервис`, `ВнешнийAPI`;
- `ЗапросКДЛ` и `РучнойВвод` не блокируют другие плейсхолдеры, но переводят задачу в `Ожидание`;
- ограничение параллелизма — 2–4 операции на задачу, настраивается;
- записи `АИС_СостоянияПлейсхолдеров` обновляются независимо, счётчики задачи — атомарно, с блокировкой/версией;
- перед `Генерация` — барьер: ждём завершения всех веток и собираем ошибки;
- для 1С используется пул фоновых заданий, а не отдельное задание на каждый плейсхолдер.

### 6.4. Лист ожидания и эскалация

- `АИС_ОбработкаЛистаОжидания` каждую минуту: `Отправлен` + срок истёк → `СрокИстек` + триггер `ИстечениеСрокаОжидания`.
- `АИС_РезультатВнешнегоЗапроса` при проведении: найти запись по ID, проверить состояние, заполнить плейсхолдер, возобновить родительскую задачу; создать дочернюю задачу типа `ПоступлениеОтветНаЗапрос` для трассировки.
- `АИС_ПроверкаСроковЗадач` каждую минуту: задачи не в `Завершена` с истёкшим сроком → эскалация.
- Эскалация: собрать таймлайн, вызвать `АнализСрываСроков`, создать `АИС_ДокладОСрывеСроков`, адресат — вышестоящая должность, копия — исполнитель; задача → `Эскалация`. При сбое LLM создать доклад с детерминированным таймлайном и пометкой «причина требует уточнения».
- Дочерние задачи имеют `РодительскаяЗадача`; циклы запрещены.

### 6.5. Идемпотентность и блокировки

- Ключ идемпотентности триггера: `ТипТриггера + ID источника + дата`; повторная регистрация не создаёт дубль.
- ID запроса в листе ожидания — UUID; повторный ответ не меняет состояние дважды.
- Регламентные задания захватывают пачку задач, ставят блокировку, обрабатывают, снимают; параллельная обработка одной задачи невозможна.
- Внешние вызовы выполняются вне транзакции; после ответа — новая транзакция с проверкой версии.

### 6.6. Интерфейс

- Гибридная схема: команды и вкладка ИИ в штатных формах `Справочник.ВходящиеДокументы`, `Справочник.ИсходящиеДокументы`, `Задача.ЗадачаИсполнителя`.
- Отдельное рабочее место `АИС_РабочееМестоДЛ` — очередь ИИ-задач, фильтры, таймлайн, плейсхолдеры и лист ожидания.
- В форме проекта исходящего документа — редактируемый текст и панель источников по плейсхолдерам.
- Административная обработка `АИС_АдминПанель` — справочники расширения, сроки, промпты, health RAG/LLM, переиндексация.

## 7. RAG-сервис

### 7.1. Стек

Python 3.12, FastAPI, pydantic-settings, httpx, qdrant-client, pytest, respx, ruff, mypy, uv. Docker-образ на python:3.12-slim.

### 7.2. API

`GET /health` — состояние сервиса, Qdrant, GigaChat (без секретов).

`POST /v1/search`

```json
{
  "query": "текст входящего документа",
  "top_k": 10,
  "filters": {
    "source_types": ["template"],
    "doc_types": ["ИсходящийДокумент"],
    "active": true,
    "position_ids": []
  }
}
```

Ответ: `results[]` с `score`, `source_type`, `source_id`, `version`, `title`, `chunk_index`, `text`, `metadata`.

`POST /v1/index/upsert` — батч `{source_type, items:[{source_id, version, title, text, metadata}]}`; идемпотентно; старые точки источника удаляются перед вставкой.

`POST /v1/index/replace` — полный снимок источника; удаляет устаревшие точки.

`DELETE /v1/index/{source_type}/{source_id}`.

Все методы, кроме `/health`, требуют `X-Service-Token`.

### 7.3. Qdrant

- Коллекция `ai_scrivener_knowledge_v1`, cosine, размерность из конфига GigaChat.
- Payload: `source_type`, `source_id`, `version`, `title`, `text`, `chunk_index`, `doc_type`, `position_ids`, `active`, `updated_at`.
- Индексы payload: `source_type`, `active`, `doc_type`, `source_id`, `position_ids`.
- ID точки: UUIDv5 от `source_type:source_id:version:chunk_index`.
- Фильтрация по `active=true`; ACL по `position_ids` включать только после индексации документов (не в MVP).

### 7.4. GigaChat

- OAuth: `POST https://ngw.devices.sberbank.ru:9443/api/v2/oauth`, `scope=GIGACHAT_API_PERS`, `RqUID`, Basic auth из client_id/client_secret.
- Токен кэшировать в памяти, обновлять за 60 секунд до истечения; при 401 — одно обновление и повтор.
- Embeddings: `POST https://gigachat.devices.sberbank.ru/api/v1/embeddings`, модель `EmbeddingsGigaR`, подтверждённая размерность — 2560, батчи до 32 текстов, таймаут 30 с, retry на 429/5xx.
- Для GigaChat используется публичный корневой сертификат «Russian Trusted Root CA» (`config/russian_trusted_root_ca.pem`); TLS-проверка не отключается. Путь к CA задаётся в `RAG_GIGACHAT_CA_BUNDLE`.
- Размерность задаётся в `config/parameters.yaml` и сверяется при старте с пробным вектором; при несовпадении — понятная ошибка и инструкция пересоздать коллекцию.

### 7.5. Чанкинг и индексация

- Нормализация текста, разбиение по заголовкам/абзацам, максимум ~1000 символов, overlap ~150.
- В чанк добавляется заголовок и тип источника.
- 1С отправляет шаблоны и обязанности из фактических объектов базы; RAG-сервис не читает 1С напрямую.
- Индексация: регламентное задание каждые 5 минут по `ДатаИзменения` + даты последней индексации; полная переиндексация из админ-панели.
- При удалении/деактивации шаблона 1С вызывает delete/upsert `active=false`; при недоступности — полная переиндексация позже.
- В MVP индексируются только шаблоны и должностные обязанности; документы — после реализации ACL.

### 7.6. Отказоустойчивость

- 1С при недоступности RAG использует полный список активных шаблонов (если он не больше лимита) или ручной выбор; задача не падает.
- Ошибки индексации логируются и повторяются; даты индексации обновляются только после успешного ответа.
- Сервис не логирует тексты документов; только ID, размеры, коды ошибок.

## 8. Интеграция с DeepSeek

Общий модуль `АИС_ИнтеграцияСLLM`:

- Модель и base URL берутся из локального `.env` (`DEEPSEEK_MODEL=deepseek-v4-flash`, `DEEPSEEK_BASE_URL=https://api.deepseek.com/v1`); ключ хранится в безопасном хранилище 1С.
- `ОтправитьПромпт(ТекстПромпта, ПараметрыМодели)`.
- `ОтправитьПромптСОжиданиемJSON(ТекстПромпта, ОжидаемаяСхема)`.
- `ВыбратьМодель(ТипЗадачи)`.
- HTTP-клиент: base URL, Bearer-ключ, таймаут, `response_format={"type":"json_object"}`, `temperature`.
- Retry: до 3 попыток при сетевых ошибках/5xx/невалидном JSON; пауза 1/2/4 с; каждая попытка в аудите.
- Валидация JSON — явные функции под каждую схему, не универсальный JSON Schema.
- При исчерпании попыток — ручное вмешательство/эскалация, задача сохраняется.
- Стоимость и токены считать по настройкам тарифа и писать в аудит.

Промпт-шаблоны:

| Код | Вход | Выход |
|---|---|---|
| `ВыборШаблонаДокумента` | тип триггера, содержание, RAG-кандидаты | `{template_id, confidence, reason}` |
| `ФормированиеПоисковогоЗапроса` | описание плейсхолдера, контекст, допустимые параметры | `{query_template_id, parameters}` |
| `КлассификацияИсточника` | описание плейсхолдера | `{source_type}` |
| `ГенерацияТекстаДокумента` | шаблон, значения, RAG-контекст | `{document_text}` |
| `АнализСрываСроков` | таймлайн | `{reasons, immediate_actions, long_term_actions, summary}` |
| `ИзвлечениеПлейсхолдеров` | текст шаблона | `{placeholders:[...]}` (админ-операция) |
| `ИзвлечениеЗначенияИзКонтекста` | плейсхолдер + RAG-фрагменты | `{value, confidence, citations}` (позже) |

Защита от prompt injection: входящий текст передаётся в отдельных delimiters, system prompt запрещает следовать инструкциям из данных, LLM не имеет инструментов и не формирует исполняемый код/запросы.

## 9. Интерфейсы и отчёты

- `АИС_РабочееМестоДЛ`: динамический список задач, фильтры по состоянию/сроку/типу, индикатор просрочки, счётчик новых триггеров, быстрые действия.
- `АИС_ФормаЗадачи`: метаданные, таймлайн аудита, плейсхолдеры, лист ожидания, кнопки «Возобновить», «Эскалация», «Завершить вручную», «Выбрать шаблон».
- `АИС_ФормаПроектаДокумента`: редактируемый текст, панель источников по плейсхолдерам, «Сгенерировать заново», «На согласование», «Подписать».
- `АИС_АдминПанель`: справочники расширения, нормативные сроки, промпты, health RAG/LLM, переиндексация, тест интеграции.
- `АИС_ТестИнтеграцииСLLM`: проверка DeepSeek, RAG, GigaChat с диагностикой без раскрытия секретов.
- Отчёты: `АИС_СтатистикаЗадач`, `АИС_ЖурналЗадачи`, `АИС_АнализСрывовСроков` (СКД).
- Длительные операции (генерация, переиндексация) — фоновые задания; UI не блокируется, показывает состояние.

## 11. Проверка и приёмка

### RAG-сервис

- `uv run pytest`, `uv run ruff check`, `uv run mypy`.
- Qdrant в тестах — локальный/in-memory; GigaChat и DeepSeek — mock через respx.
- Контрактные тесты: схемы запросов/ответов, 401, 413, 429, 5xx, несовпадение размерности.
- Интеграционный тест: 3 шаблона, русский запрос, релевантный top-1; повторная индексация не создаёт дублей.

### 1С

- Восстановление демо-базы из `.dt` в отдельную файловую базу.
- Проверка расширения в EDT (`build`/`validate`).
- `CheckConfig` в Конфигураторе на копии демо-базы.

- E2E по сценарию раздела 6.2.

### Метрики приёмки

- Выбор шаблона ≥90% на наборе из 50 сценариев.

- Все действия ИИ воспроизводимы по аудиту.

## 12. Риски и меры

| Риск | Мера |
|---|---|
| Демо-база окажется ПРОФ, а не КОРП | Маппинг строится по фактической базе; не использовать отсутствующие объекты |
| Ограничения демо-режима | Зафиксировать лимиты; RLS-тесты проводить в доступном режиме; не заявлять production-готовность |
| Конфигурация защищена от расширения | Проверить создание расширения до начала работ; при запрете — согласовать обходной путь |
| Режим совместимости базы ниже 8.3.27 | Установить режим расширения равным базе |
| Нельзя добавить RLS к базовым документам | RLS только на новых `АИС_*` объектах; базовые документы — штатные права Документооборота |
| Дублирование объектов базы | Обязательная инвентаризация и правило `reuse/extend/new` |
| Случайная фиксация `.dt`/`.cf`/`.cfe` | `.gitignore` и проверка `git status` перед коммитом |
| GigaChat: другая модель/размерность/лимиты | Модель и размерность в конфиге; проверка при старте; пересоздание коллекции |
| Невалидный JSON от DeepSeek | JSON-режим, 3 попытки, явные валидаторы, ручной fallback |
| Prompt injection из входящих документов | Delimiters, запрет инструкций из данных, отсутствие инструментов, валидация выхода |
| Произвольный запрос LLM к БД | Только утверждённые шаблоны + параметры |
| Устаревший индекс Qdrant | Версии, delete/replace, даты индексации, полная переиндексация |
| Утечка данных в облако | Минимизация, договор/политика, не индексировать конфиденциальные документы в MVP |
| Конкуренция задач | Блокировки, версия, короткие транзакции, идемпотентность |
| Сложность RLS | Отдельные роли, негативные тесты, запрет администратору видеть задачи |
| 1С не доверяет TLS-сертификатам GigaChat/DeepSeek | Установить корневые сертификаты, проверить `АИС_ТестИнтеграцииСLLM` |
| Зависание UI на LLM | Фоновые задания, состояния, ограничение таймаутов |

## 13. Открытые вопросы и допущения

1. Модель `EmbeddingsGigaR` и размерность 2560 подтверждены запросом к GigaChat; значения хранятся в конфигурации, код не хардкодит размерность.
2. База определена: `ДокументооборотПРОФ`, версия 2.1.38.11, режим совместимости 8.3.27.
3. Инвентаризация выполнена: в ПРОФ используются `Справочник.ВходящиеДокументы`, `Справочник.ИсходящиеДокументы`, `Справочник.ВнутренниеДокументы`, `Задача.ЗадачаИсполнителя`, `Справочник.Пользователи`, `Справочник.ФизическиеЛица`, `Справочник.СтруктураПредприятия`, `Справочник.Должности`. Штатного регистра назначений и `Справочник.КаналыСвязи` нет; они создаются как `АИС_*`.
4. Ограничения демо-режима (пользователи, срок, функциональность) уточняются у преподавателя.
5. Совместимость с 2.1.37.5 по умолчанию не требуется; проверяется только по отдельному требованию.
6. Коммерческая лицензия на Документооборот для production — вне рамок учебного проекта.
7. Политика хранения промптов/ответов с персональными данными и срок ретенции аудита: согласовать до промышленной эксплуатации.
8. Промышленная топология (отдельный хост RAG/Qdrant, HA, резервное копирование) — вне MVP, но volume Qdrant и бэкап PostgreSQL закладываются сразу.
