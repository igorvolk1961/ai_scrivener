# Детальный план Этапа 2 — «Метаданные и доступ»

Детализация чек-листа `docs/implementation_plan.md` §10 «Этап 2» до уровня, достаточного для создания объектов в EDT без дополнительных решений по ходу работы. Этап создаёт только структуру (метаданные, роли, демоданные) — бизнес-логика (общие модули, формы, регламентные задания) не входит и остаётся на Этапах 4–6.

## 1. Границы этапа

Входит: перечисления, справочники, регистры сведений, определяемые типы, расширение штатных объектов, роли, RLS, параметр сеанса, обработка демоданных, негативные тесты доступа.

Не входит: `АИС_ОркестраторЗадач`, `АИС_РазрешительПлейсхолдеров`, интеграции с LLM/RAG, формы и команды (кроме минимума, нужного для проверки RLS), регламентные задания. Эти объекты можно создавать пустыми заглушками только если без них нельзя проверить права — в остальном откладываются.

## 3. Новое перечисление — не требуется

Изначально предполагалось завести перечисление `АИС_СправочникШаблонов`. Проверка базовой конфигурации показала дублирование: штатное `Enums.ТипыОбъектов` уже содержит `ВходящиеДокументы`, `ИсходящиеДокументы`, `ВнутренниеДокументы` (и `Файлы`) — ровно то, что нужно. Новое перечисление не создаётся; вместо него штатный `ТипыОбъектов` используется как тип нового реквизита `АИС_ТипыДействий.ТипОбъекта` (§6).

## 4. Новые определяемые типы

| Тип | Состав | Назначение |
|---|---|---|
| `АИС_ИсточникТриггера` | входящий документ, распоряжение, бизнес-событие, расписание, внешний запрос | откуда пришёл триггер (`raw_specification.md` §5.6) |
| `АИС_РезультатЗадачи` | исходящий документ, внутренний документ, доклад, отсутствие результата | ссылка на результат задачи (`raw_specification.md` §5.6) |
| `АИС_АдресатЗапроса` | `CatalogRef.Пользователи`, `CatalogRef.Должности`, `CatalogRef.СтруктураПредприятия` | адресат запроса в листе ожидания; отдельный справочник адресатов не создаётся |

Поля «Характеристика» и «ТребуемыйВидДокумента» у `АИС_ДолжностныеОбязанности` (§5) — **не** отдельные именованные определяемые типы: у каждого ровно один потребитель (одно поле), именованный объект избыточен (принцип Оккама). Состав типизируется прямо на реквизите при создании.

## 5. Справочники

### `АИС_ДолжностныеОбязанности`

| Поле | Тип | Обязательность |
|---|---|---|

| `Текст` | строка (многострочная) | да |

| `ДатаУтверждения` | дата | да |
| `ТипТриггера` | `CatalogRef.АИС_ТипыТриггеров` (справочник, не перечисление); если на практике понадобится обязанность и для триггера, выражаемого штатным `ВидыБизнесСобытий`, решается отдельно при создании — не предрешается здесь | да |
| `ТипДействия` | `CatalogRef.АИС_ТипыДействий` | да |
| `Характеристика` | `CatalogRef.ВидыВходящихДокументов` (MVP; при появлении второй характеристики для другого типа триггера — расширить составом на реквизите, не раньше) | нет |

| `Приоритет` | число | нет, по умолчанию 0 — разрешает конфликт только между обязанностями одинаковой специфичности |
| `Активность` | булево | да |

Сопоставление при поиске обязанности (логика Этапа 5, но влияет на структуру): специфичная (с совпавшей характеристикой) всегда выигрывает у общей (без характеристики) для той же пары; `Приоритет` сравнивается только внутри одной группы специфичности.

## 6. Расширение `АИС_ТипыДействий`

| `ПодготовитьФрагментДокумента` | не заполняется (заполняет часть уже выбранного документа, не выбирает шаблон целиком) |

| `ПодготовитьДоклад` | `ВнутренниеДокументы` |
| `ВыполнитьДействиеВнеСистемы` | не заполняется |
| `ВозобновитьОтложеннуюЗадачу` | не заполняется |

## 9. Роли и доступ

Создать вместо `АИС_ОсновнаяРоль` пять ролей (`docs/implementation_plan.md` §5.8):

| Роль | Права |
|---|---|
| `АИС_АдминистраторСистемы` | чтение/запись справочников и регистров расширения, кроме содержания задач; не видит `АИС_КонтекстЗадачИИ`/`АИС_ИсторияДействийИИ` конкретных задач |
| `АИС_ДолжностноеЛицо` | штатные права на свои задачи (не меняются); чтение/запись `АИС_*` только через RLS по своей задаче |
| `АИС_ВышестоящееДолжностноеЛицо` | то же + чтение докладов, адресованных ему |
| `АИС_Аудитор` | чтение `АИС_ИсторияДействийИИ` и отчётов, без права записи |
| `АИС_СервисныйПользователь` | права, нужные регламентным заданиям и HTTP-сервисам на все `АИС_*` объекты |

RLS на `АИС_*`: через ссылку на базовую задачу (`Задача.ЗадачаИсполнителя`), не через собственную модель прав. Параметр сеанса `ТекущееДЛ` — в `УстановкаПараметровСеанса`, через `Пользователи` (при необходимости `Пользователи.ФизЛицо`).

## 10. Обработка `АИС_ЗаполнитьДемоДанные`

Создаёт на пустой демо-базе:

1. 3–5 ДЛ: `Пользователи` + `ФизическиеЛица`, с постоянной должностью через `СведенияОПользователяхДокументооборот`.
2. Иерархия должностей (`Должности` с родителем).
3. Минимум одну запись `Catalogs.ДелегированиеПрав` — проверка объединения обязанностей при замещении (п. 3 из обсуждения модели должностей).
4. 3 шаблона (по одному на вид) с заполненной ТЧ `АИС_Плейсхолдеры`.
5. Обязанности в `АИС_ДолжностныеОбязанности`:
   - минимум одна **общая** (без `Характеристика`) для пары (`ВходящиеДокументы`, `ПодготовитьИсходящийДокумент`);
   - минимум одна **специфичная** — `Характеристика = Авария` (вид входящего документа), та же пара или `ПодготовитьДоклад`, с `ТребуемыйВидДокумента` — чтобы проверить, что специфичная обязанность выигрывает и сужает выбор шаблона.
6. Значения `АИС_ТипыДействий.ТипОбъекта` по таблице §6.
7. Параметры промптов — начальные версии `АИС_ПромптПараметры` под типовые промпты (`docs/raw_specification.md` §4.8.2), без реального вызова LLM на этом этапе.

## 11. Негативные тесты доступа

- ДЛ не видит задачу другого ДЛ (ни штатную, ни `АИС_КонтекстЗадачИИ`).
- Администратор системы не видит содержание ни одной задачи ДЛ.
- Аудитор может прочитать `АИС_ИсторияДействийИИ`, но попытка записи/удаления отклоняется.
- Вышестоящее ДЛ видит задачи подчинённых только в объёме доклада, адресованного ему, не весь `АИС_КонтекстЗадачИИ` подчинённого.
- Сопоставление обязанности с характеристикой действительно выигрывает у общей обязанности той же пары (проверяется запросом/отчётом, не требует оркестратора).
