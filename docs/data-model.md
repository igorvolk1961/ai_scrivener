# Модель данных расширения ai_scrivener

Документ фиксирует дедуплицированную модель: какие объекты 1С:Документооборот используются повторно, какие создаются в расширении и почему.

Префикс `АИС_` — проектное соглашение; в документации он расшифровывается как «Автоматизированная интеллектуальная система» (AI Scrivener). Это не стандарт 1С, а способ отделить объекты расширения от базовых.

## 1. Принцип

Пользовательские сущности остаются штатными:

- документы, задачи, бизнес-процессы, файлы, права, история и уведомления — объекты Документооборота;
- расширение хранит только ИИ-специфичный контекст: оркестрацию, плейсхолдеры, ожидание ответов, аудит промптов и параметры моделей.

Новые объекты `АИС_*` не должны дублировать существующие справочники, документы или задачи.

## 5. Базовая задача и ИИ-контекст

Пользовательская задача — всегда `Задача.ЗадачаИсполнителя`. В ней хранятся:

- автор, исполнитель, роль исполнителя;
- срок и дата исполнения;
- предмет и описание;
- результат выполнения;
- состояние бизнес-процесса;
- права, история, уведомления.

`АИС_КонтекстЗадачИИ` — регистр с измерением `Задача` (`TaskRef.ЗадачаИсполнителя`) и ресурсами:

| Ресурс | Назначение |
|---|---|
| `ТипТриггера` | что запустило сценарий |
| `ТипДействия` | что должен сделать ИИ |
| `СостояниеИИ` | состояние ИИ-оркестрации |
| `Шаблон` | выбранный шаблон документа |
| `ПроектДокумента` | созданный проект `ИсходящиеДокументы` |
| `ТекстПроекта` | сгенерированный текст |
| `КандидатыШаблонов` | JSON-массив кандидатов, найденных расширением при создании адресной задачи; исполнитель оценивает их сам |
| `КлючИдемпотентности` | защита от повторного запуска |
| `Версия` | оптимистическая блокировка |
| `ГлубинаРазрешения` | глубина рекурсии плейсхолдеров |
| `ЧислоЗапросов` | число внешних запросов |
| `РучноеВмешательство` | признак ручного вмешательства |
| `ПризнакЭскалации` | признак эскалации |
| `РодительскаяЗадача` | ссылка на базовую родительскую задачу |
| `Источник` | строковый идентификатор источника/события |
| `ДатаСоздания`, `ДатаОбновления` | служебные даты |

В регистре **нет** `ДЛ`, `Должность`, `НормативныйСрок`, `ФактическоеЗавершение` и `Результат`: эти данные уже есть в базовой задаче.

Состояния:

- состояние пользовательской задачи — штатное состояние `Задача.ЗадачаИсполнителя`;
- состояние ИИ — `АИС_КонтекстЗадачИИ.СостояниеИИ`;
- переходы ИИ не меняют состояние задачи без явного действия пользователя.

## 6. Плейсхолдеры и шаблоны

- Плейсхолдеры хранятся в ТЧ `АИС_Плейсхолдеры` штатных справочников шаблонов.
- Состояние каждого плейсхолдера — `АИС_СостоянияПлейсхолдеров`.
- `АИС_ВидыПлейсхолдеров` содержит `Значение`, `Список`, `Раздел`.
- `АИС_СпособыЗаполнения` содержит `РешениеДЛ` — управленческое решение, а не запрос факта.
- Значение `Вид = Список` хранится JSON-массивом строк в `АИС_СостоянияПлейсхолдеров.Значение`; порядок элементов задаёт порядок в документе.
- Значение `Вид = Раздел` хранится ссылкой `АИС_СостоянияПлейсхолдеров.СсылкаНаРаздел`, а не строкой.
- Текст шаблона — в штатном `ШаблоныТекстов` или в штатном шаблоне документа.
- Параметры модели и JSON-схема — в `АИС_ПромптПараметры`.
- Дублировать текст шаблона в отдельном справочнике промптов не нужно.

Если структура штатных шаблонов не позволяет хранить плейсхолдеры, допускается `АИС_ШаблоныДокументов` только для ИИ-специфичных шаблонов, но не как замену штатных.

## 7. Триггеры

Приоритет:

1. `ВидыБизнесСобытий` + `ДетекторыБизнесСобытий` — если покрывают событие.
2. `АИС_ТипыТриггеров` — только для того, что не выражается бизнес-событиями.

Триггеры не создают отдельные документы. Они создают базовую задачу и запись `АИС_КонтекстЗадачИИ`.

Текущая реализация для адресного внутреннего документа (приказ, распоряжение, заявка) использует подписку `АИС_ВнутреннийДокументПриЗаписи` и тип триггера `ВнутреннийДокументАдресованДЛ`; адресату создаётся задача `Ознакомиться: ...`, а в `АИС_КонтекстЗадачИИ` сохраняются тип действия и кандидаты шаблонов. Это упрощённый путь симулятора, а не замена целевой модели бизнес-событий.

## 8. Ожидание ответа и эскалация

- Запрос к ДЛ — базовая `Задача.ЗадачаИсполнителя`.
- Метаданные ожидания (ID запроса, адресат, срок, ответ) — `АИС_ЛистОжидания`.
- Ответ заполняет результат базовой задачи и историю.
- Эскалация создаёт `ВнутреннийДокумент` с видом «Доклад о срыве сроков» и меняет `СостояниеИИ`.
- `АИС_ИсторияДействийИИ` хранит только ИИ-аудит: промпт, ответ, модель, токены, стоимость, ошибки.

## 9. Сроки

- Срок пользовательской задачи — `Задача.ЗадачаИсполнителя.СрокИсполнения`/`ДатаИсполнения`.
- Сроки процессов — штатные шаблоны процессов и `СрокиИсполненияПроцессов`.
- `АИС_НормативыИИ` — только нормативное время ИИ-ответа (например, сколько ждать RAG/LLM/внешний ответ), не дублирует сроки задач.

## 10. Доступ

- Пользовательские задачи защищаются штатной моделью прав `Задача.ЗадачаИсполнителя`.
- RLS на `АИС_КонтекстЗадачИИ`, `АИС_ЛистОжидания`, `АИС_СостоянияПлейсхолдеров` выполняется через ссылку на базовую задачу.
- Администратор не видит содержание задач.
- Аудитор читает `АИС_ИсторияДействийИИ` без права изменения.
- `HTTPService.АИС_Симулятор` аутентифицирует реального пользователя по Basic Auth, но отдельной проверки прав на операции найма/создания документов в v1 нет — известное упрощение (`plans/2026-10-26-enterprise-simulator.md`).
- Полную оргструктуру и персональную подчиненность видят `Администратор`/`АИС_АдминистраторСистемы`, `ГенДиректор`, `ГлавныйИнженер`, `ГлавныйБухгалтер`, `ДиректорПоПерсоналу` и `Программист1С`. Базовая роль `БазовыеПраваДокументооборот` даёт `Read`/`View` на `Справочник.СтруктураПредприятия`, `РегистрСведений.ПодчиненностьСотрудников`, `Справочник.Пользователи` и `Справочник.Должности`; `АИС_Сотрудники.СоздатьСотрудника` назначает её каждому пользователю. Дополнительно эти же права явно добавлены ролям `АИС_АдминистраторСистемы` и `АИС_ВышестоящееДолжностноеЛицо`.
- Прямой UI — `DataProcessor.АИС_Оргструктура` («АИС: Сервис» → «Структура предприятия и подчиненность»): дерево подразделений с руководителями и дерево персональной подчиненности. Роли `АИС_АдминистраторСистемы` и `АИС_ВышестоящееДолжностноеЛицо` имеют на неё `Use`/`View`.
- Прямой UI шаблонов — в `АИС: Сервис` добавлена обработка `АИС_Шаблоны` с единым списком шаблонов внутренних, входящих и исходящих документов, колонкой текста, полями «Статус шаблона»/«Текст шаблона» и кнопкой «Сохранить». `АИС_АдминистраторСистемы` (администратор и `Программист1С`) имеет на все три справочника `Read/View/InputByString/Insert/Update/Edit/InteractiveInsert` и права пометки удаления; остальные должностные лица редактировать шаблоны не могут.
- Шаблон: `Черновик` → техническое согласование `Программист1С` (`Согласован`) → окончательное утверждение автора исходного документа (`Утверждён`). В поиск шаблонов попадает только `Утверждён`.
- Подразделения в `Справочник.СтруктураПредприятия` создаёт и изменяет предопределённая должность `Программист1С` по распоряжению Гендиректора; симулятор сам подразделения не создаёт.
- Симулятор не содержит UI, отчётов и рисования оргструктуры: он только читает сведения из 1С, принимает решения и выполняет действия от имени сотрудников.

## 11. Что изменилось относительно первой модели

- `АИС_ЗадачиРеакции` переименован в `АИС_КонтекстЗадачИИ` и больше не хранит поля базовой задачи.
- Удалены новые документы запроса/ответа/доклада: используются базовая задача и `ВнутреннийДокумент`.
- Удалены `АИС_КаналыСвязи` и `АИС_ИсточникиДанных`: используются штатные классификаторы.
- `АИС_ПромптШаблоны` заменён на `АИС_ПромптПараметры` + `ШаблоныТекстов`.
- `АИС_РасписаниеТаймеров` заменён на `АИС_РасписаниеТриггеров` + регламентное задание.
- `АИС_НормативныеСроки` заменён на `АИС_НормативыИИ` с явным разделением сроков задачи и ИИ.

## 12. Принятые решения

Проектирование завершено; полный список — `docs/design-decisions.md`.

- Триггеры: штатные `ВидыБизнесСобытий`/`ДетекторыБизнесСобытий`, `АИС_ТипыТриггеров` — для ИИ-специфичных событий.
- Промпты: текст в `ШаблоныТекстов`, параметры в `АИС_ПромптПараметры`.
- Доклад о срыве: `ВнутреннийДокумент` + вид, без отдельного документа.
- Запрос к ДЛ: базовая задача + `АИС_ЛистОжидания`.
- Раздел: содержимое в `Файлы`/`ВерсииФайлов`, `АИС_РазделыДокумента` хранит ссылку, версию, хеш и подтверждение; текст не дублируется.
- Симулятор предприятия (2026-10-26): отдельный репозиторий работает через `HTTPService.АИС_Симулятор`; действия атрибутируются реальным пользователям, а не сервисному токену.
- Адресный внутренний документ (2026-10-26): подписка создаёт задачу адресату и сохраняет кандидатов шаблонов; поиск шаблона выполняется на стороне расширения.
- Автошаблонизация (2026-10-26): документ без шаблона или с дополнениями становится черновиком шаблона, автор получает задачу на утверждение; формирование выполняет `АИС_ОбщегоНазначения.ВызватьИИ`.
- Кадровый контур (2026-10-26): `Заявка на найм` + `АИС_ЗапрашиваемыеДолжности`; Главный бухгалтер согласует вилку, должностные инструкции запрашиваются у автора заявки, только затем задача уходит HR.

## 13. Разделы документа как специализированные плейсхолдеры

Раздел — не отдельный документ и не обычное скалярное значение. Это плейсхолдер с богатым значением: структурированный блок документа без «шапки» и части реквизитов.

### 13.1. Два уровня

- **Раздел шаблона** — описание в ТЧ `АИС_Плейсхолдеры` штатного шаблона: имя, заголовок, порядок, обязательность, формат, требуется ли подтверждение.
- **Раздел документа** — экземпляр в `АИС_РазделыДокумента`: содержимое, файл/версия, ответственный, задача, статус и подтверждение.

### 13.2. Поля

`АИС_СостоянияПлейсхолдеров`:

- `ВидПлейсхолдера`: `Значение` / `Список` / `Раздел` (перечисление `АИС_ВидыПлейсхолдеров`);
- `СсылкаНаРаздел` — `CatalogRef.АИС_РазделыДокумента` (справочник, не регистр — у регистра сведений нет ссылочного типа);
- для `Список` значение — JSON-массив строк в `Значение`, порядок элементов задаёт порядок в документе;
- `Источник` в регистре — фактический способ заполнения (`EnumRef.АИС_СпособыЗаполнения`), не путать с `ИсточникДанных` в ТЧ шаблона;
- остальные поля — состояние, запрос, значение, ошибка.

`АИС_РазделыДокумента` — справочник, не регистр: каждая версия раздела — отдельный элемент, `Устарел` остаётся в базе как история.

| Поле | Тип | Назначение |
|---|---|---|
| `Владелец` | `CatalogRef.ИсходящиеДокументы` | документ-владелец (штатный механизм подчинённого справочника) |
| `Раздел` | `String` | код/имя раздела |
| `Заголовок` | `String` | заголовок раздела |
| `Порядок` | `Number` | порядок в документе |
| `Обязательный` | `Boolean` | обязательность раздела |
| `Формат` | `String` | текст, HTML, DOCX, смешанный |
| `Источник` | `String` | `ЗапросКДЛ`, `ГотовыйФайл`, `RAGКандидат` |
| `Файл` | `CatalogRef.Файлы` | файл раздела |
| `Версия` | `String` | версия файла |
| `Хеш` | `String` | хеш содержимого для подтверждения |
| `Ответственный` | `CatalogRef.Пользователи` | кто отвечает за раздел |
| `Задача` | `TaskRef.ЗадачаИсполнителя` | штатная задача на раздел |
| `Статус` | `EnumRef.АИС_СостоянияРазделов` | состояние раздела |
| `Подтвердил` | `CatalogRef.Пользователи` | кто подтвердил |
| `ДатаПодтверждения` | `Date` | когда подтвердил |
| `Комментарий` | `String` | примечание |

`АИС_ЛистОжидания` — справочник (не регистр: измерение было бы искусственным `Запрос`, а ссылаться на конкретный запрос нужно извне, из `АИС_СостоянияПлейсхолдеров.ЗапросОжидания`):

- `ТипЗапроса` — перечисление `АИС_ТипыЗапросовЛистаОжидания` (`Значение` / `ПодтверждениеРаздела`);
- `ОжидаемаяВерсия`, `ОжидаемыйХеш`;
- `СсылкаНаРаздел` (`CatalogRef.АИС_РазделыДокумента`);
- `ТипИсточника` — перечисление `АИС_ТипыИсточниковОжидания` (`ДЛ` / `ВнешнийСервис`);
- `Состояние` — перечисление `АИС_СостоянияЗапросовОжидания` (`Отправлен`, `ПолученОтвет`, `СрокИстек`);
- `Адресат` (`DefinedType.АИС_АдресатЗапроса`);
- остальные поля — как для обычного запроса.

### 13.3. Статусы раздела

`АИС_СостоянияРазделов`:

- `НеНачат`;
- `Черновик`;
- `НаПодтверждении`;
- `Подтвержден`;
- `Устарел`;
- `Отклонен`.

Правила:

- `Подтвержден` действителен только для конкретной версии и хеша.
- Изменение файла или версии переводит раздел в `Устарел`.
- `Отклонен` требует новой версии или нового ответа ДЛ.
- ИИ не может выставить `Подтвержден`.

### 13.4. Подтверждение

Даже готовый файл из хранилища не используется автоматически. Создаётся запрос на подтверждение конкретной версии:

1. Найти кандидат (файл, прошлый раздел, RAG-фрагмент).
2. Создать `АИС_ЛистОжидания` с `ТипЗапроса = ПодтверждениеРаздела`.
3. Создать штатную задачу ответственному ДЛ.
4. ДЛ подтверждает или отклоняет версию/хеш.
5. Результат фиксируется в задаче, `ИсторияСобытийЗадач` и `АИС_ИсторияДействийИИ`.
6. При подтверждении раздел становится `Подтвержден`, при изменении файла — `Устарел`.

Если готового файла нет, источник — `ЗапросКДЛ`: ДЛ готовит раздел, прикладывает файл или текст, после чего подтверждает версию.

### 13.5. Сборка документа

- Шаблон содержит маркеры разделов и их порядок.
- Сборка детерминированная: проверить обязательные разделы, порядок, версии и подтверждения.
- LLM может подготовить черновик раздела, но не выполняет финальную вёрстку и не подтверждает содержимое.
- Если подтверждённая версия изменилась, сборка блокируется до повторного подтверждения.

### 13.6. Что создаётся в расширении

Создано (проверено сборкой через EDT CLI в этой сессии):

- перечисления `АИС_СостоянияРазделов`, `АИС_ВидыПлейсхолдеров`, `АИС_СтатусыПлейсхолдеров`, `АИС_ТипыЗапросовЛистаОжидания`, `АИС_ТипыИсточниковОжидания`, `АИС_СостоянияЗапросовОжидания`;
- справочники `АИС_РазделыДокумента` (подчинён `ИсходящиеДокументы`), `АИС_ЛистОжидания`;
- регистр `АИС_СостоянияПлейсхолдеров` с полями `ВидПлейсхолдера`, `СсылкаНаРаздел`, `Состояние`, `ЗапросОжидания` (`CatalogRef.АИС_ЛистОжидания`).

Все три объекта, которые в исходной спецификации были регистрами (`АИС_РазделыДокумента`, `АИС_ЛистОжидания`, а также `АИС_РасписаниеТриггеров` в §4.3.4), стали справочниками: регистр сведений не производит ссылочный тип (`refType`), а на запись в каждом из них нужно ссылаться из других объектов.

Штатные `ИсходящиеДокументы`, `Задача.ЗадачаИсполнителя`, `Файлы`, `ВерсииФайлов`, `РабочиеГруппы` и `ВизыСогласования` остаются основой; разделы не превращаются в отдельные документы.

## 14. Мастер шаблонов

Подробное описание — в `docs/template-factory.md`. Модель мастера:

- штатные `ШаблоныВходящих/Исходящих/ВнутреннихДокументов`, `Файлы`, `ВерсииФайлов`, `ПравилаАвтозаполненияФайлов`;
- ТЧ `АИС_Плейсхолдеры` в трёх справочниках шаблонов — канонический состав полей в §14.1;
- `АИС_СтатусыШаблонов` — измерение `Шаблон`; ресурсы `Версия`, `Статус`, `Автор`, `Дата`, `Комментарий`, `РезультатАнализа`, `Ошибки`, `ДатаИндексации`;
- `АИС_СравненияШаблонов` — `ИсходныйШаблон`, `ЦелевойШаблон`, `Версия`, `ОценкаСходства`, `ТекстоваяОценка`, `ОценкаПлейсхолдеров`, `ОценкаСтруктуры`, `ОценкаМетаданных`, `РазличияJSON`, `Рекомендация`, `Решение`, `Пользователь`, `Дата`, `Комментарий`;
- `АИС_СостоянияШаблонов` — `Черновик`, `НаПроверке`, `Утвержден`, `Устарел`, `Отклонен`;
- `АИС_РекомендацииПоШаблонам` — `ОбновитьСуществующий`, `Объединить`, `СоздатьНовый`, `РучноеРешение`.

### 14.1. Канонический состав ТЧ `АИС_Плейсхолдеры`

Единый источник истины по составу ТЧ. `plans/implementation_plan.md` §5.3 и `docs/template-factory.md` §7 ссылаются на этот раздел и не дублируют поля.

| Поле | Назначение | Обязательность |
|---|---|---|
| `Имя` | имя плейсхолдера, совпадает с `{{...}}`; уникально в шаблоне | да |
| `Описание` | семантика данных для мастера и интерфейса | нет |
| `Вид` | `Значение`, `Список`, `Раздел` | да |
| `ТипДанных` | строка, число, дата, ссылка; для `Список` — тип элемента | да |
| `Обязательность` | требуется ли значение | да |
| `ИсточникДанных` | `CatalogRef.ИсточникиДанных`: где брать значение | для источников, кроме `РучнойВвод` и `РешениеДЛ` |
| `СпособЗаполнения` | `EnumRef.АИС_СпособыЗаполнения`, включая `РешениеДЛ` | да |
| `ПравилоАвтозаполнения` | ссылка на базовое `ПравилаАвтозаполненияФайлов` | нет |
| `ШаблонЗапроса` | утверждённый запрос для `ЗапросВБД` | для `ЗапросВБД` |
| `ПараметрыИсточникаJSON` | параметры конкретного источника | нет |
| `Падеж` | падеж для ФИО или должности | нет |
| `ЭтоФИО` | значение является ФИО | нет |
| `Пол` | пол для согласования | нет |
| `Порядок` | порядок в документе | для `Раздел` |
| `Формат` | текст, HTML, DOCX, смешанный | для `Раздел` |
| `Маркер` | точный маркер в тексте шаблона | да |
| `Заголовок` | заголовок раздела | для `Раздел` |
| `ТребуетПодтверждения` | требуется подтверждение версии и хеша | для `Раздел` |
| `Статус` | статус разметки в мастере (принят, отклонён, требует проверки); не путать с runtime-статусом `АИС_СтатусыПлейсхолдеров` | да |

Состав реализован в трёх штатных справочниках шаблонов в Этапе B1.

Правила хранения значений:

- `Вид = Значение` — скаляр в `АИС_СостоянияПлейсхолдеров.Значение`.
- `Вид = Список` — JSON-массив строк в `АИС_СостоянияПлейсхолдеров.Значение`; порядок элементов задаёт порядок в документе.
- `Вид = Раздел` — ссылка `АИС_СостоянияПлейсхолдеров.СсылкаНаРаздел`; содержимое, версия и хеш — в `АИС_РазделыДокумента`.

`ПравилоАвтозаполнения` и `ШаблонЗапроса` — разные поля: первое ссылается на базовое правило подстановки, второе — на утверждённый запрос с параметрами. `ИсточникДанных` и `СпособЗаполнения` тоже разные: первое отвечает «откуда», второе — «как».

Мастер анализирует DOCX/текст, предлагает плейсхолдеры, списки и разделы, генерирует базовые правила автозаполнения, проводит тестовое заполнение, а публикация и индексация выполняются только после подтверждения человеком. Пользователь может принять или отклонить каждый плейсхолдер, добавить/удалить его и изменить параметры. Перед созданием нового шаблона мастер сравнивает кандидата с существующими и предлагает обновить, объединить или создать новый; решение принимает пользователь.

## 15. Вычитка документов

Двухуровневая проверка проекта документа. Подробности — `docs/proofreading.md`.

- **Быстрая** — без LLM: плейсхолдеры, обязательные разделы, даты, суммы, номера, ссылки, формат, повторы, склонения.
- **Глубокая** — LLM: орфография, пунктуация, грамматика, стиль, смысл, логика, противоречия.

`АИС_ПроверкиДокументов`:

- документ, версия/хеш;
- режим, статус;
- страницы, токены, модель;
- дата начала/окончания, сводка, ошибка.

`АИС_ЗамечанияПроверки`:

- проверка, номер;
- тип и важность;
- цитата, позиция;
- сообщение, предложение;
- уверенность;
- решение пользователя, дата.

`АИС_ЛимитыВычитки`:

- пользователь, период;
- лимит и использование страниц;
- лимит и использование токенов;
- дата сброса, активность.

Правила:

- пользователь видит страницы, не токены;
- быстрая проверка не расходует квоту;
- глубокая проверка блокируется при исчерпании квоты;
- цитата замечания обязана существовать в тексте;
- замечания не применяются автоматически;
- принятые замечания применяются детерминированно и аудируются;
- локальная LLM предпочтительна для конфиденциальных документов.
