# Критический обзор документации

Дата: 2026-10-23. Обзор выполнен по полному корпусу документации (`README.md`, `docs/raw_specification.md`, `docs/implementation_plan.md`, `docs/data-model.md`, `docs/design-decisions.md`, `docs/process-diagrams.md`, `docs/template-factory.md`, `docs/proofreading.md`, `docs/requirements/*`) и по фактическому состоянию кода (`src/`, `rag-service/`).

Цель — зафиксировать замечания по пяти осям: дублирование штатного функционала 1С:Документооборот, недостающие звенья в проектировании, реализуемость с учётом ограничений наивного RAG, сложность де-факто мультиагентной архитектуры, и отсутствие модели для управленческих решений/экспертного мнения как категории плейсхолдера. Документ не блокирует реализацию; решения по пунктам фиксируются либо здесь (статус `закрыт`), либо переносятся в `docs/design-decisions.md`.

Проект методологически дисциплинирован: есть отдельный документ про дедупликацию (`data-model.md`), явная таблица «что не создаётся» и причины. Это снижает число находок по первой оси, но не снимает их полностью.

## 2. Недостающие звенья

| № | Замечание | Статус |
|---|---|---|
| 2.1 | **Асимметрия управления стоимостью.** Для вычитки продумана подробная система квот (`АИС_ЛимитыВычитки`). Для основного пайплайна нет ни квот, ни бюджета, ни алертов. Решение: отдельная квота на основной пайплайн, поведение при превышении. См. `docs/design-decisions.md` §15. | закрыт |
| 2.2 | **Утечка данных во внешний LLM недооценена для MVP-пути.** Решение: требование «локальная LLM или политика организации» распространено на весь пайплайн, не только вычитку; критично перед пилотом на реальных документах. См. `docs/design-decisions.md` §16. | закрыт |
| 2.3 | **`АИС_ИсторияДействийИИ` хранит полный промпт и ответ LLM бессрочно.** Решение: срок хранения — не менее срока хранения связанной задачи, доступ ограничен ролью `АИС_Аудитор`, автомаскирование в MVP не делается (технически ненадёжно для свободного текста) — зафиксировано как явное допущение. См. `docs/design-decisions.md` §16. | закрыт |
| 2.4 | **Норматив ИИ (`АИС_НормативыИИ`) не имеет последствия.** Решение: превышение пишет событие в аудит + отражается в `АИС_СтатистикаЗадач`, не создаёт автоэскалацию (эскалация остаётся по штатному `СрокИсполнения`). См. `docs/design-decisions.md` §14. | закрыт |
| 2.5 | **Нет memoization в рекурсивном разрешении плейсхолдеров.** Решение: кэш «подпись параметров → значение» на время жизни задачи, до построения полного графа зависимостей (после MVP). Решение принято, реализация — Этап 8. См. `docs/design-decisions.md` §18, `docs/remediation-plan.md`. | закрыт |
| 2.6 | **Гонка между публикацией шаблона и переиндексацией RAG.** Решение: публикация вызывает `upsert` в RAG синхронно, регламентная индексация остаётся догоняющей. См. `docs/design-decisions.md` §18. | закрыт |
| 2.7 | **Нет общего рейт-лимитера/приоритизации между подсистемами.** Решение: общий компонент (`АИС_ОчередьЗапросовLLM`), приоритет — оркестратор > мастер шаблонов > вычитка, единый backoff. Реализация — Этап 4. См. `docs/design-decisions.md` §15. | закрыт |
| 2.8 | **Разрыв между объёмом документации и фактическим кодом.** Полностью реализован RAG-микросервис; в `src/` 1С-расширения создана и собрана (EDT CLI) бо́льшая часть метаданных Этапа 2 (8 перечислений, 3 определяемых типа, 7 справочников, 4 регистра — см. `docs/stage2-plan.md`), но оркестратора, разрешителя плейсхолдеров, интеграции с LLM, ролей (кроме заглушки), RLS, демоданных и UI в BSL пока нет. Основной объём риска проекта — в бизнес-логике, которую документация только специфицирует. README обновлён честно (`docs/remediation-plan.md`, Волна 4). | информационно |
| 2.10 | **Периодическое обязательство из распоряжения могло быть молча потеряно.** Решение: промпт `ОпределениеПериодичностиРаспоряжения` анализирует текст на признаки периодичности при регистрации; если обнаружены — создание записи `АИС_РасписаниеТриггеров` становится обязательным условием закрытия задачи по распоряжению, а не просто подсказкой. ## 3. Реализуемость с учётом ограничений наивного RAG

Сильная сторона: область применения RAG сознательно сужена (`implementation_plan.md#2.1` — «почему не RAG для всех значений»), RAG держится в стороне от точных транзакционных значений. Это снимает самый опасный класс ошибок наивного RAG (галлюцинации в данных документа).

| № | Замечание | Статус |
|---|---|---|
| 3.1 | **Self-reported confidence LLM используется как жёсткий гейт.** Решение: порог не задаётся произвольно — калибровочный прогон `tools/llm_eval` сравнивает заявленный confidence с фактической корректностью, порог подбирается по результату, повторяется при обновлении модели. См. `docs/design-decisions.md` §15. | закрыт |
| 3.2 | **Чанкинг не учитывает структуру текста.** Решение: переход на чанкинг по структурным границам (абзац/пункт), overlap только на границе чанка. Доработка RAG-сервиса после Этапа 3, не блокирует MVP. См. `docs/design-decisions.md` §18. | закрыт |
| 3.3 | **Нет гибридного поиска (dense + keyword/BM25) и reranker.** Решение: обязательная предпосылка перед включением FR-040/FR-041, не требуется для MVP. См. `docs/design-decisions.md` §18. | закрыт |
| 3.4 | **Нет постоянного контроля деградации качества поиска.** Решение: регулярный (не в CI) прогон `tools/llm_eval` на golden-наборе на Этапе 7. См. `docs/design-decisions.md` §18. | закрыт |
| 3.5 | **Критерий «выбор шаблона ≥90% на 50 сценариях» статистически слаб для масштаба.** Принято как явное пилотное допущение, подлежит пересмотру при росте корпуса. См. `docs/design-decisions.md` §13. | закрыт |
| 3.6 | FR-040/FR-041 требуют retrieval-качества выше наивной схемы. Решение: явно обусловлены предварительной реализацией 3.3. См. `docs/design-decisions.md` §13. | закрыт |

## 4. Сложность де-факто мультиагентной архитектуры

Термин «мультиагент» в документации не встречается, но система — это не менее 7 различных LLM-«ролей» со своими промптами и JSON-схемами (выбор шаблона, формирование поискового запроса, классификация источника, генерация текста, анализ срыва сроков, плюс 4–5 ролей в мастере шаблонов, плюс LLM-рецензент в вычитке), оркестрируемых одним детерминированным координатором. Паттерн «orchestrator + stateless workers» вместо автономных агентов с переговорами — правильное решение, оно снижает классические риски мультиагентных систем (эмерджентность, договорённости между агентами). Часть сложности остаётся:

| № | Замечание | Статус |
|---|---|---|
| 4.1 | **Компаундирование ошибок по цепочке** не промоделировано. Решение: составная метрика «доля документов, собранных полностью без ручного вмешательства» добавлена в критерии приёмки Этапа 7, измеряется эмпирически. См. `docs/design-decisions.md` §13. | закрыт |
| 4.2 | **Рефлексивная хрупкость эскалации.** Модуль анализа срыва сроков сам вызывает LLM, даже когда причиной срыва мог быть сбой того же провайдера ранее в цепочке; fallback есть, но это второй слой отказоустойчивости поверх первого. | информационно |
| 4.3 | **Состояние задачи размазано по двум параллельным машинам состояний.** Решение: формальная таблица допустимых переходов (состояние × инициатор) и обязательные тестовые сценарии конкуренции добавлены в `implementation_plan.md` §6.1. | закрыт |
| 4.4 | **Регрессионное тестирование промптов не встроено в CI.** Решение: тот же регулярный прогон `tools/llm_eval` на Этапе 7 (см. 3.4). См. `docs/design-decisions.md` §18. | закрыт |
| 4.5 | **Ресурсный конфликт между подсистемами** — см. 2.7, то же решение (`АИС_ОчередьЗапросовLLM`). См. `docs/design-decisions.md` §15. | закрыт |
| 4.6 | **Трудоёмкость.** Спроектировано около десятка специализированных LLM-ролей, каждая требует eval-набора, версионирования промпта, валидатора JSON-схемы и fallback-логики — а в коде сейчас нет ни одной (см. 2.8). Объём работы по реализации ядра оркестрации заметно больше, чем предполагает текущий раздел «Статус» в `README.md`. | информационно |

## 5. Управленческие решения и экспертное мнение как плейсхолдер

Все способы заполнения плейсхолдера (`АИС_СпособыЗаполнения`: `ПрямоеПоле`, `ЗапросВБД`, `ЗапросКДЛ`, `РасчетныйСервис`, `ВнешнийAPI`, `RAGКонтекст`, `РучнойВвод` — уже создано в коде, `src/Enums/АИС_СпособыЗаполнения`) смоделированы как способы *получить известное значение*, а не как акт *принятия решения экспертом*. Для плейсхолдеров, которые должны содержать управленческое решение, формулировку резолюции, оценку ситуации или творческую формулировку, это существенный пробел, а не просто недостающий канал ввода.

| № | Замечание | Статус |
|---|---|---|
| 5.1 | **Терминология закрепляет рамку «ДЛ = источник данных».** Решение: новая категория `РешениеДЛ` в `АИС_СпособыЗаполнения`, явно отличная от «запроса факта»; глоссарий (`docs/glossary.md`) разделяет «ДЛ как держатель сведений» и «ДЛ как лицо, принимающее решение». См. `docs/design-decisions.md` §17. | закрыт |
| 5.2 | **`ЗапросКДЛ` и `РучнойВвод` не имеют собственной модели взаимодействия для решений.** Решение: для `РешениеДЛ` — показ прецедентов (RAG top-k по похожим прошлым решениям) без автозаполнения, фиксация рассмотренных и отклонённых вариантов в комментарии. См. `docs/design-decisions.md` §17. | закрыт |
| 5.3 | **Решение попадает под тот же таймер и ту же эскалацию, что и запрос факта.** Решение: норматив/срок ожидания для `РешениеДЛ` настраивается отдельно от `ЗапросКДЛ`, истечение создаёт напоминание, а не доклад о срыве. См. `docs/design-decisions.md` §17. | закрыт |
| 5.4 | **Нет промежуточной формы между скаляром и разделом.** Решение: короткое суждение для `РешениеДЛ` хранится как обычное строковое значение плейсхолдера в MVP, полноценный `Раздел` — только для действительно развёрнутого решения. См. `docs/design-decisions.md` §17. | закрыт |
| 5.5 | **Нет голосового/диалогового канала и опоры на прецеденты.** Решение: голосовой ввод — явный backlog (не упущение), канал остаётся текстовым; прецеденты — через RAG top-k для `РешениеДЛ` (см. 5.2). См. `docs/design-decisions.md` §17. | закрыт |

## 6. Как использовать этот документ

- Пункты со статусом `открыт` — кандидаты на решение перед/во время реализации соответствующего этапа; закрытые решения переносятся в `docs/design-decisions.md` по той же схеме, что и остальные проектные решения.
- Пункты `информационно` не требуют решения, но важны для ожиданий по срокам и бюджету.
- Документ не входит в источник истины требований (`docs/requirements/requirements.yaml`); при принятии решения по пункту он либо становится новым FR/NFR со статусом `proposed`, либо фиксируется как явное допущение в `docs/design-decisions.md`.
