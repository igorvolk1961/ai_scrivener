# Критический обзор документации

Дата: 2026-10-23. Обзор выполнен по полному корпусу документации (`README.md`, `docs/raw_specification.md`, `docs/implementation_plan.md`, `docs/data-model.md`, `docs/design-decisions.md`, `docs/process-diagrams.md`, `docs/template-factory.md`, `docs/proofreading.md`, `docs/requirements/*`) и по фактическому состоянию кода (`src/`, `rag-service/`).

Цель — зафиксировать замечания по пяти осям: дублирование штатного функционала 1С:Документооборот, недостающие звенья в проектировании, реализуемость с учётом ограничений наивного RAG, сложность де-факто мультиагентной архитектуры, и отсутствие модели для управленческих решений/экспертного мнения как категории плейсхолдера. Документ не блокирует реализацию; решения по пунктам фиксируются либо здесь (статус `закрыт`), либо переносятся в `docs/design-decisions.md`.

Проект методологически дисциплинирован: есть отдельный документ про дедупликацию (`data-model.md`), явная таблица «что не создаётся» и причины. Это снижает число находок по первой оси, но не снимает их полностью.

## 1. Дублирование функционала 1С:Документооборот

| № | Замечание | Статус |
|---|---|---|
| 1.1 | **Возможный пропуск — подсистема контроля исполнения.** У 1С:Документооборот ПРОФ есть штатный механизм контроля сроков поручений/задач с контролёром, напоминаниями и просрочками. Ни в `data-model.md`, ни в `raw_specification.md` этот механизм не упомянут и не исключён явно. Проект реализует параллельную логику: `АИС_НормативыИИ` + `АИС_ПроверкаСроковЗадач` + эскалация с LLM-анализом причин. Нужно проверить по метаданным фактической базы, что штатный контроль не закрывает часть этой функции, и зафиксировать решение так же, как для остальных объектов. | открыт |
| 1.2 | **Подтверждено и устранено полностью.** В базовой конфигурации нет объекта «Замещения», но есть штатный периодический регистр `СведенияОПользователяхДокументооборот` (пользователь → должность/подразделение на дату) и `Catalogs.ДелегированиеПрав` (кто кого замещает на период). Их достаточно: `АИС_НазначенияДолжностей` как хранимый регистр отменён полностью, действующие должности ДЛ (постоянная + замещаемые) вычисляются функцией объединения, обязанности резолвятся по объединённому набору. См. `docs/design-decisions.md` §5, `docs/requirements/requirements.yaml` FR-001/FR-003. | закрыт |
| 1.3 | **Логическая натяжка «приоритет штатным триггерам».** Три из шести типов триггеров (`Таймер`, `ПоступлениеОтветНаЗапрос`, `ИстечениеСрокаОжидания`) — состояния, которые существуют только внутри расширения и не могут быть обнаружены штатным детектором бизнес-событий по построению. Формулировка «`АИС_ТипыТриггеров` — fallback, если штатное не покрывает» создаёт иллюзию, что переиспользование — основной путь, тогда как для половины типов `АИС_*`-классификатор обязателен. Не дублирование, но переоценка объёма переиспользования штатного механизма. | открыт |
| 1.4 | **Не подтверждено наличие `ВидыБизнесСобытий`/`ДетекторыБизнесСобытий` в редакции ПРОФ** в нужном объёме (в ряде редакций 1С:Документооборот эта подсистема шире представлена в КОРП). Весь принцип «переиспользования триггеров» держится на этом допущении, но оно не проверено и не в таблице рисков. | открыт |

## 2. Недостающие звенья

| № | Замечание | Статус |
|---|---|---|
| 2.1 | **Асимметрия управления стоимостью.** Для вычитки продумана подробная система квот (`АИС_ЛимитыВычитки`). Для основного пайплайна (выбор шаблона, классификация источника, формирование запроса, генерация, анализ срыва сроков — 5+ LLM-вызовов на задачу) нет ни квот, ни бюджета, ни алертов, только «стоимость считать и писать в аудит». При 100 активных задачах (NFR-011) это основной источник расходов на LLM, а не вычитка, но контроля над ним нет. | открыт |
| 2.2 | **Утечка данных во внешний LLM недооценена для MVP-пути.** В таблице рисков «утечка документов во внешнюю LLM» привязана только к вычитке и к индексации RAG («вне MVP»). Реальный входящий документ уже с Этапа 1 MVP уходит в DeepSeek (внешний облачный API) для генерации текста и классификации источников — это не отражено как риск того же уровня. | открыт |
| 2.3 | **`АИС_ИсторияДействийИИ` хранит полный промпт и ответ LLM бессрочно**, доступные аудитору на чтение. Если промпт включает содержание документа или персональные данные, это противоречит духу NFR-022 (логи без текстов документов) — ограничение там касается только логов сервиса, а не аудит-регистра 1С. Политика хранения/маскирования персональных данных в аудите не описана. | открыт |
| 2.4 | **Норматив ИИ (`АИС_НормативыИИ`) не имеет последствия.** Задано нормативное время ИИ-ответа, но не описано, что происходит при превышении (в отличие от срока пользовательской задачи, который ведёт к эскалации). | открыт |
| 2.5 | **Нет memoization в рекурсивном разрешении плейсхолдеров.** Общее под-значение, нужное двум плейсхолдерам через расчётный сервис, будет резолвиться дважды в MVP (построение графа зависимостей отложено на «после MVP»). Повышает риск упереться в лимит 50 запросов на задачу раньше, чем нужно. | открыт |
| 2.6 | **Гонка между публикацией шаблона и переиндексацией RAG.** Индексация — по регламенту каждые 5 минут. Задача, попавшая в `ПоискШаблона` сразу после публикации/обновления шаблона, может не увидеть его в top-k ещё 5 минут. Сценарий не покрыт критериями приёмки. | открыт |
| 2.7 | **Нет общего рейт-лимитера/приоритизации между подсистемами.** Оркестратор, мастер шаблонов и вычитка независимо дёргают DeepSeek/GigaChat/локальную LLM со своими retry/backoff. При одновременной нагрузке возможен одновременный всплеск ретраев на лимит одного провайдера. В таблице рисков это помечено как мера («очередь, приоритизация»), но компонента для этого в архитектуре нет. | открыт |
| 2.8 | **Разрыв между объёмом документации и фактическим кодом.** Полностью реализован только RAG-микросервис. В `src/` 1С-расширения — только скелет метаданных (2 регистра, 2 справочника, 3 перечисления, роль); оркестратора, разрешителя плейсхолдеров, интеграции с LLM и UI в BSL пока нет. Основной объём риска проекта — в коде, который документация только специфицирует. | информационно |
| 2.10 | **Периодическое обязательство из распоряжения может быть молча потеряно.** Начальник может устным или письменным распоряжением установить требование, привязанное к таймеру (например, «присылай отчёт каждый понедельник»). Технически это требование вступает в силу только через отдельную фиксацию — создание записи `АИС_РасписаниеТриггеров` со ссылкой на распоряжение (`raw_specification.md` §4.1.4, §4.3.4). Но ничто в системе не проверяет, что такая фиксация действительно произошла: нет разбора текста распоряжения на предмет периодичности, нет напоминания исполнителю или администратору, нет отчёта о распоряжениях без связанного расписания. Если фиксация не выполнена, обязательство не присоединяется к обязанностям ДЛ (п. 5) и никогда не превращается в триггер — при этом ни начальник, ни исполнитель не получают сигнала о расхождении между тем, что было поручено, и тем, что реально исполняется системой. | открыт |
| 2.9 | **Доклад о срыве сроков уходит без шага человеческой верификации — в отличие от всех остальных документов системы.** Обычный исходящий документ (`raw_specification.md` §4.10.1) проходит `Проект → НаСогласовании → Подписан → Отправлен` с обязательной проверкой ДЛ. Доклад о срыве сроков (`raw_specification.md` §4.7.1, подтверждено в `process-diagrams.md` §5.2) создаётся и **сразу** направляется вышестоящему ДЛ, копия исполнителю — постфактум, не как шаг согласования. Именно самый чувствительный документ — текст, приписывающий причину невыполнения задачи конкретному сотруднику и уходящий его начальнику, — единственный без человеческой проверки перед отправкой. При уже признанном риске галлюцинаций LLM и невалидного JSON это означает, что ошибочный ИИ-анализ «кто виноват» может достичь руководителя без возможности проверки. Нарушает паттерн human-in-the-loop, выдержанный везде в проекте, и создаёт организационно-кадровый/репутационный риск, не упомянутый в документации. | открыт |

## 3. Реализуемость с учётом ограничений наивного RAG

Сильная сторона: область применения RAG сознательно сужена (`implementation_plan.md#2.1` — «почему не RAG для всех значений»), RAG держится в стороне от точных транзакционных значений. Это снимает самый опасный класс ошибок наивного RAG (галлюцинации в данных документа).

| № | Замечание | Статус |
|---|---|---|
| 3.1 | **Self-reported confidence LLM используется как жёсткий гейт** при выборе шаблона. Известно, что калибровка уверенности у LLM слабая — число confidence не гарантированно коррелирует с фактической правильностью. Нет калибровочного датасета или проверки, что порог действительно фильтрует ошибки. | открыт |
| 3.2 | **Чанкинг не учитывает структуру текста** (фиксированные ~1000 символов + overlap 150, без учёта границ абзацев/пунктов/таблиц). Для юридических и канцелярских текстов на русском это регулярно режет смысловые единицы посередине. | открыт |
| 3.3 | **Нет гибридного поиска (dense + keyword/BM25) и reranker.** Домен насыщен точными идентификаторами (номера приказов, даты, ГОСТы) — чистый косинусный поиск систематически слабее на точных совпадениях. Пример из `proofreading.md` («Приказ № 15 относится к другому подразделению») иллюстрирует именно этот класс ошибки. | открыт |
| 3.4 | **Нет постоянного контроля деградации качества поиска.** `tools/llm_eval` не запускается в CI «по стоимости» — дрейф качества (рост числа шаблонов, смена моделей провайдерами) не будет замечен автоматически. | открыт |
| 3.5 | **Критерий «выбор шаблона ≥90% на 50 сценариях»** приемлем для пилота, но статистически слаб для долгосрочной гарантии и не масштабируется на корпус в сотни шаблонов, который прямо предполагает мастер шаблонов. | открыт |
| 3.6 | Запланированные FR-040 (извлечение значений из текста с цитатой) и FR-041 (ACL-индексация документов) требуют retrieval-качества выше того, что обеспечивает наивная схема без reranking/hybrid-search, а бюджета на это усиление в документации не заложено. | открыт |

## 4. Сложность де-факто мультиагентной архитектуры

Термин «мультиагент» в документации не встречается, но система — это не менее 7 различных LLM-«ролей» со своими промптами и JSON-схемами (выбор шаблона, формирование поискового запроса, классификация источника, генерация текста, анализ срыва сроков, плюс 4–5 ролей в мастере шаблонов, плюс LLM-рецензент в вычитке), оркестрируемых одним детерминированным координатором. Паттерн «orchestrator + stateless workers» вместо автономных агентов с переговорами — правильное решение, оно снижает классические риски мультиагентных систем (эмерджентность, договорённости между агентами). Часть сложности остаётся:

| № | Замечание | Статус |
|---|---|---|
| 4.1 | **Компаундирование ошибок по цепочке** не промоделировано. Документ с несколькими плейсхолдерами проходит выбор шаблона → N классификаций источника → N заполнений → генерация → (опц.) вычитка. Целевые метрики заданы по шагам (≥90%, ≥95%), но итоговая вероятность «весь документ собран правильно без ручного вмешательства» падает мультипликативно с числом шагов и нигде не оценена. | открыт |
| 4.2 | **Рефлексивная хрупкость эскалации.** Модуль анализа срыва сроков сам вызывает LLM, даже когда причиной срыва мог быть сбой того же провайдера ранее в цепочке; fallback есть, но это второй слой отказоустойчивости поверх первого. | информационно |
| 4.3 | **Состояние задачи размазано по двум параллельным машинам состояний** (штатный статус задачи + `СостояниеИИ`), синхронизируемым через версию и блокировки при конкурентной обработке регламентными заданиями разной периодичности (10 с / 1 мин) и внешними ответами в произвольный момент. Формальной таблицы допустимых переходов/матрицы тестов на неё нет, только прозаическое описание цепочки. | открыт |
| 4.4 | **Регрессионное тестирование промптов не встроено в CI** (дорого) — дрейф качества 7+ независимо версионируемых промптов при обновлении моделей провайдерами обнаруживается только вручную. | открыт |
| 4.5 | **Ресурсный конфликт между подсистемами** — см. 2.7, тоже проявление мультиагентной сложности: несколько логически независимых «агентных» пайплайнов конкурируют за один внешний ресурс без общего шедулера. | открыт |
| 4.6 | **Трудоёмкость.** Спроектировано около десятка специализированных LLM-ролей, каждая требует eval-набора, версионирования промпта, валидатора JSON-схемы и fallback-логики — а в коде сейчас нет ни одной (см. 2.8). Объём работы по реализации ядра оркестрации заметно больше, чем предполагает текущий раздел «Статус» в `README.md`. | информационно |

## 5. Управленческие решения и экспертное мнение как плейсхолдер

Все способы заполнения плейсхолдера (`АИС_СпособыЗаполнения`: `ПрямоеПоле`, `ЗапросВБД`, `ЗапросКДЛ`, `РасчетныйСервис`, `ВнешнийAPI`, `RAGКонтекст`, `РучнойВвод` — уже создано в коде, `src/Enums/АИС_СпособыЗаполнения`) смоделированы как способы *получить известное значение*, а не как акт *принятия решения экспертом*. Для плейсхолдеров, которые должны содержать управленческое решение, формулировку резолюции, оценку ситуации или творческую формулировку, это существенный пробел, а не просто недостающий канал ввода.

| № | Замечание | Статус |
|---|---|---|
| 5.1 | **Терминология закрепляет рамку «ДЛ = источник данных».** `raw_specification.md` §2 (глоссарий): «Источник данных — место, откуда берётся значение для плейсхолдера: БД документов, **другое ДЛ**, расчётный сервис, внешний API». ДЛ перечислено наравне с БД и внешним API, а не как лицо, формулирующее суждение. | открыт |
| 5.2 | **`ЗапросКДЛ` и `РучнойВвод` не имеют собственной модели взаимодействия.** Описаны одной строкой (`implementation_plan.md` §6.3: «`РучнойВвод`: плейсхолдер ждёт ДЛ»). Механика `ЗапросКДЛ` — та же, что для любого внешнего источника: задача + `АИС_ЛистОжидания` + один текстовый ответ. Нет шага «показать варианты/прецеденты», нет поддержки диалога/уточнения, нет фиксации рассмотренных и отклонённых альтернатив — то есть самой ценной для аудита части управленческого решения. | открыт |
| 5.3 | **Решение попадает под тот же таймер и ту же эскалацию, что и запрос факта.** `АИС_ЛистОжидания` не различает «жду простую дату из отдела кадров» и «жду, пока руководитель обдумает сложную резолюцию» — один `СрокОжидания`, одна дорожка до `ИстечениеСрокаОжидания` → эскалация. Усугубляет п. 2.9: доклад о срыве срока, уходящий без проверки, может быть сформирован именно потому, что ДЛ добросовестно взвешивал решение, а не бездействовал. | открыт |
| 5.4 | **Нет промежуточной формы между скаляром и разделом.** `АИС_РазделыДокумента` (файл, версия, хеш, подтверждение) избыточно тяжеловесен для короткого, но содержательного суждения (формулировка резолюции на 1–2 предложения), а классификация плейсхолдера `Вид = Значение/Раздел` не выделяет категорию «решение, требующее экспертизы». | открыт |
| 5.5 | **Нет голосового/диалогового канала и опоры на прецеденты.** `raw_specification.md` §1.3: результаты вне системы (телефон, email) попадают в систему только как текст, напечатанный кем-то; распознавание речи не рассматривается. RAG сознательно не подсказывает значения (`implementation_plan.md` §2.1 — правильно против галлюцинаций в фактах), но взамен ИИ не предлагает прецеденты/варианты для решения — человек остаётся один на один с пустым полем и таймером. | открыт |

## 6. Как использовать этот документ

- Пункты со статусом `открыт` — кандидаты на решение перед/во время реализации соответствующего этапа; закрытые решения переносятся в `docs/design-decisions.md` по той же схеме, что и остальные проектные решения.
- Пункты `информационно` не требуют решения, но важны для ожиданий по срокам и бюджету.
- Документ не входит в источник истины требований (`docs/requirements/requirements.yaml`); при принятии решения по пункту он либо становится новым FR/NFR со статусом `proposed`, либо фиксируется как явное допущение в `docs/design-decisions.md`.
