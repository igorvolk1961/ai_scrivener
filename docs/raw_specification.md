# Спецификация задачи: ИИ-помощник должностного лица в системе 1С:Предприятие

## 1. Общие сведения

### 1.1. Контекст проекта
Разрабатывается надстройка над платформой 1С:Предприятие 8.3, реализующая интеллектуального помощника должностного лица (ДЛ) для автоматизации работы с документами. Помощник реагирует на события (триггеры), определяет необходимые действия в соответствии с должностными обязанностями ДЛ, находит и заполняет данные в шаблонах документов, генерирует проекты документов/распоряжений/докладов.

### 1.2. Цели системы
- Автоматизировать подготовку проектов документов по триггерам.
- Снизить когнитивную нагрузку на ДЛ за счет автоматического поиска данных.
- Обеспечить соблюдение нормативных сроков исполнения.
- Автоматически эскалировать ситуации срыва сроков с анализом причин.
- Обеспечить прослеживаемость всех действий ИИ-агента.

### 1.3. Ограничения и допущения
- Платформа: 1С:Предприятие 8.3 (минимум 8.3.16 для внешних HTTP-сервисов, рекомендуется 8.3.21+).
- СУБД: PostgreSQL (для production на Linux) или MS SQL Server.
- ОС сервера: Ubuntu 22.04/24.04 LTS.
- ОС рабочих мест: Windows 10/11 или Ubuntu 22.04/24.04 LTS.
- LLM: внешний OpenAI-совместимый API (GigaChat, YandexGPT, DeepSeek (не начальном этапе разработки)).
- Разработка ведется с использованием ИИ-помощника кодирования; спецификация является основным источником требований.
- Обучение/дообучение LLM на данных заказчика на первом этапе не планируется.
- Каналы связи вне системы (телефон, мессенджеры, email) — ручной ввод результатов ДЛ.

## 2. Глоссарий

| Термин | Определение |
|---|---|
| **ДЛ** | Должностное лицо — пользователь системы, занимающий одну или несколько должностей. |
| **Должность** | Штатная единица с определенным набором обязанностей и местом в иерархии. |
| **Должностные обязанности** | Формализованное описание действий ДЛ в различных ситуациях. |
| **Триггер** | Событие, требующее реакции ДЛ (входящий документ, таймер, распоряжение, произвольное событие, ответ на запрос, истечение срока ожидания). |
| **Плейсхолдер** | Именованный фрагмент шаблона документа, подлежащий заполнению данными. |
| **Источник данных** | Место, откуда берется значение для плейсхолдера: БД документов, другое ДЛ, расчетный сервис, внешний API. |
| **Лист ожидания** | Реестр незаполненных плейсхолдеров, по которым отправлены запросы к внешним источникам. |
| **Задача реагирования** | Единица работы: от получения триггера до генерации итогового документа/действия. |
| **Эскалация** | Автоматическая генерация доклада о срыве сроков с анализом причин. |

## 3. Роли и права доступа

| Роль | Права |
|---|---|
| **Администратор системы** | Управление справочниками (должности, шаблоны, типы триггеров, источники данных, нормативные сроки). Не видит содержание задач ДЛ. |
| **Должностное лицо (ДЛ)** | Видит только свои задачи, свои должности, свои входящие/исходящие. Может редактировать проекты документов до отправки. Вводит результаты действий вне системы. |
| **Вышестоящее ДЛ** | Видит свои задачи + доклады подчиненных. Может отдавать распоряжения. |
| **Аудитор** | Просмотр журнала действий ИИ без возможности редактирования. |

Принцип: need-to-know. ДЛ видит только то, что относится к его текущим должностям.

## 4. Функциональные требования

### 4.1. Управление ДЛ, должностями и обязанностями

**4.1.1. Справочник «ДолжностныеЛица»**
- Реквизиты: ФИО, контакт, подразделение, признак активности.
- Связь с регистром `НазначенияДолжностей` (многие-ко-многим через даты).

**4.1.2. Справочник «Должности»**
- Реквизиты: наименование, иерархический родитель (вышестоящая должность), признак активности.
- Иерархия произвольной глубины.

**4.1.3. Регистр «НазначенияДолжностей»**
- Измерения: ДЛ, Должность.
- Реквизиты: дата начала, дата окончания (для временных назначений), признак постоянного.

**4.1.4. Справочник «ДолжностныеОбязанности»**
- Реквизиты: наименование, должность-владелец, текст (многострочный), версия, дата утверждения.
- Поддерживается версионность: история изменений обязанностей сохраняется.
- Обязанности привязываются к парам (ТипТриггера, ТипДействия) — описывают, что делать в конкретной ситуации.

### 4.2. Управление шаблонами документов и плейсхолдерами

**4.2.1. Справочник «ШаблоныДокументов»**
- Реквизиты: наименование, тип документа (исходящий документ / распоряжение / доклад / фрагмент документа), текст шаблона с плейсхолдерами вида `{{ИмяПлейсхолдера}}`, версия, признак активности.
- Табличная часть «Плейсхолдеры»:
  - Имя (совпадает с именем в тексте шаблона).
  - Описание (семантика: что это за данные).
  - Тип данных (строка, дата, число, ссылка на справочник).
  - Обязательность (да/нет).
  - Источник данных (ссылка на справочник «ИсточникиДанных»).
  - Поисковый запрос / шаблон запроса (может содержать ссылки на другие плейсхолдеры).
  - Параметры источника (JSON — специфичные для типа источника настройки).

**4.2.2. Справочник «ТипыДокументов»**
- Исходящий документ, распоряжение, доклад, фрагмент документа.

### 4.3. Управление триггерами и нормативными сроками

**4.3.1. Справочник «ТипыТриггеров»**
- Предопределенные: `ВходящийДокумент`, `Таймер`, `Распоряжение`, `ПроизвольноеСобытие`, `ПоступлениеОтветНаЗапрос`, `ИстечениеСрокаОжидания`.
- Возможность расширения администратором.

**4.3.2. Справочник «ТипыДействий»**
- Предопределенные: `ПодготовитьИсходящийДокумент`, `ПодготовитьФрагментДокумента`, `ПодготовитьРаспоряжение`, `ПодготовитьДоклад`, `ВыполнитьДействиеВнеСистемы`, `ВозобновитьОтложеннуюЗадачу`.

**4.3.3. Регистр «НормативныеСроки»**
- Измерения: ТипТриггера, ТипДействия.
- Реквизит: нормативное время (в часах/минутах).
- Переопределяется вручную при постановке задачи начальником.

**4.3.4. Документ «РасписаниеТаймеров»**
- Для триггеров типа «Таймер»: расписание (cron-подобное) + привязка к ДЛ/должности + тип действия.
- Регламентное задание генерирует триггеры по расписанию.

### 4.4. Обработка входящих событий

**4.4.1. Документ «ВходящийДокумент»**
- Реквизиты: номер, дата поступления, адресат (ДЛ), содержание (текст), прикрепленные файлы, признак обработанности.
- При регистрации автоматически создается задача реагирования.

**4.4.2. Документ «РаспоряжениеВходящее»**
- От вышестоящего ДЛ к подчиненному. Структура аналогична входящему документу.

**4.4.3. Документ «ПроизвольноеСобытие»**
- Универсальный документ для регистрации событий из произвольных каналов.

### 4.5. Задачи реагирования (ядро системы)

**4.5.1. Регистр «ЗадачиРеагирования»**
- Измерение: ID задачи (уникальный).
- Реквизиты:
  - ДЛ-исполнитель.
  - Должность (в рамках которой исполняется).
  - Тип триггера.
  - Источник триггера (ссылка на документ-триггер).
  - Тип требуемого действия.
  - Состояние: `Инициация`, `ПоискШаблона`, `РазрешениеПлейсхолдеров`, `Ожидание`, `Генерация`, `ВерификацияДЛ`, `Завершена`, `Эскалация`.
  - Нормативный срок (дата/время).
  - Фактическое завершение.
  - Результат (ссылка на сгенерированный документ / действие).
  - Родительская задача (для каскадных).
  - Признак эскалации.

**4.5.2. Регистр «СостоянияПлейсхолдеров»**
- Измерения: ID задачи, имя плейсхолдера.
- Реквизиты:
  - Состояние: `ТребуетсяЗапрос`, `Запрошен`, `Ожидает`, `Заполнен`, `НеМожетБытьЗаполнен`.
  - Источник данных.
  - Сформированный поисковый запрос.
  - Полученное значение.
  - ID связанного запроса в листе ожидания.

### 4.6. Лист ожидания и асинхронные операции

**4.6.1. Регистр «ЛистОжидания»**
- Измерение: ID запроса (уникальный).
- Реквизиты:
  - ID задачи-владельца.
  - Имя плейсхолдера.
  - Тип источника (ДЛ / внешний сервис).
  - Адресат запроса (ДЛ или URL сервиса).
  - Текст запроса (сформированный документ/сообщение).
  - Дата отправки.
  - Нормативный срок ожидания.
  - Состояние: `Отправлен`, `ПолученОтвет`, `СрокИстек`.
  - Полученный ответ (текст/структура).

**4.6.2. Автоматические триггеры:**
- При поступлении `РезультатВнешнегоЗапроса` (ручной ввод ДЛ) → система находит соответствующую запись в листе ожидания → заполняет плейсхолдер → возобновляет родительскую задачу → создает триггер `ПоступлениеОтветНаЗапрос`.
- Регламентное задание (периодичность — 1 минута) проверяет лист ожидания: если `НормативныйСрокОжидания < ТекущаяДата` и состояние = `Отправлен` → состояние меняется на `СрокИстек` → создается триггер `ИстечениеСрокаОжидания`.

### 4.7. Эскалация при срыве сроков

**4.7.1. Логика эскалации:**
- Регламентное задание проверяет задачи с состоянием ≠ `Завершена` и `НормативныйСрок < ТекущаяДата`.
- Для каждой такой задачи запускается подпроцесс эскалации:
  1. Собирается таймлайн: когда создана задача, какие запросы отправлялись, какие ответы получены, какие плейсхолдеры не заполнены.
  2. Формируется промпт для LLM с просьбой проанализировать причины срыва и предложить план мероприятий (первоочередные + долгосрочные).
  3. Генерируется документ «ДокладОСрывеСроков».
  4. Доклад направляется вышестоящему ДЛ + исполнителю.
  5. Задача переводится в состояние `Эскалация`.

### 4.8. Интеграция с LLM

**4.8.1. Общий модуль «ИнтеграцияСLLM»**
- Функции:
  - `ОтправитьПромпт(ТекстПромпта, ПараметрыМодели) → Структура{Успех, Ответ, Токены, Стоимость, Ошибка}`.
  - `ОтправитьПромптСОжиданиемJSON(ТекстПромпта, ОжидаемаяСхема) → Структура`.
  - `ВыбратьМодель(ТипЗадачи) → ПараметрыМодели` (для разных задач — разные модели/температуры).
- Настройки (хранятся в константах или справочнике настроек):
  - URL API.
  - API-ключ (хранится зашифрованным).
  - Модель по умолчанию.
  - Таймаут запроса.
  - Максимальное число токенов.
  - Температура (по умолчанию 0.3 для структурированных задач, 0.7 для генерации текста).

**4.8.2. Типовые промпт-шаблоны (хранятся в справочнике «ПромптШаблоны»):**
- `ВыборШаблонаДокумента` — на входе: тип триггера, содержание, список доступных шаблонов. На выходе: ID шаблона.
- `ИзвлечениеПлейсхолдеров` — на входе: текст шаблона. На выходе: JSON-список плейсхолдеров с описаниями.
- `ФормированиеПоисковогоЗапроса` — на входе: описание плейсхолдера, контекст. На выходе: текст запроса к БД.
- `КлассификацияИсточника` — на входе: описание плейсхолдера. На выходе: тип источника (БД/ДЛ/расчетный/внешний).
- `ГенерацияТекстаДокумента` — на входе: шаблон + заполненные плейсхолдеры. На выходе: итоговый текст.
- `АнализСрываСроков` — на входе: таймлайн задачи. На выходе: JSON с причинами и планом.

### 4.9. Разрешение плейсхолдеров (оркестратор)

**4.9.1. Алгоритм:**
1. Для каждой задачи в состоянии `РазрешениеПлейсхолдеров`:
2. Для каждого плейсхолдера в состоянии `ТребуетсяЗапрос`:
   a. Сформировать поисковый запрос (через LLM по шаблону `ФормированиеПоисковогоЗапроса`).
   b. Определить источник данных (через LLM по шаблону `КлассификацияИсточника` или из метаданных шаблона).
   c. В зависимости от источника:
      - **БД документов**: выполнить запрос, при успехе — заполнить плейсхолдер.
      - **Другое ДЛ**: сформировать проект запроса → записать в лист ожидания → состояние плейсхолдера = `Ожидает` → задача → `Ожидание`.
      - **Расчетный сервис**: рекурсивно разрешить аргументы (каждый аргумент — как плейсхолдер), затем вызвать сервис.
      - **Внешний API**: сформировать HTTP-запрос по спецификации источника → выполнить → распарсить ответ.
3. Если все плейсхолдеры заполнены → задача → `Генерация`.
4. Если есть незаполненные → задача → `Ожидание`.

**4.9.2. Защита от бесконечной рекурсии:**
- Максимальная глубина вложенности — 5.
- Максимальное число запросов на задачу — 50.
- При превышении — задача → `Эскалация`.

### 4.10. Генерация документов

**4.10.1. Документ «ИсходящийДокумент»**
- Реквизиты: номер, дата, адресат, тема, текст, основание (ссылка на задачу), шаблон (ссылка), статус (`Проект`, `НаСогласовании`, `Подписан`, `Отправлен`).

**4.10.2. Документ «РаспоряжениеИсходящее»**
- Аналогично, плюс: адресат-ДЛ, срок исполнения.

**4.10.3. Документ «Доклад»**
- Аналогично, плюс: адресат-вышестоящее ДЛ, тип (информационный / о срыве сроков).

**4.10.4. Документ «ДокладОСрывеСроков»**
- Специализированный: причина срыва (текст, сгенерированный LLM), план мероприятий (табличная часть: мероприятие, срок, ответственный, тип — первоочередное/долгосрочное).

### 4.11. Учет действий вне системы

**4.11.1. Документ «РезультатВнешнегоДействия»**
- Реквизиты: задача-владелец, ДЛ-исполнитель, дата/время фактического действия, канал связи (телефон/email/лично/...), контакт собеседника, краткое содержание, прикрепленные файлы.
- При регистрации: задача возобновляется, если была в состоянии `Ожидание` по действию вне системы.

**4.11.2. Документ «РезультатВнешнегоЗапроса»**
- Для ответов на запросы из листа ожидания. Реквизиты: ID запроса в листе ожидания, ДЛ-ответивший, текст ответа, дата получения.

### 4.12. Аудит и журналирование

**4.12.1. Регистр «ИсторияДействийИИ»**
- Измерение: ID записи (уникальный).
- Реквизиты:
  - Дата/время.
  - ID задачи.
  - Тип действия (выбор шаблона / формирование промпта / запрос к источнику / генерация текста / ...).
  - Входные данные (JSON).
  - Промпт (полный текст, отправленный в LLM).
  - Ответ LLM (полный текст).
  - Токены (input/output).
  - Стоимость (если применимо).
  - Результат действия.
  - Ошибка (если была).
  - ДЛ-инициатор (если действие запущено пользователем).

**4.12.2. Обработка «ЖурналЗадачи»**
- По ID задачи показывает полный таймлайн: все действия ИИ, все переходы состояний, все запросы и ответы.

### 4.13. Пользовательские интерфейсы

**4.13.1. Рабочее место ДЛ «МояПанель»**
- Список активных задач (с фильтрами по состоянию, сроку, типу).
- Уведомления о новых триггерах.
- Быстрые действия: открыть задачу, перейти к проекту документа, ввести результат внешнего действия.
- Индикатор просроченных задач.

**4.13.2. Форма задачи реагирования**
- Метаданные задачи (триггер, ДЛ, срок).
- Таймлайн (история действий ИИ).
- Список плейсхолдеров с состояниями.
- Список запросов в листе ожидания.
- Кнопки: «Возобновить», «Перевести в эскалацию», «Завершить вручную».

**4.13.3. Форма проекта документа**
- Текст документа (редактируемый).
- Справа — панель с источниками данных по плейсхолдерам.
- Кнопки: «Сгенерировать заново», «Отредактировать», «На согласование», «Подписать».

**4.13.4. Рабочее место администратора**
- Управление справочниками.
- Настройка нормативных сроков.
- Просмотр общей статистики (без содержания задач).

## 5. Нефункциональные требования

**5.1. Производительность:**
- Время генерации промпта и отправки в LLM — не более 2 секунд.
- Обработка одного плейсхолдера (без учета времени LLM) — не более 1 секунды.
- Регламентные задания не должны блокировать работу пользователей.

**5.2. Надежность:**
- Все изменения в регистрах — транзакционные.
- При сбое LLM — задача не теряется, остается в текущем состоянии, повторная попытка — по таймеру или вручную.
- Лист ожидания сохраняется при перезапуске сервера.

**5.3. Безопасность:**
- API-ключ LLM — в зашифрованном виде (использовать штатные средства 1С для хранения секретов).
- Разграничение доступа — через штатные роли 1С.
- Журнал аудита — только на чтение для роли «Аудитор».

**5.4. Масштабируемость:**
- Архитектура должна позволять вынести оркестратор во внешний микросервис без изменения схемы данных 1С (через HTTP-сервисы).

**5.5. Объяснимость:**
- Любое действие ИИ должно быть воспроизводимо: по записи в журнале можно восстановить, какой промпт был отправлен и какой ответ получен.

### 6.3. Формат взаимодействия с LLM API

## 7. Этапы разработки

### Этап 1. MVP (минимально жизнеспособный продукт)
**Цель:** end-to-end сценарий «входящий документ → проект исходящего».

- Справочники: `ДолжностныеЛица`, `Должности`, `ШаблоныДокументов` (с плейсхолдерами), `ТипыТриггеров`, `ТипыДействий`.
- Регистр `ЗадачиРеагирования` (базовые состояния).
- Документы: `ВходящийДокумент`, `ИсходящийДокумент`.
- Общий модуль `ИнтеграцияСLLM` (один метод `ОтправитьПромпт`).
- Промпт-шаблоны: `ВыборШаблонаДокумента`, `ГенерацияТекстаДокумента`.
- Обработка `МояПанельДЛ` (базовая).
- Сценарий: входящий документ → ИИ выбирает шаблон → заполняет плейсхолдеры из БД (без рекурсии) → генерирует проект → ДЛ видит и редактирует.

**Критерии приемки этапа 1:**
- ДЛ регистрирует входящий документ.
- Система автоматически создает задачу реагирования.
- ИИ выбирает шаблон и генерирует проект исходящего документа.
- ДЛ видит проект, может отредактировать, подписать.
- Все действия ИИ записаны в журнал.

### Этап 2. Расширение источников данных
- Добавить источники: «Другое ДЛ», «Внешний API».
- Регистр `ЛистОжидания`.
- Документы: `ЗапросКДЛ`, `РезультатВнешнегоЗапроса`.
- Триггеры: `ПоступлениеОтветНаЗапрос`, `ИстечениеСрокаОжидания`.
- Регламентное задание `ОбработкаЛистаОжидания`.
- Рекурсивное разрешение плейсхолдеров (с ограничением глубины).

**Критерии приемки этапа 2:**
- Плейсхолдер может быть запрошен у другого ДЛ.
- Задача корректно приостанавливается и возобновляется при получении ответа.
- При истечении срока ожидания — автоматический триггер.

### Этап 3. Расчетные сервисы и эскалация
- Источник «Расчетный сервис» с рекурсией по аргументам.
- Регистр `НормативныеСроки`.
- Документ `ДокладОСрывеСроков`.
- Регламентное задание `ПроверкаСроковЗадач`.
- Промпт-шаблон `АнализСрываСроков`.

**Критерии приемки этапа 3:**
- Плейсхолдер может зависеть от расчетного сервиса.
- При срыве сроков автоматически генерируется доклад с анализом причин.

### Этап 4. Полнота и полировка
- Документ `РаспоряжениеВходящее`, `РаспоряжениеИсходящее`, `Доклад`.
- Действия вне системы (`РезультатВнешнегоДействия`).
- Произвольные события.
- Полноценный аудит и отчеты.
- Админ-панель.
- Настройка нормативных сроков.

## 8. Критерии приемки всей системы

1. ДЛ может зарегистрироваться в системе и быть назначенным на одну или несколько должностей.
2. На каждый из 6 типов триггеров система создает задачу реагирования.
3. ИИ корректно выбирает шаблон документа в ≥90% случаев (оценивается на тестовой выборке из 50 сценариев).
4. ИИ корректно заполняет плейсхолдеры из БД в ≥95% случаев.
5. Лист ожидания корректно приостанавливает и возобновляет задачи.
6. При срыве сроков автоматически генерируется аргументированный доклад.
7. Все действия ИИ записаны в журнал и могут быть воспроизведены.
8. Разграничение доступа работает: ДЛ не видит чужие задачи.
9. Система стабильно работает при 100 одновременных активных задачах.
10. Время отклика UI — не более 2 секунд на типичную операцию.

## 9. Риски и митигации

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| LLM генерирует некорректный JSON | Средняя | Высокое | Валидация ответа, повторная попытка (до 3 раз), fallback на ручной ввод |
| Бесконечная рекурсия при разрешении плейсхолдеров | Низкая | Высокое | Ограничение глубины (5) и числа запросов (50) |
| Срыв сроков из-за медленных внешних сервисов | Средняя | Среднее | Таймауты, эскалация, возможность ручной отмены |
| Утечка API-ключа LLM | Низкая | Критическое | Шифрование, хранение в защищенном хранилище, ротация |
| Перегрузка LLM API | Средняя | Среднее | Очередь запросов, приоритизация, fallback на более простую модель |
| Некорректная классификация источника данных | Средняя | Среднее | Возможность ручной корректировки ДЛ, накопление статистики для улучшения промптов |

## 10. Открытые вопросы (требуют решения в ходе разработки)

1. **Формат хранения плейсхолдеров в шаблоне.** Варианты:
   - Текстовый шаблон с `{{Имя}}` + табличная часть с метаданными.
   - Структурированный шаблон (каждый плейсхолдер — отдельный элемент с типом).
   - **Рекомендация:** текстовый шаблон + табличная часть. Проще в редактировании, достаточно гибкости.

2. **Способ хранения промпт-шаблонов.** Варианты:
   - В справочнике `ПромптШаблоны` (редактируемые администратором).
   - Захардкожены в общем модуле.
   - **Рекомендация:** справочник. Позволяет итеративно улучшать промпты без изменения кода.

3. **Идентификация соответствия «запрос → ответ» в листе ожидания.** Варианты:
   - По уникальному ID запроса.
   - По паре (ДЛ-отправитель, ДЛ-получатель, дата).
   - **Рекомендация:** уникальный ID запроса + ссылка в документе-ответе.

4. **Формат спецификации внешних API.** Варианты:
   - JSON-Schema в справочнике `ИсточникиДанных`.
   - OpenAPI-спецификация.
   - **Рекомендация:** JSON-Schema для простоты. OpenAPI — если потребуется интеграция с множеством внешних сервисов.

5. **Модель LLM для разных задач.** Варианты:
   - Одна модель на все задачи.
   - Разные модели: быстрая/дешевая для классификации, мощная для генерации текста.
   - **Рекомендация:** разные модели. Настройка в справочнике `ПромптШаблоны`.
