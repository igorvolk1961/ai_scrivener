# Спецификация задачи: ИИ-помощник должностного лица в 1С:Документооборот

## 1. Общие сведения

Выделено в отдельный артефакт — `docs/system-analysis/view-and-scope.md` (Vision & Scope).

### 1.1. Контекст проекта

Разрабатывается расширение конфигурации **1С:Документооборот ПРОФ 2.1.38.11** для интеллектуального помощника должностного лица (ДЛ). Помощник реагирует на события (триггеры), определяет необходимые действия в соответствии с должностными обязанностями ДЛ, находит и заполняет данные в шаблонах документов, генерирует проекты документов, распоряжений и докладов.

Расширение не заменяет Документооборот и не создаёт параллельные документы, задачи и справочники. Пользовательские сущности остаются штатными; расширение хранит ИИ-специфичный контекст.

### 1.2. Цели системы

- Автоматизировать подготовку проектов документов по триггерам.
- Снизить когнитивную нагрузку на ДЛ за счёт автоматического поиска данных.
- Обеспечить соблюдение нормативных сроков исполнения.
- Автоматически эскалировать ситуации срыва сроков с анализом причин.
- Обеспечить прослеживаемость всех действий ИИ-агента.

### 1.3. Ограничения и допущения

- Платформа: 1С:Предприятие 8.3.27.
- Поставка: расширение `.cfe` для `ДокументооборотПРОФ` 2.1.38.11; базовая конфигурация не изменяется.
- Штатные объекты переиспользуются: `Пользователи`, `ФизическиеЛица`, `Должности`, `СтруктураПредприятия`, `ВходящиеДокументы`, `ИсходящиеДокументы`, `ВнутренниеДокументы`, `Задача.ЗадачаИсполнителя`, `Файлы`.
- ИИ-специфичные объекты получают префикс `АИС_`; новые документы не создаются.
- СУБД: PostgreSQL (production) или файловая база (локальный учебный стенд).
- ОС сервера: Ubuntu 22.04/24.04 LTS.
- ОС рабочих мест: Windows 10/11 или Ubuntu 22.04/24.04 LTS.
- LLM: внешний OpenAI-совместимый API (DeepSeek; GigaChat для эмбеддингов).
- Разработка ведётся с использованием ИИ-помощника кодирования; спецификация является основным источником требований.
- Обучение/дообучение LLM на данных заказчика на первом этапе не планируется.
- Каналы связи вне системы (телефон, мессенджеры, email) — ручной ввод результатов ДЛ.

## 4. Функциональные требования

Сценарии, выведенные из этого раздела в формате актор/предусловие/поток, — `docs/system-analysis/use-cases.md`.

### 4.1. Управление ДЛ, должностями и обязанностями

**4.1.1. Штатные объекты ДЛ**

- `Справочник.Пользователи` — учётная запись, вход, связь с физическим лицом.
- `Справочник.ФизическиеЛица` — ФИО, контакты, персональные данные.
- `Справочник.СтруктураПредприятия` — подразделение и руководитель.

Собственный справочник `ДолжностныеЛица` не создаётся.

**4.1.2. Штатный справочник «Должности»**

- Реквизиты: наименование, иерархический родитель (вышестоящая должность), признак активности.
- Иерархия произвольной глубины.

**4.1.3. Определение действующих должностей ДЛ — без нового регистра**

Собственный регистр назначений не создаётся. ДЛ может одновременно иметь одну постоянную должность и замещать одну или несколько других; все их обязанности при этом объединяются, а источник (постоянная или замещаемая должность) не важен для их применения.

- Постоянная должность пользователя на дату — штатный периодический регистр `InformationRegisters.СведенияОПользователяхДокументооборот` (измерение `Пользователь`, ресурсы `Должность`, `Подразделение`).
- Замещаемые должности — штатный `Catalogs.ДелегированиеПрав` (`ОтКого`, `Кому`, `ДатаНачалаДействия`, `ДатаОкончанияДействия`, `Действует`): для ДЛ-получателя находятся активные на дату записи, и для каждого `ОтКого` берётся его должность через тот же `СведенияОПользователяхДокументооборот`.
- Действующие должности ДЛ на дату = {постоянная должность} ∪ {должности всех, кого ДЛ замещает на эту дату}. Вычисляется функцией общего модуля (`АИС_ДолжностныеОбязанности.АктивныеДолжностиПользователя(Пользователь, Дата)`), не хранится отдельно.
- Штатный `ПодчиненностьСотрудников` не используется для этой задачи: он хранит руководителя/подчинённого, а не должность.

**4.1.4. Справочник «АИС_ДолжностныеОбязанности»**

- Реквизиты: наименование, должность-владелец, текст, версия, дата утверждения.
- История версий обязанностей сохраняется.
- Обязанности привязываются к парам (`ТипТриггера`, `ТипДействия`) и описывают, что делать в конкретной ситуации.
- **Характеристика триггера (опционально)** — уточняет пару (`ТипТриггера`, `ТипДействия`) внутри ситуации: для `ВходящиеДокументы` — ссылка на штатный `ВидВходящегоДокумента`; для других типов триггера может использоваться аналогичный классификатор. Пример: триггер `ВходящиеДокументы` с `ВидВходящегоДокумента = Авария` и то же самое действие `ПодготовитьДоклад` — это другая обязанность (и, возможно, другая должность-владелец), чем `ВходящиеДокументы` без уточнения. При сопоставлении обязанность с заданной характеристикой, совпадающей с характеристикой фактического триггера, имеет приоритет над обязанностью без характеристики (общим правилом) для той же пары; явный `Приоритет` используется только для разрешения конфликта между обязанностями одинаковой специфичности.
- **Требуемый вид документа (опционально)** — ссылка на `ВидИсходящегоДокумента`/`ВидВнутреннегоДокумента`, если обязанность требует документ конкретного вида (например, «Акт о результатах расследования» для аварии).
- **Фильтрация кандидатов шаблона — не только исполнитель.** Корпус шаблонов, из которого RAG/LLM выбирают, сужается детерминированно до запуска поиска, в два шага: (1) `ТипДействия` определяет, какой из трёх справочников шаблонов используется (`ПодготовитьИсходящийДокумент` → `ШаблоныИсходящихДокументов`; `ПодготовитьРаспоряжение`/`ПодготовитьДоклад` → `ШаблоныВнутреннихДокументов`; и так далее); (2) если найденная обязанность (с учётом характеристики триггера) задаёт требуемый вид документа — кандидаты дополнительно сужаются до этого вида. RAG/LLM ранжируют и выбирают только внутри уже отфильтрованного детерминированно набора, а не всего корпуса — это сужение по типу триггера и обязанности, а не просто подсказка модели.
- Обязанность резолвится по объединённому набору действующих должностей ДЛ (§4.1.3), а не только по одной постоянной должности; при совпадении правил у нескольких действующих должностей применяются все (конфликт разрешается приоритетом правила, не выбором одной должности).
- Для триггера `Распоряжение` требуемое действие может определяться непосредственно текстом распоряжения (письменного или устного, зафиксированного при регистрации), без обязательного совпадения с правилом `АИС_ДолжностныеОбязанности` — каталог обязанностей не единственный источник того, что нужно сделать. Это касается разового действия; если распоряжение устанавливает периодическое/отложенное по времени требование, оно присоединяется к обязанностям только через фиксацию в `АИС_РасписаниеТриггеров` (§4.3.4) — без этой фиксации периодическое требование не действует.
- Штатный `Справочник.Инструкции` не дублируется: он предназначен для инструкций по документам/процессам, а не для обязанностей по должности.

**4.1.5. Назначение исполнителя задачи по обязанности**

При срабатывании триггера исполнитель штатной задачи определяется, а не оставляется неявным:

1. Классифицировать триггер по его характеристике (для входящего документа — его `Вид`, проставленный при регистрации делопроизводителем или детектором бизнес-события).
2. Найти в `АИС_ДолжностныеОбязанности` наиболее специфичную обязанность для пары (`ТипТриггера`, `ТипДействия`): сперва с совпадающей характеристикой, затем — общую (без характеристики), если специфичной нет.
3. Взять должность-владельца найденной обязанности.
4. Найти ДЛ, у кого эта должность входит в действующие на дату (§4.1.3: постоянная или замещаемая).
5. Если найден ровно один ДЛ — он становится исполнителем задачи. Если ноль или больше одного — требуется ручной выбор исполнителя или эскалация; задача не создаётся без исполнителя.

Сопоставление по характеристике — детерминированное (без LLM): характеристика триггера известна на момент его регистрации, поэтому угадывать её не требуется.

### 4.2. Управление шаблонами документов и плейсхолдерами

**4.2.1. Штатные справочники шаблонов**

Используются:

- `ШаблоныВходящихДокументов`;
- `ШаблоныИсходящихДокументов`;
- `ШаблоныВнутреннихДокументов`.

Собственный `ШаблоныДокументов` не создаётся. Штатные шаблоны расширяются табличной частью `АИС_Плейсхолдеры`:

- `Имя` — совпадает с именем в тексте шаблона;
- `Описание` — семантика данных;
- `ТипДанных` — строка, дата, число, ссылка;
- `Вид` — `Значение`, `Список` или `Раздел`;
- `Заголовок`, `Порядок`, `Формат` — для раздела;
- `ТребуетПодтверждения` — для раздела;
- `Обязательность` — да/нет;
- `ИсточникДанных` — ссылка на штатный `ИсточникиДанных`;
- `СпособЗаполнения` — значение `АИС_СпособыЗаполнения`, включая `РешениеДЛ`;
- `ШаблонЗапроса` — утверждённый запрос с параметрами;
- `ПараметрыИсточникаJSON` — настройки конкретного источника;
- `Падеж`, `ЭтоФИО`, `Пол` — согласование ФИО и должности;
- `Маркер` — точный маркер в тексте шаблона;
- `ПравилоАвтозаполнения` — ссылка на базовое правило;
- `Статус` — статус разметки в мастере.

Полный канонический состав полей — `docs/data-model.md` §14.1.

Раздел документа — специализированный плейсхолдер: его значение хранится не строкой, а ссылкой на `АИС_РазделыДокумента`. Это позволяет использовать общий конвейер состояний, листа ожидания и аудита, но не смешивать большой текст раздела с обычными скалярными значениями.

Если структура штатного шаблона не позволяет хранить плейсхолдеры, допускается `АИС_ШаблоныДокументов` только для ИИ-специфичных шаблонов, но не как замена штатных.

**4.2.2. Штатные виды документов**

Используются `ВидыВходящихДокументов`, `ВидыИсходящихДокументов`, `ВидыВнутреннихДокументов`. Собственный `ТипыДокументов` не создаётся.

### 4.3. Управление триггерами и нормативами

**4.3.1. Триггеры**

Приоритет — штатные `ВидыБизнесСобытий` и `ДетекторыБизнесСобытий`. Если они не покрывают событие, используется `АИС_ТипыТриггеров` с предопределёнными значениями:

- `ВходящиеДокументы`, `Таймер`, `Распоряжение`, `ПроизвольноеСобытие`, `ПоступлениеОтветНаЗапрос`, `ИстечениеСрокаОжидания`.

**4.3.2. Справочник «АИС_ТипыДействий»**

Начальные значения (создаются демоданными/администратором как обычные элементы справочника, а не платформенные «предопределённые» — см. ниже):

- `ПодготовитьИсходящийДокумент`;
- `ПодготовитьФрагментДокумента`;
- `ПодготовитьРаспоряжение`;
- `ПодготовитьДоклад`;
- `НайтиИнформацию` — ответ текстом (RAG + генерация), без создания проекта документа; `ТипОбъекта` не заполняется;
- `ВыполнитьДействиеВнеСистемы`;
- `ВозобновитьОтложеннуюЗадачу`.

Платформенный механизм «Предопределённые элементы» для этого справочника не используется: формат его представления в файловом проекте расширения не подтверждён на практике (ни один справочник в фактической базе его не использует), а FR-005 и так требует, чтобы администратор мог добавлять типы без изменения кода — код ищет значение по `Код`/`Наименование`, а не по предопределённому имени.

Реквизит `ТипОбъекта` (штатный `EnumRef.ТипыОбъектов`, значения `ВходящиеДокументы`/`ИсходящиеДокументы`/`ВнутренниеДокументы`; новое перечисление не создаётся) явно связывает тип действия со справочником шаблонов, используемым при фильтрации кандидатов (§4.1.4). Для действий без своего справочника шаблонов (`ПодготовитьФрагментДокумента`, `ВыполнитьДействиеВнеСистемы`, `ВозобновитьОтложеннуюЗадачу`) реквизит остаётся незаполненным. Это данные, а не код: по FR-005 администратор добавляет новые типы действий без изменения кода, поэтому и связь нового типа со справочником шаблонов должна задаваться значением реквизита, а не веткой в BSL.

**4.3.3. Регистр «АИС_НормативыИИ»**

- Измерения: `ТипТриггера`, `ТипДействия`.
- Реквизит: нормативное время ИИ-ответа (в минутах).
- Сроки пользовательской задачи задаются в штатной `Задача.ЗадачаИсполнителя` (`СрокИсполнения`, `ДатаИсполнения`) и не дублируются.
- Норматив ИИ может быть переопределён вручную при постановке задачи.

**4.3.4. Справочник «АИС_РасписаниеТриггеров»**

Справочник, не регистр: измерением регистра было бы только искусственное `ИдентификаторРасписания` (не настоящий бизнес-ключ), а запись должна допускать ссылку на себя извне (из аудита/истории) — оба признака говорят «справочник» (тот же разбор, что для разделов и листа ожидания).

- Для триггеров типа «Таймер»: `ТипТриггера` (`CatalogRef.АИС_ТипыТриггеров`), `ДЛ`, `Должность`, `Расписание` (cron-подобная строка), `СледующийЗапуск`, `Активность`.
- `Распоряжение` (`CatalogRef.ВнутренниеДокументы`, опционально) — ссылка на породившее распоряжение, если запись создана по нему; для записей, заведённых администратором напрямую, не заполняется.
- Регламентное задание `АИС_ГенерацияТриггеровПоТаймеру` (Этап 4–5, не создано сейчас вместе с модулем-реализацией) создаёт триггеры по расписанию.
- Отдельный документ `РасписаниеТаймеров` не создаётся.
- Периодическое/отложенное по времени требование из устного или письменного распоряжения начальника (например, «присылай отчёт каждый понедельник») создаёт триггер только после явной фиксации — элемента `АИС_РасписаниеТриггеров`, ссылающегося на породившее его распоряжение. Само распоряжение расписание не создаёт автоматически. Незафиксированное периодическое требование не присоединяется к обязанностям по должности (§4.1.4) и не производит триггеров — оно просто не существует для системы, пока не зафиксировано.
- **Защита от молчаливой потери фиксации.** При регистрации распоряжения промпт `ОпределениеПериодичностиРаспоряжения` (§4.8.2) анализирует текст на признаки периодичности. Если периодичность обнаружена — создание записи `АИС_РасписаниеТриггеров` со ссылкой на это распоряжение становится обязательным условием завершения базовой задачи по распоряжению: задача не может быть закрыта, пока расписание не создано (или ДЛ явно не отметил, что периодичность определена неверно). Если текст не содержит признаков периодичности — ничего дополнительно не запрашивается, разовые распоряжения не создают трения. Снимает риск, при котором фиксация остаётся исключительно на памяти исполнителя.

### 4.4. Обработка входящих событий

**4.4.1. Штатный справочник «ВходящиеДокументы»**

- Реквизиты: номер, дата поступления, адресат, содержание, файлы, признак обработанности.
- При регистрации создаётся штатная задача и запись `АИС_КонтекстЗадачИИ`; LLM в транзакции документа не вызывается.
- Исполнитель задачи определяется алгоритмом §4.1.5 по `Виду` входящего документа; задача не создаётся без определённого исполнителя.

**4.4.2. Распоряжения**

- Распоряжение от вышестоящего ДЛ регистрируется как `ВнутреннийДокумент` с соответствующим видом.
- Собственный `РаспоряжениеВходящее` не создаётся.

**4.4.3. Произвольные события**

- Регистрируются как бизнес-событие или `АИС_ТипыТриггеров` (если бизнес-события не покрывают).
- Собственный документ `ПроизвольноеСобытие` не создаётся.
- Источник этого триггера — свободный текст, который ДЛ вводит сам, а не объект базы: команда «Сообщить о событии» / «Новый запрос» в `АИС_РабочееМестоДЛ`. Текст сохраняется в штатном `Задача.ЗадачаИсполнителя.Описание` — отдельное хранилище не создаётся.
- Поскольку текста нет в виде структурированного поля (как `ВидВходящегоДокумента` у входящего документа), наиболее специфичная обязанность по §4.1.5 не может быть найдена детерминированно. Промпт `КлассификацияПроизвольногоСобытия` (§4.8.2) по тексту определяет: (а) это ситуация, требующая действия по обязанностям — предлагает `ТипТриггера`/`Характеристику`/`ТипДействия`, дальше решение исполнителя идёт по обычному алгоритму §4.1.5; или (б) это простой запрос на поиск информации — тип действия `НайтиИнформацию` (§4.3.2), результат — текстовый ответ без проекта документа.
- `АИС_ИсточникТриггера` для этого случая не заполняется ссылкой — как и для «расписания», у свободного текста нет объекта-источника; это ожидаемое поведение, не пробел.

### 4.5. Задачи реагирования (ядро системы)

**4.5.1. Штатная задача «Задача.ЗадачаИсполнителя»**

Пользовательская задача хранит:

- автора, исполнителя, роль исполнителя;
- срок и дату исполнения;
- предмет и описание;
- результат выполнения;
- состояние бизнес-процесса;
- права, историю и уведомления.

**4.5.2. Регистр «АИС_КонтекстЗадачИИ»**

- Измерение: `Задача` (`TaskRef.ЗадачаИсполнителя`).
- Ресурсы:
  - тип триггера;
  - тип действия;
  - состояние ИИ (`Инициация`, `ПоискШаблона`, `РазрешениеПлейсхолдеров`, `Ожидание`, `Генерация`, `ВерификацияДЛ`, `Завершена`, `Эскалация`);
  - выбранный шаблон;
  - проект документа (`CatalogRef.ИсходящиеДокументы`);
  - текст проекта;
  - ключ идемпотентности;
  - версия;
  - глубина разрешения;
  - число запросов;
  - признак ручного вмешательства;
  - признак эскалации;
  - родительская задача;
  - источник;
  - даты создания и обновления.

Регистр **не хранит** ДЛ, должность, нормативный срок, фактическое завершение и результат: это поля штатной задачи.

**4.5.3. Регистр «АИС_СостоянияПлейсхолдеров»**

Регистр обоснован (не справочник): измерения `Задача`+`ИмяПлейсхолдера` — настоящий композитный бизнес-ключ, значения по нему именно читаются/перезаписываются «текущим состоянием», а не накапливаются как самостоятельные объекты с жизненным циклом — в отличие от раздела, листа ожидания и расписания.

- Измерения: `Задача`, `ИмяПлейсхолдера`.
- Реквизиты:
  - `ВидПлейсхолдера` — перечисление `АИС_ВидыПлейсхолдеров` (`Значение` / `Список` / `Раздел`);
  - `СсылкаНаРаздел` — `CatalogRef.АИС_РазделыДокумента` (§4.5.4);
  - `Состояние` — перечисление `АИС_СтатусыПлейсхолдеров` (`ТребуетсяЗапрос`, `Запрошен`, `Ожидает`, `Заполнен`, `НеМожетБытьЗаполнен`);
  - способ заполнения (перечисление `АИС_СпособыЗаполнения`), не путать с `ИсточникДанных` в ТЧ шаблона;
  - сформированный запрос;
  - полученное значение;
  - `ЗапросОжидания` — `CatalogRef.АИС_ЛистОжидания` (§4.6.1);
  - ошибка.

**4.5.4. Справочник «АИС_РазделыДокумента»**

Не регистр: каждая версия раздела — отдельный элемент справочника, подчинённый владельцу `ИсходящиеДокументы`. Это даёт настоящую ссылку (`CatalogRef.АИС_РазделыДокумента`), которую можно хранить в других полях (`АИС_СостоянияПлейсхолдеров.СсылкаНаРаздел`, `АИС_ЛистОжидания`) — у регистра сведений такого ссылочного типа нет технически (нет `refType` среди `producedTypes`), поэтому первоначальный выбор «регистр» был неисполним буквально.

- Владелец: `Catalog.ИсходящиеДокументы`.
- Реквизиты: код раздела, заголовок, порядок, обязательность, формат;
  - источник (`ЗапросКДЛ`, `ГотовыйФайл`, `RAGКандидат`);
  - файл (`CatalogRef.Файлы`), версия, хеш;
  - ответственный (`CatalogRef.Пользователи`), задача (`TaskRef.ЗадачаИсполнителя`);
  - статус (`АИС_СостоянияРазделов`);
  - кто и когда подтвердил;
  - комментарий.
- Новая версия раздела (новый файл/хеш) — новый элемент справочника, а не перезапись существующего; старый элемент остаётся со статусом `Устарел` — естественная история версий без отдельного механизма.

Подтверждение раздела действительно только для конкретной версии и хеша. Изменение файла переводит раздел в `Устарел`; ИИ не может подтвердить раздел.

### 4.6. Лист ожидания и асинхронные операции

**4.6.1. Справочник «АИС_ЛистОжидания»**

Справочник, не регистр — по той же причине, что и раздел: измерением было бы искусственное `Запрос`, а ссылаться на конкретный запрос ожидания нужно извне (`АИС_СостоянияПлейсхолдеров.ЗапросОжидания`).

- `Задача` (`TaskRef.ЗадачаИсполнителя`) — задача-владелец;
- `Плейсхолдер` — имя плейсхолдера;
- `ТипЗапроса` — перечисление `АИС_ТипыЗапросовЛистаОжидания` (`Значение` / `ПодтверждениеРаздела`);
- `СсылкаНаРаздел` (`CatalogRef.АИС_РазделыДокумента`) — для подтверждения раздела;
- `ОжидаемаяВерсия`, `ОжидаемыйХеш`;
- `ТипИсточника` — перечисление `АИС_ТипыИсточниковОжидания` (`ДЛ` / `ВнешнийСервис`);
- `Адресат` (`DefinedType.АИС_АдресатЗапроса`);
- `Текст` — текст запроса;
- `ДатаОтправки`;
- `СрокОжидания` — нормативный срок ожидания;
- `Состояние` — перечисление `АИС_СостоянияЗапросовОжидания` (`Отправлен`, `ПолученОтвет`, `СрокИстек`);
- `Ответ` — полученный ответ, `ДатаОтвета`;
- `ЧислоПопыток`.

Запрос к ДЛ — это штатная задача, а не отдельный документ `ЗапросКДЛ`. Подтверждение раздела — тот же лист ожидания с `ТипЗапроса = ПодтверждениеРаздела` и привязкой к версии/хешу.

**4.6.2. Автоматические триггеры**

- Ответ по запросу: найти запись `АИС_ЛистОжидания`, заполнить результат штатной задачи и историю, заполнить плейсхолдер, возобновить `АИС_КонтекстЗадачИИ`.
- Подтверждение раздела: зафиксировать версию/хеш, перевести `АИС_РазделыДокумента` в `Подтвержден`; при изменении файла — в `Устарел`.
- Регламентное задание раз в минуту проверяет лист ожидания: если срок истёк и состояние `Отправлен` → `СрокИстек` → триггер `ИстечениеСрокаОжидания`.

### 4.7. Эскалация при срыве сроков

**4.7.1. Логика эскалации**

- Регламентное задание проверяет задачи с состоянием ≠ `Завершена` и истёкшим `СрокИсполнения`.
- Для каждой задачи:
  1. собирается таймлайн: создание задачи, запросы, ответы, незаполненные плейсхолдеры;
  2. формируется промпт для LLM с анализом причин и планом мероприятий;
  3. создаётся `ВнутреннийДокумент` с видом «Доклад о срыве сроков»;
  4. доклад направляется вышестоящему ДЛ и исполнителю;
  5. `АИС_КонтекстЗадачИИ.СостояниеИИ` → `Эскалация`.

Отдельный документ `ДокладОСрывеСроков` не создаётся.

### 4.8. Интеграция с LLM

**4.8.1. Общий модуль «АИС_ИнтеграцияСLLM»**

- `ОтправитьПромпт(ТекстПромпта, ПараметрыМодели) → Структура{Успех, Ответ, Токены, Стоимость, Ошибка}`.
- `ОтправитьПромптСОжиданиемJSON(ТекстПромпта, ОжидаемаяСхема) → Структура`.
- `ВыбратьМодель(ТипЗадачи) → ПараметрыМодели`.

Настройки:

- URL API;
- API-ключ в защищённом хранилище;
- модель по умолчанию;
- таймаут;
- максимальное число токенов;
- температура (0.3 для структурированных задач, 0.7 для генерации текста).

**4.8.2. Промпт-шаблоны**

- Текст промпта хранится в штатном `Справочник.ШаблоныТекстов`.
- Версия, модель, температура, лимит токенов и ожидаемая JSON-схема — в `АИС_ПромптПараметры`.
- Собственный `ПромптШаблоны` не создаётся.

Типовые промпты:

- `ВыборШаблонаДокумента`;
- `ИзвлечениеПлейсхолдеров`;
- `ФормированиеПоисковогоЗапроса`;
- `КлассификацияИсточника`;
- `КлассификацияПроизвольногоСобытия` — по свободному тексту произвольного события (§4.4.3) определяет `ТипТриггера`/`Характеристику`/`ТипДействия` либо что это запрос на поиск информации (`НайтиИнформацию`);
- `ОпределениеПериодичностиРаспоряжения` — по тексту распоряжения (§4.3.4) определяет, содержит ли оно периодическое/отложенное по времени требование; при положительном ответе фиксация расписания становится обязательной;
- `ГенерацияТекстаДокумента`;
- `АнализСрываСроков`.

### 4.9. Разрешение плейсхолдеров (оркестратор)

**4.9.1. Алгоритм**

1. Для каждой задачи в состоянии `РазрешениеПлейсхолдеров`.
2. Для каждого плейсхолдера в состоянии `ТребуетсяЗапрос`:
   - сформировать поисковый запрос (LLM по шаблону `ФормированиеПоисковогоЗапроса`);
   - определить источник (LLM по шаблону `КлассификацияИсточника` или из метаданных шаблона);
   - выполнить:
     - **БД документов** — утверждённый запрос, заполнить плейсхолдер;
     - **Другое ДЛ** — создать штатную задачу и запись `АИС_ЛистОжидания`, плейсхолдер → `Ожидает`, `СостояниеИИ` → `Ожидание`;
     - **Расчётный сервис** — рекурсивно разрешить аргументы и вызвать сервис;
     - **Внешний API** — HTTP-запрос по спецификации источника, валидация ответа.
3. Если все плейсхолдеры заполнены → `СостояниеИИ` → `Генерация`.
4. Если есть незаполненные → `СостояниеИИ` → `Ожидание`.

**4.9.2. Защита от бесконечной рекурсии**

- Максимальная глубина — 5.
- Максимальное число запросов на задачу — 50.
- При превышении — `СостояниеИИ` → `Эскалация`.

### 4.10. Генерация документов

**4.10.1. Штатный справочник «ИсходящиеДокументы»**

- Реквизиты: номер, дата, адресат, тема, текст, основание, шаблон, статус (`Проект`, `НаСогласовании`, `Подписан`, `Отправлен`).
- Собственный `ИсходящийДокумент` не создаётся.

**4.10.2. Распоряжения и доклады**

- Распоряжения и доклады — `ВнутренниеДокументы` с соответствующими видами.
- Доклад о срыве сроков — `ВнутреннийДокумент` с видом «Доклад о срыве сроков» и табличной частью плана мероприятий.
- Собственные `РаспоряжениеИсходящее`, `Доклад`, `ДокладОСрывеСроков` не создаются.

### 4.11. Учёт действий вне системы

**4.11.1. Результат внешнего действия**

- Регистрируется как результат штатной задачи и/или `ВнутреннийДокумент`, если нужен жизненный цикл документа.
- Реквизиты: задача-владелец, ДЛ-исполнитель, дата/время, канал связи (`ВидыКонтактнойИнформации`/`СпособыДоставки`), контакт, содержание, файлы.
- При регистрации задача возобновляется, если ждала это действие.
- Собственный документ `РезультатВнешнегоДействия` не создаётся.

**4.11.2. Результат внешнего запроса**

- Ответ фиксируется в результате штатной задачи и истории.
- Реквизиты: ID запроса в `АИС_ЛистОжидания`, ответивший ДЛ, текст, дата.
- Собственный документ `РезультатВнешнегоЗапроса` не создаётся.

### 4.12. Аудит и журналирование

**4.12.1. Регистр «АИС_ИсторияДействийИИ»**

- Измерение: ID записи.
- Реквизиты:
  - дата/время;
  - задача;
  - тип действия;
  - входные данные (JSON);
  - промпт;
  - ответ LLM;
  - токены;
  - стоимость;
  - результат;
  - ошибка;
  - ДЛ-инициатор;
  - модель и версия промпта.

История событий штатной задачи остаётся в `ИсторияСобытийЗадач`; ИИ-аудит её не дублирует.

**4.12.2. Обработка «АИС_ЖурналЗадачи»**

- По задаче показывает полный таймлайн: действия ИИ, переходы `СостояниеИИ`, запросы и ответы.

### 4.13. Пользовательские интерфейсы

**4.13.1. Рабочее место ДЛ «АИС_РабочееМестоДЛ»**

- Список активных штатных задач с фильтрами по состоянию, сроку и типу.
- Уведомления о новых триггерах.
- Быстрые действия: открыть задачу, перейти к проекту документа, ввести результат внешнего действия.
- Индикатор просроченных задач.

**4.13.2. Форма задачи**

- Команды и вкладка ИИ в штатной форме `Задача.ЗадачаИсполнителя`.
- Метаданные задачи, `СостояниеИИ`, таймлайн, плейсхолдеры, лист ожидания.
- Разделы документа: ответственный, статус, версия/хеш, подтверждение.
- Кнопки: «Возобновить», «Перевести в эскалацию», «Завершить вручную».

**4.13.3. Форма проекта документа**

- Команды и панель источников в штатной форме `Справочник.ИсходящиеДокументы`.
- Редактируемый текст, источники по плейсхолдерам, кнопки «Сгенерировать заново», «На согласование», «Подписать».
- Панель готовности разделов: обязательные, подтверждённые, устаревшие.

**4.13.4. Рабочее место администратора**

- Управление объектами расширения.
- Настройка `АИС_НормативыИИ`.
- Просмотр статистики без содержания задач.

### 4.14. Мастер шаблонов

Создание шаблонов вручную по одному правилу не масштабируется. Мастер шаблонов автоматизирует разметку, а человек утверждает смысл.

**4.14.1. Режимы**

- импорт существующего DOCX/ODT/TXT/HTML;
- создание по описанию словами;
- клонирование существующего шаблона;
- ручной режим.

**4.14.2. Конвейер**

1. Загрузить файл или выбрать шаблон.
2. Извлечь текст и структуру: разделы, списки, таблицы, колонтитулы.
3. AI-анализ: плейсхолдеры, типы, источники, падежи, повторяемые блоки.
4. Показать таблицу проверки человеку.
5. Сгенерировать `ПравилаАвтозаполненияФайлов` и ТЧ `АИС_Плейсхолдеры`.
6. Выполнить тестовое заполнение.
7. Опубликовать: статус `Утвержден`, версия, активность, индексация RAG.

**4.14.3. Объекты**

- штатные `ШаблоныВходящих/Исходящих/ВнутреннихДокументов`, `Файлы`, `ВерсииФайлов`, `ПравилаАвтозаполненияФайлов`;
- ТЧ `АИС_Плейсхолдеры` в трёх справочниках шаблонов — метаданные плейсхолдеров;
- `АИС_СтатусыШаблонов` — версии, статусы, результаты анализа;
- `АИС_СостоянияШаблонов` — `Черновик`, `НаПроверке`, `Утвержден`, `Устарел`, `Отклонен`;
- обработка `АИС_МастерШаблонов`;
- общие модули `АИС_ГенераторПравилШаблона`, `АИС_ПроверкаШаблона`.

**4.14.4. Формат**

Поддерживаются нативные поля Word/закладки и маркеры проекта:

```text
{{ДатаДокумента}}
{{ФИО.Дательный}}
{{#Список:Поручения}}...{{/Список:Поручения}}
{{#Раздел:Обоснование}}...{{/Раздел:Обоснование}}
```

Маркеры проекта отображаются на `ЗаменяемуюСтроку` и `ЗначениеЗамены`. Финальную вставку выполняет детерминированный DOCX-движок, не LLM.

**4.14.5. Ручная корректировка и отклонение**

- пользователь может принять или отклонить каждый предложенный плейсхолдер;
- добавить новый плейсхолдер вручную;
- удалить плейсхолдер и его правило;
- изменить имя, тип данных, источник, способ заполнения, обязательность, падеж и формат;
- объединить дубли;
- отклонить всю ИИ-разметку и перейти в ручной режим;
- отклонить шаблон полностью без создания правил;
- поддержать undo/redo, автосохранение и предпросмотр;
- показать маркер в документе и обоснование ИИ.

**4.14.6. Сравнение с существующими шаблонами**

Перед созданием нового шаблона мастер:

1. Находит похожие активные шаблоны (вид документа, должность, RAG/эмбеддинги, реквизиты).
2. Сравнивает текст, плейсхолдеры, структуру и метаданные.
3. Показывает side-by-side diff и оценку сходства.
4. Предлагает: обновить существующий, объединить, создать новый или ручное решение.
5. Пользователь принимает окончательное решение.
6. Решение и различия записываются в `АИС_СравненияШаблонов`.

При высокой похожести и изменении только плейсхолдеров предлагается обновление существующего шаблона. Создание нового требует явного подтверждения и причины.

**4.14.7. Алгоритм сравнения**

- текст: cosine similarity эмбеддингов + нормализованный diff;
- плейсхолдеры: добавленные, удалённые, переименованные, изменённые по типу/источнику/обязательности/падежу;
- структура: разделы, списки, таблицы, порядок;
- метаданные: вид документа, должность, организация, назначение.

Веса и пороги хранятся в `config/parameters.yaml`. LLM объясняет различия и предлагает сопоставление, но не принимает решение и не перезаписывает шаблон.

**4.14.8. Критерии приёмки**

- шаблон из DOCX создаётся без ручного заполнения каждого правила;
- человек проверяет и утверждает таблицу плейсхолдеров;
- базовые правила автозаполнения создаются автоматически;
- тестовое заполнение проходит до публикации;
- опубликованный шаблон индексируется в RAG;
- ИИ не публикует шаблон без подтверждения;
- пользователь может отклонить, добавить, удалить или изменить любой плейсхолдер;
- при высокой похожести предлагается обновление существующего шаблона, при низкой — создание нового с подтверждением и причиной;
- решение по сравнению и различия записываются в аудит.

### 4.15. Вычитка документов

Функция опциональна и двухуровнева.

**4.15.1. Уровни**

- **Быстрая** — без LLM: плейсхолдеры, обязательные разделы, даты, суммы, номера, ссылки, формат, повторы, склонения через штатный модуль.
- **Глубокая** — LLM: орфография, пунктуация, грамматика, стиль, смысл, логика, противоречия.

Быстрая проверка запускается после генерации и перед подписью. Глубокая — по кнопке, с показом остатка квоты.

**4.15.2. Замечания**

LLM возвращает только замечания с цитатой, позицией, типом, важностью, сообщением, предложением и confidence. Цитата обязана существовать в тексте; иначе замечание отбрасывается. Замечания не применяются автоматически: пользователь принимает или отклоняет каждое. Принятые применяются детерминированно, после чего выполняется повторная быстрая проверка.

**4.15.3. Квоты**

- администратор задаёт лимит страниц на период;
- лимит может задаваться по роли, подразделению, пользователю;
- пользователь видит страницы, не токены;
- перед запуском показывается оценка: «Документ ≈ 8 страниц, останется 4»;
- быстрая проверка квоту не расходует;
- глубокая блокируется при исчерпании квоты;
- для локальной LLM квота защищает вычислительные мощности, для внешней — бюджет.

**4.15.4. Данные**

- `АИС_ПроверкиДокументов` — запуски, режим, статус, страницы, токены, модель, сводка;
- `АИС_ЗамечанияПроверки` — замечания, цитаты, предложения, решения;
- `АИС_ЛимитыВычитки` — лимиты и использование;
- `АИС_РежимыПроверки`, `АИС_ТипыЗамечаний`, `АИС_ВажностиЗамечаний`;
- `АИС_ПроверкаДокумента`, `АИС_ПанельЗамечаний`.

**4.15.5. Критерии приёмки**

- быстрая проверка не расходует квоту;
- глубокая блокируется при исчерпании квоты;
- замечания содержат существующие цитаты;
- замечания не применяются автоматически;
- принятые замечания применяются и аудируются;
- при перегрузке локальной LLM есть очередь или деградация до быстрой проверки.

## 5. Нефункциональные требования

**5.1. Производительность**

- Время генерации промпта и отправки в LLM — не более 2 секунд.
- Обработка одного плейсхолдера без учёта времени LLM — не более 1 секунды.
- Регламентные задания не блокируют работу пользователей.

**5.2. Надёжность**

- Все изменения в регистрах транзакционные.
- При сбое LLM задача не теряется, остаётся в текущем состоянии; повтор по таймеру или вручную.
- `АИС_ЛистОжидания` сохраняется при перезапуске сервера.

**5.3. Безопасность**

- API-ключ LLM — в защищённом хранилище 1С.
- Разграничение доступа — штатные роли Документооборота + роли расширения.
- `АИС_ИсторияДействийИИ` — только чтение для аудитора.

**5.4. Совместимость**

- Расширение применяется к `ДокументооборотПРОФ` 2.1.38.11 без изменения базовой конфигурации.
- Режим совместимости расширения — 8.3.27.
- Проверка выполняется на копии демо-базы; `.cfe` применяется и снимается без потери доменных данных.

**5.5. Масштабируемость**

- Архитектура позволяет вынести оркестратор во внешний микросервис без изменения схемы данных 1С.

**5.6. Объяснимость**

- Любое действие ИИ воспроизводимо по записи в `АИС_ИсторияДействийИИ`.

## 7. Этапы разработки

### Этап 0. Мастер шаблонов

Ключевой этап: без него шаблоны создаются вручную и проект не масштабируется.

- импорт DOCX/текста, извлечение структуры;
- AI-анализ плейсхолдеров, разделов, списков, типов, источников, падежей;
- таблица проверки человеком;
- автогенерация `ПравилаАвтозаполненияФайлов` и ТЧ `АИС_Плейсхолдеры`;
- тестовое заполнение;
- публикация и индексация RAG.

**Критерии приёмки:** шаблон из DOCX создаётся без ручного заполнения каждого правила, проверяется человеком и индексируется.

### Этап 1. MVP

**Цель:** end-to-end сценарий «входящий документ → проект исходящего».

- Штатные `Пользователи`, `ФизическиеЛица`, `Должности`, `СтруктураПредприятия`, `СведенияОПользователяхДокументооборот`, `ДелегированиеПрав`.
- `АИС_ДолжностныеОбязанности`.
- Штатные шаблоны с ТЧ `АИС_Плейсхолдеры`.
- `АИС_ТипыДействий`, `АИС_ТипыТриггеров` (если нужны).
- `АИС_КонтекстЗадачИИ` + штатная `Задача.ЗадачаИсполнителя`.
- `АИС_ИнтеграцияСLLM`, промпты в `ШаблоныТекстов` + `АИС_ПромптПараметры`.
- `АИС_РабочееМестоДЛ` и команды в штатных формах.

**Критерии приёмки:**

- ДЛ регистрирует `Справочник.ВходящиеДокументы`.
- Создаётся одна штатная задача и одна запись `АИС_КонтекстЗадачИИ`.
- ИИ выбирает шаблон и генерирует проект в `ИсходящиеДокументы`.
- ДЛ редактирует и подписывает проект.
- Все действия ИИ записаны в `АИС_ИсторияДействийИИ`.

### Этап 1.5. Вычитка документов

- быстрая проверка без LLM;
- глубокая LLM-проверка по кнопке;
- замечания с цитатами и accept/reject;
- квоты в страницах на пользователя;
- локальная LLM и очередь/деградация при перегрузке;
- аудит.

**Критерии приёмки:** быстрая проверка не расходует квоту, глубокая блокируется при лимите, замечания не применяются автоматически.

### Этап 2. Расширение источников данных

- Источники «Другое ДЛ», «Внешний API».
- `АИС_ЛистОжидания`; запрос к ДЛ — штатная задача.
- Триггеры `ПоступлениеОтветНаЗапрос`, `ИстечениеСрокаОжидания`.
- Регламентное задание `АИС_ОбработкаЛистаОжидания`.
- Рекурсивное разрешение с ограничениями.

**Критерии приёмки:**

- Плейсхолдер запрашивается у другого ДЛ.
- Штатная задача приостанавливается и возобновляется после ответа.
- При истечении срока ожидания создаётся триггер.

### Этап 3. Расчётные сервисы и эскалация

- Источник «Расчётный сервис» с рекурсией.
- `АИС_НормативыИИ`.
- Доклад о срыве сроков — `ВнутреннийДокумент` + вид.
- Регламентное задание `АИС_ПроверкаСроковЗадач`.
- Промпт `АнализСрываСроков`.

**Критерии приёмки:**

- Плейсхолдер зависит от расчётного сервиса.
- При срыве срока формируется доклад с анализом причин.

### Этап 4. Полнота и полировка

- Распоряжения и доклады на базе `ВнутренниеДокументы`.
- Действия вне системы через результат штатной задачи/`ВнутреннийДокумент`.
- Произвольные события через бизнес-события/`АИС_ТипыТриггеров`.
- Полный аудит, отчёты, админ-панель.
- Настройка `АИС_НормативыИИ`.

## 8. Критерии приёмки всей системы

1. ДЛ — `Пользователь`, связанный с `ФизическимЛицом`, назначен на одну или несколько должностей.
2. На каждый из 6 типов триггеров создаётся штатная задача и запись `АИС_КонтекстЗадачИИ`.
3. ИИ корректно выбирает шаблон в ≥90% случаев на выборке из 50 сценариев.
4. ИИ корректно заполняет плейсхолдеры из БД в ≥95% случаев.
5. `АИС_ЛистОжидания` корректно приостанавливает и возобновляет задачи.
6. При срыве сроков формируется доклад `ВнутреннийДокумент` с анализом причин.
7. Все действия ИИ записаны в `АИС_ИсторияДействийИИ` и воспроизводимы.
8. ДЛ не видит чужие задачи; доступ к базовым задачам — штатный, к `АИС_*` — через задачу.
9. Система стабильно работает при 100 активных задачах.
10. Время отклика UI — не более 2 секунд на типичную операцию.
11. Шаблон из DOCX создаётся мастером без ручного заполнения каждого правила, проверяется человеком и индексируется.
12. Вычитка: быстрая проверка без LLM, глубокая по кнопке, квоты в страницах, замечания с цитатами и accept/reject.

## 9. Риски и митигации

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| LLM генерирует некорректный JSON | Средняя | Высокое | Валидация, 3 попытки, ручной fallback |
| Бесконечная рекурсия плейсхолдеров | Низкая | Высокое | Глубина 5, число запросов 50 |
| Срыв сроков из-за внешних сервисов | Средняя | Среднее | Таймауты, эскалация, ручная отмена |
| Утечка API-ключа | Низкая | Критическое | Защищённое хранилище, ротация |
| Перегрузка LLM API | Средняя | Среднее | Очередь, приоритизация, fallback |
| Некорректная классификация источника | Средняя | Среднее | Ручная корректировка, статистика |
| Базовая конфигурация обновляется | Средняя | Высокое | Расширение не меняет базу; проверка `.cfe` после обновления |
| Дублирование объектов базы | Средняя | Высокое | Маппинг и правило `reuse/extend/new` |
| Ручное создание шаблонов | Высокая | Высокое | Мастер шаблонов, автогенерация правил, проверка человеком |
| Потеря вёрстки DOCX | Средняя | Высокое | Детерминированный DOCX-движок, тестовый рендер |
| Дорогая ежедневная вычитка | Высокая | Высокое | Быстрая проверка, diff-only, кэш, квоты в страницах |
| Галлюцинации при вычитке | Средняя | Высокое | Обязательная цитата, confidence, accept/reject |
| Перегрузка локальной LLM | Средняя | Высокое | Очередь, квоты, деградация до быстрой проверки |
| Утечка документов во внешнюю LLM | Низкая | Критическое | Локальная LLM или политика организации |
| Ограничения расширения на RLS | Средняя | Среднее | RLS на `АИС_*`, штатные права на базовые задачи |

## 10. Принятые проектные решения

Проектирование завершено. Полный список решений — `docs/design-decisions.md`.

- Формат плейсхолдеров: маркеры `{{...}}` + ТЧ `АИС_Плейсхолдеры`; маркеры отображаются на `ЗаменяемуюСтроку`.
- Промпты: текст в `ШаблоныТекстов`, параметры в `АИС_ПромптПараметры`.
- Запрос к ДЛ: базовая задача + `АИС_ЛистОжидания`; отдельный документ не создаётся.
- Внешние API: JSON-схема в расширенных реквизитах штатного `ИсточникиДанных`.
- Триггеры: штатные бизнес-события, `АИС_ТипыТриггеров` — для ИИ-специфичных событий.
- Доклад о срыве: `ВнутреннийДокумент` + вид.
- LLM: DeepSeek для генерации, GigaChat для эмбеддингов, локальная LLM для вычитки.
- Раздел: содержимое в `Файлы`/`ВерсииФайлов`, `АИС_РазделыДокумента` (справочник, подчинён `ИсходящиеДокументы`) хранит ссылку, версию, хеш и подтверждение; новая версия — новый элемент, старая → `Устарел`.
- `АИС_РазделыДокумента`, `АИС_ЛистОжидания`, `АИС_РасписаниеТриггеров` — справочники, а не регистры: нужен ссылочный тип (`refType`), которого у регистра сведений нет (§6.1).
- Должности: `АИС_НазначенияДолжностей` не создаётся — действующие должности (постоянная + замещаемые) вычисляются функцией поверх штатных `СведенияОПользователяхДокументооборот` и `ДелегированиеПрав` (§4.1.3).
- Обязанности: `АИС_ДолжностныеОбязанности` резолвится по объединённому набору действующих должностей, с опциональной характеристикой триггера и требуемым видом документа (§4.1.4); исполнитель задачи определяется детерминированно (§4.1.5).
- Произвольное событие: свободный текст в `Задача.Описание`, классификация текстом через LLM (`КлассификацияПроизвольногоСобытия`); простой поиск — новый тип действия `НайтиИнформацию` (§4.3.2, §4.4.3).
- `АИС_ТипыДействий`/`АИС_ТипыТриггеров`: начальные значения — обычные элементы справочника (демоданные/администратор), платформенный механизм «Предопределённые» не используется — формат не подтверждён, да и не нужен при admin-расширяемости (FR-005).
- Мастер шаблонов: DOCX, маркеры, детерминированная вставка; content controls — следующий этап.
- Сравнение шаблонов: веса 0.4/0.3/0.2/0.1, пороги 0.90/0.70.
- Вычитка: квота 30 страниц/день по умолчанию, страница ≈ 1800 символов, локальная LLM.
