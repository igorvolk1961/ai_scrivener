## 0. Резюме

Каркас переноса собран: метаданные, константы, клиенты сервисов, регламентное задание, снимок, dispatcher инструментов, interactions, формы администрирования и «Мои запросы ИИ», сервисы `agent-service` и `search-service`.

Сквозной сценарий при этом не запускается. Причины:

1. `АИС_АгентИИ.ПоставитьЗадачуВОчередь` не вызывается ниоткуда, поэтому запусков агента не существует.
2. Роль-промпт не формируется, `agent.role_prompt` всегда пустой.
3. `search-service` не читает токен из env и отклоняет все запросы.
4. Approval реализован как один булев флаг на run, а не как разрешение на конкретный инструмент и аргументы.
5. Инструменты, которых нет в dispatcher, уже перечислены в allowlist и при вызове переводят run в `Ошибка`.

Цель плана — сначала получить один управляемый сквозной сценарий на группах «Документы» и «Поиск/знания», затем расширять группы и инфраструктуру.

## 1. Цель и границы

### 1.1. Цель MVP

Сценарий:

```text
документ в 1С
  → задача исполнителю
  → АИС_КонтекстЗадачИИ
  → run в АИС_ЗапускиАгентов
  → регламентное задание
  → agent-service /v1/agent/step
  → tool_call
  → АИС_ИнструментыАгента (группа, ACL, approval)
  → interaction при необходимости
  → ответ пользователя
  → продолжение run
  → complete_task
```

Ограничения MVP:

- работают только группы «Документы» и «Поиск/знания»; «Интернет» включается после отдельной проверки;
- агент включён только пилотному сотруднику;
- роли, подразделения и адресация через объект не автоматизируются;
- остальные группы (персонал, разделы, замечания, корпус знаний) остаются выключенными и не попадают в allowlist до реализации;
- `АИС_Симулятор` не используется production-агентом.

### 1.2. Что не входит в этот план

- Перенос сценарных конфигов симулятора и его UI.
- `technical_approve_template`, `approve_template`.
- Автоматическое создание сотрудников, должностей и приказов.
- Изменение RAG-контура: `search_example` и `search_knowledge_base` продолжают выполняться 1С через `АИС_ИнтеграцияСRAG`.

## 2. Диагностика текущего состояния

### 2.1. Блокеры P0

| № | Проблема | Где | Последствие |
|---|---|---|---|
| 1 | Нет постановки задач в очередь | `src/CommonModules/АИС_АгентИИ/Module.bsl:60` — определение без вызовов; `src/CommonModules/АИС_Уведомления/Module.bsl:80` пишет контекст, но не ставит run | Очередь всегда пуста |
| 2 | Нет генерации роль-промпта | в `АИС_АгентИИ` нет `СформироватьРольПромпт`; `ОбеспечитьНастройкиАгента` ставит `НеСформирован` | Пустой `role_prompt`, автовключение невозможно |
| 3 | `search-service` не читает env | `search-service/src/search_service/__main__.py` вызывает `create_app()` без настроек; `Settings(service_token="")` | Все запросы к `/v1/search` получают 401 |
| 4 | Approval не привязан к инструменту и аргументам | `src/CommonModules/АИС_АгентИИ/Module.bsl:409` — один флаг `approved` на run | Одно одобрение открывает все мутирующие инструменты, включая high-risk |
| 5 | В allowlist есть нереализованные инструменты | `АИС_АгентИИ.РазрешенныеИнструменты`, `АИС_ИнструментыАгента.ВыполнитьИнструмент` | `tool_not_implemented` → run в `Ошибка` |

### 2.2. Разрывы P1

1. `ВыполнитьОдинШаг` и `ОбработатьОчередь` не проверяют `АИС_АгентВключен`, флаги групп и `АИС_НастройкиАгента.Включен` на каждом шаге.
2. `Попытки` не инкрементируется, `СледующаяПопытка` всегда «сейчас» — нет backoff.
3. Между `НайтиАктивныйЗапуск` и `СоздатьЭлемент` нет блокировки — возможны два run на одну задачу.
4. Нет проверки версии контекста перед мутирующим инструментом и нет idempotency key `run + step + tool + hash(args)`.
5. Нет `ИстечьПросроченныеВзаимодействия` и задания `АИС_АгентТаймауты`; `СрокОтвета` не проверяется.
6. Снимок передаёт `subject` = сама задача (`type = "Задача"`, `id` задачи), а не предмет; `title` и `description` — одно и то же; нет `candidates` и `approval` в `context`.
7. Dispatcher не пишет аудит в `АИС_ИсторияДействийИИ`; поля `Запуск`, `Инструмент`, `Группа`, `ЗапросJSON`, `ДлительностьМС`, `ХешАргументов` не добавлены.
8. `ПродолжитьПослеОтвета` не проверяет статус interaction; ключ идемпотентности interaction равен UUID run и не уникален для нескольких вопросов.
9. Нет монитора запусков, списка агентов, backfill-команды и формы «Передать задачу ИИ».
10. Роль `АИС_ДолжностноеЛицо` не имеет прав на `АИС_ВзаимодействияИИ`.
11. `agent-service` использует `GENERIC_SCHEMA` для всех инструментов, не проверяет allowlist модели и не поддерживает per-tool JSON-схемы.
12. CI, pre-commit, `deploy/docker-compose.yml` не включают `agent-service` и `search-service`.
13. README, `requirements.yaml`, `traceability_matrix.md` не отражают миграцию агента.

### 2.3. Незакоммиченная правка

В рабочем дереве изменён `АИС_АгентИИ.ВыполнитьОдинШаг`: ошибка `approval_required` переводит run в `Ожидает` вместо `Ошибка`. Правка допустима только как временное смягчение и должна быть заменена полноценной обработкой в задаче A4 (лимит повторов, очистка `Ошибка`, явное указание модели вызвать `request_action_approval`).

### A4. Approval state machine

Задачи:

- заменить булев `ОдобрениеJSON` на структуру:

```json
{
  "subject_kind": "documents | action",
  "tool": "create_document",
  "args_hash": "sha256",
  "decision": "approved | rejected",
  "answer_text": "",
  "interaction_id": "uuid",
  "created_at": "..."
}
```

- `АИС_АгентИИ.ПроверитьОдобрение(Запуск, Инструмент, Аргументы)`:
  - считает хеш аргументов;
  - требует совпадения `tool` и `args_hash`;
  - учитывает только `decision = approved`;
  - после использования помечает approval израсходованным или очищает;
- `АИС_АгентИИ.УстановитьОдобрение(Запуск, Инструмент, Аргументы, Решение, Текст, Interaction)` вызывается из `ПродолжитьПослеОтвета`;

- автоодобрение разрешено только для `create_document`, `approve_document`, `cancel_document` и только по документам из `documents`;
- для `subject_kind = action` автоодобрение запрещено всегда;
- high-risk инструменты никогда не автоодобряются: `hire_employee`, `accounting_decision`, `create_department`, `manage_document_sections`, `manage_remarks`, `return_document`, `route_remarks`, `kb_*`;

- заполнять `policy.allowed_addressees` по ACL исполнителя;
- убрать дублирование `title = description`.

DoD:

- для задачи с предметом-документом агент видит тип, id и заголовок документа;
- в снимке есть кандидаты триггера;
- чужие документы и адресаты не попадают в снимок.

### A6. Согласование allowlist и реализаций

Задачи:

- ввести `АИС_АгентИИ.РеализованныеИнструменты()` и пересекать с ним `РазрешенныеИнструменты()`;
- временно исключить из allowlist `get_checklist`, `get_job_description`, `save_external_example` и все инструменты групп 13–16, пока они не реализованы;
- либо реализовать `get_checklist`, `get_job_description`, `save_external_example` в рамках A6, если они нужны пилоту.

DoD:

- при включённой группе агент не может получить инструмент, который вернёт `tool_not_implemented`;
- включение любой группы не приводит к гарантированной ошибке run.

## 4. Инкремент B. Надёжность контура (P1)

### B1. Таймауты interactions

- `АИС_АгентИИ.ИстечьПросроченныеВзаимодействия()`;
- задание `АИС_АгентТаймауты` каждые 5 минут;
- по истечении: interaction → `Истек`, run → `Истек`, задача остаётся открытой, уведомление закрывается или переводится в «просрочено»;
- не выполнять автоматических действий после истечения.

### B2. Проверки на каждом шаге

- в `ВыполнитьОдинШаг` проверять `АИС_АгентВключен`, `АИС_НастройкиАгента.Включен`, флаги групп;
- при выключении мастера, группы или агента текущий шаг завершается, run → `Отменен`, interaction закрывается;
- перед мутирующим инструментом перечитывать задачу, контекст и версию; устаревшая версия не применяется.

### B3. Backoff и защита от race

- инкрементировать `Попытки` при 5xx/сети;
- `СледующаяПопытка = сейчас + min(2^Попытки, предел)`; после предела — `Ошибка`;
- создание run защитить блокировкой или уникальным ключом на задачу;
- `Заблокирован`/`КлючБлокировки` выставлять до чтения снимка;
- при перезапуске 1С незавершённые блокировки снимать по таймауту.

### B4. Идемпотентность инструментов

- ключ `run + step + tool + hash(args)` хранить в `АИС_ЗапускиАгентов` или отдельном регистре;
- перед мутирующим инструментом проверять, не создан ли уже результат;
- повторный вызов после сетевого сбоя не создаёт второй документ, задачу или пользователя.

### B5. Аудит

- расширить `АИС_ИсторияДействийИИ` полями `Запуск`, `Инструмент`, `Группа`, `ЗапросJSON`, `ДлительностьМС`, `ХешАргументов`;
- dispatcher пишет запись на каждый вызов инструмента, включая ошибки и отказы по ACL/approval;
- ключ LLM и токены сервисов не логировать;
- срок хранения аудита — 1 год, запусков и interactions — 90 дней; вынести в константы.

### B6. UI и права

- монитор `АИС_ЗапускиАгентов`: состояние, задача, сотрудник, шаг, попытки, ошибка, время; кнопки «Повторить», «Отменить», «Открыть задачу»;
- список `АИС_НастройкиАгента` с карточкой и кнопкой «Импортировать промпты»;
- права `АИС_ДолжностноеЛицо`: чтение своих interactions и запись ответа;
- админ-формы скрыть через `CommandInterface.cmi`;
- добавить `ScheduledJob.АИС_АгентОчередь` и `ScheduledJob.АИС_АгентТаймауты` в подсистему.

## 7. Порядок работ и зависимости

```text
A1 (очередь) ─┬─ A2 (роль-промпт)
              ├─ A4 (approval) ── B1 (таймауты)
              ├─ A5 (снимок)
              └─ A6 (allowlist)
A3 (search-service) ── D2 (CI/compose)
A4 ── B4 (идемпотентность) ── B5 (аудит)
B2, B3 ── B6 (UI)
C1..C4 ── после A и B
D1, D3, D4 ── параллельно, начиная с A1
```

Рекомендуемая последовательность:

1. A1, A2, A3 — без них нет запуска и нет проверяемого агента.
2. A4, A5, A6 — без них сценарий небезопасен и неполон.
3. B1–B6 — довести до эксплуатационной надёжности.
4. C1–C4 — расширять по одной группе.
5. D1–D4 — поддерживать контракт, CI и документацию постоянно.

## 9. Rollout и откат

1. `АИС_АгентВключен = Ложь`, все группы выключены.
2. Развернуть `agent-service` и `search-service`, проверить `/health`.
3. Загрузить расширение, выполнить импорт настроек агентов и промптов.
4. Включить пилотному сотруднику «Документы» и «Поиск/знания»; проверить вручную.
5. Включить «Интернет».
6. Включать остальные группы по одной после приёмки.
7. Откат: выключить мастер-флаг или группу; новые run не создаются, текущие останавливаются после шага, interactions остаются видимыми, данные не удаляются.

## 10. Риски

- LLM может зацикливаться на `approval_required` или неверных аргументах; нужен лимит повторов и понятные tool results.
- Пустой или некачественный роль-промпт делает агента бесполезным; нужен backfill и ручная проверка пилота.
- Публичный интернет-провайдер нестабилен и может быть недоступен; `search-service` должен деградировать предсказуемо.
- Очередь в 1С может создавать нагрузку при большом числе задач; нужен предел на запуск и расписание.
- Мутирующие инструменты без идемпотентности создают дубли; обязательна проверка результата.
- Данные документов и интернета недоверенные; агент не должен выполнять инструкции из них.
- Расширение прав `АИС_ДолжностноеЛицо` может открыть чужие interactions при ошибке в запросе; проверять отбор по сотруднику.
- Сроки хранения запусков, interactions и аудита нужно закрепить в константах до промышленной эксплуатации.

## 12. Решения, которые нужно зафиксировать

1. Границы MVP: только «Документы» и «Поиск/знания» для одного пилотного сотрудника.
2. Модель approval: строго `tool + hash(args)` со сбросом после использования; текущее глобальное одобрение на run недопустимо.
3. Источник роль-промпта: отдел кадров при найме + импорт `system_prompts/*.md`; из должностной инструкции не генерируется.
4. Судьба незакоммиченной правки `approval_required`: заменить обработкой A4 с лимитом повторов.
5. Сроки хранения: запуски и interactions — 90 дней, аудит — 1 год; вынести в константы.
6. Провайдер интернет-поиска на MVP — DuckDuckGo через `search-service`; смена провайдера — отдельный релиз сервиса.
