# Регуляторный контур: триггеры, дела, пробелы и комплаенс-ДЛ

Дата: 2026-11-02

## Цель

Добавить в расширение и симулятор контур обработки внешних регуляторных триггеров:
приём события → дело → входящий документ → задача со сроком → устранение →
проверка доказательств → закрытие или эскалация. Найденные при этом пробелы
плана должны фиксироваться в реестре и блокировать утверждение плана, пока
критические пробелы не устранены или явно не приняты собственником.

## Границы

Входит:

- универсальный приём внешних триггеров (регуляторы и другие внешние субъекты);
- реестр обязательств и правил маршрутизации;
- надзорные дела, сроки, эскалация;
- реестр пробелов и ворота утверждения плана;
- новое ДЛ — директор по правовым вопросам и комплаенсу;
- пилотный сценарий одного регулятора (по умолчанию — пожарный надзор).

Не входит в первый этап:

- коммерческие переговоры с поставщиками и клиентами;
- электронный документооборот с внешними системами (ЭДО);
- юридически значимые подписи и реальные API госорганов;
- автоматическое обжалование в суде;
- вложения файлов (во втором этапе; в MVP — текст и ссылки на документы).

## Ключевые решения

1. Расширение 1С — универсальный транспорт и workflow. Оно не знает, что такое
   МЧС или ФНС; конкретика задаётся справочниками требований и правилами
   маршрутизации.
2. Внешние субъекты не являются пользователями ИБ и не входят в оргструктуру.
   Для HTTP-записи используется сервисная учётная запись.
3. Обработка триггера идемпотентна по паре `Источник + ВнешнийИдентификатор`.
4. Уже утверждённые документы не переписываются. Новые требования оформляются
   новой редакцией, дополнением или отдельным приказом.
5. Контур включается флагом `regulatory.enabled`; по умолчанию выключен.
6. Пилотный регулятор — пожарный надзор. Это данные конфигурации, а не код.

## Модель данных расширения

Новые перечисления:

- `АИС_ВидыВнешнихСубъектов`: Регулятор, Поставщик, Клиент, Банк, Иное.
- `АИС_СтатусыТриггеров`: Новый, Принят, ВРаботе, Обработан, Ошибка, Закрыт.
- `АИС_СтадииНадзорногоДела`: Открыто, Проверка, Предписание, Устранение,
  ПовторнаяПроверка, Санкция, Приостановка, Суд, Закрыто.
- `АИС_СтатусыПробелов`: Открыт, ВРаботе, Устранён, ПринятРиск, Отклонён.
- `АИС_Критичность`: Низкая, Средняя, Высокая, Критическая.

Существующие объекты 1С:ДО, которые нужно использовать вместо дублей:

- `Справочник.Контрагенты` — мастер-сущность контрагента: наименование,
  полное наименование, ИНН, КПП, регистрационный номер, юр/физлицо, контакты,
  ответственный, дополнительные реквизиты.
- `ВходящиеДокументы.Отправитель` — ссылка `CatalogRef.Контрагенты`.
- `ИсходящиеДокументы.Получатель` — ссылка `CatalogRef.Контрагенты`;
  `ИсходящиеДокументы.Адресат` — `CatalogRef.КонтактныеЛица`.
- `Справочник.КонтактныеЛица` — представители контрагента.
- У `Справочник.Контрагенты` нет встроенного признака «регулятор / поставщик /
  клиент», поэтому классификация и параметры поведения хранятся в расширении.

Новые справочники:

- `АИС_ПрофилиВнешнихСубъектов`: ссылка на `Справочник.Контрагенты`, вид
  (регулятор/поставщик/клиент/банк/иное), код, активен, ответственный,
  параметры поведения/примечание. Это дополнение к стандартному контрагенту,
  а не второй контрагент.
- `АИС_РегуляторныеТребования`: код, регулятор (`CatalogRef.Контрагенты`),
  требование, правовое основание, контроль, требуемое доказательство,
  периодичность, ответственная роль/логин, критичность, активно.
- `АИС_ВнешниеТриггеры`: внешний идентификатор, источник
  (`CatalogRef.Контрагенты`), профиль, тип, дата события, дата получения,
  содержание, реквизиты JSON, статус, дело, входящий документ, задача, текст
  ошибки, ключ идемпотентности.
- `АИС_НадзорныеДела`: номер, регулятор (`CatalogRef.Контрагенты`), предмет,
  триггер, стадия, критичность, владелец, дата открытия, срок, дата закрытия,
  итог.
- `АИС_Пробелы`: дело, требование, документ, раздел, описание, доказательство,
  критичность, владелец, срок, статус, задача, комментарий.
- `АИС_ПравилаМаршрутизации`: тип триггера, вид документа, ответственный логин,
  шаблон задачи, срок в днях, приоритет, логин эскалации, активно.

Регистр:

- `АИС_ЖурналВнешнихСобытий`: дата, событие, объект, статус, детали, пользователь.
  Только добавление записей; используется для аудита.

Стандартные объекты для документов и задач: `ВходящиеДокументы`,
`ИсходящиеДокументы`, `КонтактныеЛица`, `Задача.ЗадачаИсполнителя`,
`РегистрСведений.СвязиДокументов`, `Справочник.Контрагенты`.

## HTTP-контракты

Добавить в `src/HTTPServices/АИС_Симулятор/АИС_Симулятор.mdo` и `Module.bsl`:

- `POST /triggers` — принять триггер.
- `GET /triggers?status=&source=&since=&id=` — очередь и карточка.
- `POST /triggers/status` — статус, комментарий, ошибка.
- `GET /cases?status=&id=` — дела.
- `POST /cases/stage` — смена стадии, срок, комментарий.
- `POST /incoming-documents` — входящий документ от внешнего субъекта.
- `POST /findings` / `GET /findings` / `POST /findings/status` — пробелы.
- `GET /obligations` / `POST /obligations` — реестр требований.
- `GET /plan/readiness?document=` — критические открытые пробелы плана.

Расширить `POST /tasks`:

- `Срок` (дата/время), `Приоритет`, `Автор`, `Корреляция`, `Дело`, `Пробел`.
- Идемпотентность: по `Корреляция`, если задана, иначе по текущему правилу.

`POST /triggers` (тело):

```json
{
  "Источник": "МЧС",
  "Тип": "ПлановаяПроверка",
  "ВнешнийИдентификатор": "МЧС-2026-000123",
  "ДатаСобытия": "2026-11-02T10:00:00",
  "Содержание": "Уведомление о проверке",
  "Реквизиты": {"Объект": "...", "Основание": "..."},
  "Вложения": []
}
```

Ответ: `Триггер`, `Дело`, `ВходящийДокумент`, `Задача`, `Срок`, `Статус`.
Повторный вызов с тем же ключом возвращает существующие объекты.

## Обработка

1. `POST /triggers` валидирует источник и тип, проверяет идемпотентность.
2. По `АИС_ПравилаМаршрутизации` создаются дело, входящий документ и задача
   ответственному (в пилоте — комплаенс-ДЛ) со сроком.
3. Документы связываются через `СвязиДокументов`; пишется аудит.
4. Агент комплаенса читает триггер, дело, требования и план; создаёт пробелы
   и задачи на устранение владельцам функций.
5. Владельцы устраняют, создают документы-доказательства, закрывают задачи.
6. Комплаенс принимает доказательства, меняет стадию дела; при просрочке —
   эскалация Гендиректору/собственнику.
7. Повторная проверка закрывает дело или переводит в санкцию/приостановку.

## Пробелы и ворота плана

- Пробел создаётся при отсутствии владельца, контроля, доказательства, срока
  или бюджета для требования; также по результатам стресс-сценариев.
- Критические открытые пробелы блокируют `Собрать` и утверждение плана.
- Собственник может явно принять остаточный риск: статус `ПринятРиск` с
  комментарием и датой.
- Уже утверждённый план не переписывается: создаётся дополнение/новая редакция,
  старые документы остаются историей.

## Новое ДЛ

Добавить `ДиректорПоКомплаенсу`:

- должность: директор по правовым вопросам и комплаенсу;
- прямой руководитель: `ГенДиректор`;
- роли: `ДолжностноеЛицо` (при необходимости `ВышестоящееДолжностноеЛицо`);
- мандат: вести реестр требований, дела, сроки, пробелы; требовать
  доказательства; создавать задачи-требования руководителям служб в рамках
  регуляторного дела; эскалировать Гендиректору и собственнику;
- запрещено: найм, утверждение разделов плана, изменение чужих документов.

Добавить инструмент симулятора `create_remediation_task` (или расширить
`create_task`) с обязательной ссылкой на пробел/дело и записью в аудит.

## Этапы реализации

### Этап 0. Подготовка

- Снять резервную копию live-базы.
- Развернуть копию базы для проверки метаданных и миграции.
- Зафиксировать текущее количество документов/задач/сотрудников для проверки,
  что загрузка расширения ничего не удалила.

### Этап 1. Метаданные расширения

- Создать перечисления, справочники, регистр из раздела «Модель данных».
- Добавить реквизиты/индексы идемпотентности.
- Добавить URL-шаблоны и права ролям:
  `АИС_ДолжностноеЛицо`, `АИС_СервисныйПользователь`,
  `АИС_АдминистраторСистемы`.
- Проверить, есть ли у `Задача.ЗадачаИсполнителя` стандартный срок; если нет —
  добавить расширение `АИС_СрокКонтроля` и использовать его.

### Этап 2. BSL-сервисы

- Новый общий модуль `АИС_ВнешниеТриггеры`:
  - `ПринятьТриггер`, `НайтиТриггерПоКлючу`, `СоздатьДелоПоТриггеру`,
    `СоздатьВходящийДокумент`, `СоздатьЗадачуПоПравилу`,
    `ЗафиксироватьПробел`, `ПроверитьГотовностьПлана`, `ЭскалироватьПросрочку`.
- Тонкие HTTP-обработчики в `Module.bsl`; вся логика — в модуле.
- Идемпотентность: уникальность `Источник + ВнешнийИдентификатор`; при гонке —
  повторный поиск и возврат существующей записи.
- `Собрать`/утверждение плана: проверка критических пробелов.
- Аудит в `АИС_ЖурналВнешнихСобытий`.

### Этап 3. Симулятор: клиент и агент

- `client.py`: модели `ExternalTrigger`, `RegulatoryCase`, `Finding`,
  `Obligation`; методы приёма/списка/статусов.
- `deepseek_agent.py`: инструменты
  `list_regulatory_triggers`, `read_regulatory_case`, `list_obligations`,
  `record_gap`, `create_remediation_task`, `update_case_stage`,
  `create_incoming_document`, `complete_task`.
- Новый агент `ДиректорПоКомплаенсу`; промпт в `prompts/system.md`:
  не выдумывать требования, ссылаться на реестр, фиксировать доказательства,
  не подменять владельцев, эскалировать просрочки.
- `owner_orders.py` или новый `regulatory.py`: после раунда сотрудников
  обрабатывать новые триггеры, запускать комплаенс, проверять просрочки.
- Конфиг: `regulatory` (enabled, pilot regulator, routing), новое ДЛ, `owner-11`
  «О регуляторной готовности» после существующих заказов.
- Новый `owner-11` не менять уже изданные/завершённые заказы.

### Этап 4. Пробелы и пилот

- Создать пилотного регулятора в `Справочник.Контрагенты` и его профиль
  в `АИС_ПрофилиВнешнихСубъектов`.
- Заполнить `АИС_РегуляторныеТребования` пилотного регулятора.
- Заполнить правила маршрутизации.
- Сценарий: проверка → предписание → пробел → задача → доказательство →
  повторная проверка → закрытие.
- Второй сценарий: просрочка → эскалация → санкция.
- Проверить, что критический пробел блокирует сборку, а `ПринятРиск` разрешает.

### Этап 5. UI и наблюдаемость

- Минимально: вкладка/секция «Регуляторы» со списком триггеров, дел, пробелов,
  сроков и статусов.
- Журнал: отдельный префикс `regulatory`; события приёма, маршрутизации,
  эскалации, закрытия.
- `GET /plan/readiness` отображать в UI перед утверждением.

## Без обнуления

- Не восстанавливать базу и не пересоздавать её.
- Загружать только аддитивные метаданные; перед загрузкой — backup.
- Не менять текущий `owner-4`; новый контур включать после его завершения или
  на копии.
- Новое ДЛ добавлять наймом/`POST /employees`, а не пересборкой оргструктуры.
- Утверждённый план получает дополнение/новую редакцию, старые документы
  остаются историей.
- Флаг `regulatory.enabled=false` до пилота; затем включить.

## Проверка

- Юнит-тесты симулятора: payloads, идемпотентность, маршрутизация, ворота
  пробелов, запреты инструментов.
- HTTP-тесты на копии: дубль триггера, неизвестный источник, отсутствующий
  ответственный, просрочка, критический пробел, принятый риск.
- Регрессия: существующие 61 тест, `ruff`, `mypy`; сборка EDT и
  `load_extension.sh`; проверка, что количество старых документов/задач не
  изменилось.
- Приёмка пилота: пожарная проверка, предписание, пробел, задача, доказательство,
  повторная проверка, закрытие; затем сценарий просрочки с эскалацией.

## Риски

- Метаданные расширения разрастаются; MVP ограничить шестью справочниками.
- У задач может не быть стандартного срока; проверить и при необходимости
  добавить реквизит расширения.
- Ворота плана могут заблокировать текущий прогон; включать только для новых
  редакций/после `owner-4`.
- LLM может выдумать требование; обязательна ссылка на `АИС_РегуляторныеТребования`
  и доказательство.
- Не смешивать регуляторов с коммерческими контрагентами в MVP; общий контур
  оставить расширяемым.

## Открытые решения (по умолчанию)

- Пилотный регулятор: пожарный надзор; при необходимости меняется seed-данными.
- Вложения: второй этап; MVP — текст, ссылки, документы.
- Название ДЛ: `ДиректорПоКомплаенсу`.
- Правила маршрутизации: справочник 1С, не JSON в симуляторе.
- Флаг: выключен до пилота.
