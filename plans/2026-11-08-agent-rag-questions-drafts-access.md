Дата: 2026-11-08

- `ai-scrivener-enterprise-sim` — агент-имитатор, клиент, UI симулятора.

## 0. Статус реализации

Реализовано в текущей итерации:

- RAG: scope `examples`, отдельная коллекция, `examples_store`, маршрутизация retrieve/index/metadata/cleanup, конфигурация и тесты;
- расширение: справочники `АИС_ЧекЛисты`, `АИС_ПунктыЧекЛиста`, `АИС_ЧерновикиДокументов`, регистры `АИС_ОтветыНаВопросыОбразцов`, `АИС_РазрешенияОбменаИнформацией`;
- расширение: поля образца (URL, дата, источник, хеш, статус, модель), поля вопроса (`КодВопроса`, `ТекстВопроса`, `РазрешитьСвободныйВвод`), `АИС_ЧекЛист`/`АИС_ВерсияЧекЛиста` в инструкциях;
- расширение: `GET/POST /checklists`, `GET /job-descriptions`, `GET /job-duties`, `POST /examples/search`, `POST /examples`, `POST /knowledge/search`;
- правило «одна действующая инструкция на должность»: поиск только действующих, серверная проверка дубля, права HTTP-маршрутов;
- симулятор: чек-лист переносится в справочник, парсер 29 пунктов, `save_checklist`;
- симулятор: инструменты `search_example`, `search_knowledge_base`, `search_internet(category)`, `save_external_example`, `get_checklist`, `get_job_description`, `ask_example_changes`, `ask_decision`;
- fallback-гард: интернет для example/knowledge запрещён без пустого RAG-результата;
- вопросы: валидация 1–7 вариантов, рекомендуемые первыми, свободный ввод, варианты не сохраняются;
- файловое хранилище взаимодействий и UI-вкладка «Вопросы» с API ответов;
- `check_document_access`, черновики, четыре действия согласования и запросы информации с формулировкой по отношению;
- UI-карточка согласования черновика.

Порядок изменён: сначала доделываются части, не требующие реальных данных.
Отложено до старта развертывания предприятия:

- индексация `АИС_ОбразцыДокументов` в examples-scope и бэкфилл;
- наполнение публичных обязанностей полными текстами инструкций;
- интеграционные сценарии на реальной базе и golden set.

Следующие шаги без реальных данных:

- загрузка полного текста внешнего образца по URL (fetch/извлечение);
- тесты API черновиков и запросов на синтетических данных;
- доработка промптов под новые инструменты.

## 1. Цель

Добавить агентам-имитаторам должностных лиц (ДЛ) шесть контуров:

1. RAG-поиск образцов документов (`search_example`) с вопросами об изменениях образца.
2. RAG-поиск нормативно-справочной информации (`search_knowledge_base`).
3. Вопросы пользователю: изменения образца и принятие решения.
4. Сохранение внешнего образца вместе с вопросами (без вариантов ответов).
5. Черновик, согласование, отправка, доработка и отказ; проверка доступа и запросы информации у других ДЛ.
6. Справочник чек-листов; пока в нём один чек-лист — для разработки новой должностной инструкции.

Ключевые инварианты:

- интернет для образцов используется ТОЛЬКО после пустого `search_example`;
- интернет для НСИ используется ТОЛЬКО после пустого `search_knowledge_base`;
- отправка адресату выполняется ТОЛЬКО после `approve_send`;
- ограниченная информация не передаётся смежному ДЛ без действующего распоряжения общего начальника;
- должностные обязанности всех ДЛ и чек-листы общедоступны;
- на одну должность разрабатывается ОДНА общая должностная инструкция; если должность занимают несколько ДЛ, инструкция у них общая и повторно не создаётся;
- вопросы пользователю: 1–7 предопределённых вариантов, свободный ввод всегда доступен и в лимит не входит;
- варианты ответов НЕ сохраняются вместе с образцом и вопросами: модель формирует их в момент вопроса;
- модель ОБЯЗАНА определить рекомендуемый вариант и поставить его первым в списке; для `single` — ровно один рекомендуемый, для `multiple` — один или несколько.

## 2. Архитектурные решения

| Решение | Выбор | Причина |
|---|---|---|
| Где хранятся образцы | `Справочник.АИС_ОбразцыДокументов` + вопросы в `Справочник.АИС_ВопросыПриСозданииДокументаПоОбразцу` | справочники уже созданы; вопросы подчинены образцу |
| Где искать образцы | отдельный RAG-scope `examples` и коллекция `ai_scrivener_examples` | не смешивать образцы с НСИ и документами |
| Где искать НСИ | существующий scope `knowledge` | не менять текущий контур знаний |
| Кто отвечает на вопросы | пользователь через UI симулятора; агент ждёт ответ | агент не имеет интерактивного терминала |
| Где хранятся вопросы/ответы агента | файловое хранилище взаимодействий `state/interactions/` | работает и при UI, и при CLI-запуске |
| Черновик | отдельный `Справочник.АИС_ЧерновикиДокументов`; реальный документ создаётся только при отправке | адресат не видит черновик и не получает задачу раньше времени |
| Контроль доступа | `АИС_ПраваДоступа.ПроверитьДоступность` + регистр разрешений обмена | переиспользовать существующий ACL |
| Исключение для смежников | структурированный регистр `АИС_РазрешенияОбменаИнформацией` | нельзя разбирать свободный текст распоряжения |
| Свежесть НСИ | `actual/outdated/requires_confirmation/unknown` | запрос подтверждения только по явному основанию |
| Чек-листы | `Справочник.АИС_ЧекЛисты` + подчинённый `Справочник.АИС_ПунктыЧекЛиста` | чек-лист — справочные данные, а не документ; пункты нужны для проверки инструкции |
| Должностные инструкции | одна активная инструкция на `Справочник.Должности`, без привязки к сотруднику | несколько ДЛ на одной должности используют общий документ |

### Этап 1. RAG-scope `examples`

Файлы:
- `rag-service/src/rag_service/config.py`

- `src/CommonModules/АИС_ИнтеграцияСRAG/Module.bsl`
- `src/CommonModules/АИС_ИндексацияДокументов/Module.bsl`

Задачи:

1. Добавить конфигурацию:
   - `examples_scope_enabled` (по умолчанию `false` до создания коллекции);
   - `examples_collection`, `examples_alias`, путь/лимиты — по аналогии с `documents`.
2. Добавить в приложение `examples_store`; расширить `_scope_store` значением `examples`.
3. Расширить `RetrieveRequest.scope` до `knowledge | documents | examples`.
4. В `Retriever.retrieve` выбирать store по scope; для `examples` не требовать ACL, но фильтровать `active=true`.
5. Добавить source type `document_example`; индексировать `Справочник.АИС_ОбразцыДокументов`:
   - `source_id` — UUID образца;
   - `version` — `Версия`;
   - `title` — заголовок/вид;
   - `text` — `Содержание` + текст файла;
   - `doc_type` — `ВидДокумента`;
   - `is_current` — `Активность`;
   - `content_hash` — хеш текста;
   - metadata: `example_id`, `document_kind`, `source_type`.
6. Индексировать при записи образца, при изменении вопросов и по полной сверке.
7. `search_knowledge_base` не должен возвращать `document_example`: scope `knowledge` уже отдельный, но добавить тест-инвариант.
8. Создать коллекцию и alias, включить `examples_scope_enabled`.

Критерии:

- `/v1/retrieve` со `scope=examples` возвращает образцы;
- `scope=knowledge` не возвращает образцы;
- повторная индексация не создаёт дублей;
- пустой результат возвращает `results: []` без ошибки.

Добавить в образец:

- `ИсточникURL` (String);
- `ДатаПолучения` (Date);
- `ТипИсточника` (String: `RAG` | `Интернет`);
- `ХешСодержимого` (String);
- `СтатусПодтверждения` (String: `unconfirmed` | `confirmed`);
- `МодельГенерации` (String).

Добавить в вопрос:

- `КодВопроса` (String, стабильный идентификатор вопроса);
- `ТекстВопроса` (String, полный текст);
- `ТипОтвета` — `single` | `multiple`;
- `РазрешитьСвободныйВвод` (Boolean, по умолчанию `true`);
- `Подсказка` (String);
- `ОтветПоУмолчанию` (String, только для свободного ввода).

Варианты ответов в справочнике вопросов НЕ хранятся. Модель формирует их
при вызове `ask_example_changes`/`ask_decision`, выбирает рекомендуемый
вариант и ставит его первым.

Новый регистр `АИС_ОтветыНаВопросыОбразцов`:

- измерения: `Образец`, `Вопрос`, `Пользователь`;
- ресурсы: `ОтветJSON`, `СвободныйТекст`, `ДатаОтвета`.

Новый справочник `АИС_ЧерновикиДокументов`:

- `Автор` (Пользователи);
- `ВидДокумента` (ВидыВнутреннихДокументов);
- `Заголовок` (String, 150);
- `Содержание` (String);
- `Адресат` (Пользователи);
- `Основание` (ВнутренниеДокументы, опционально);
- `ВидЧерновика` (`document` | `information_request` | `approval_response`);
- `ВидЗапроса` (`provide` | `confirm` | `clarify`, опционально);
- `Статус` (`draft` | `on_review` | `rework` | `approved` | `sent` | `rejected`);
- `Замечания` (String);
- `ИсходныеДокументы` (JSON-массив UUID);
- `Версия` (Number).

Новый регистр `АИС_РазрешенияОбменаИнформацией`:

- измерения: `Распоряжение`, `Отправитель`, `Получатель`, `Категория`;
- ресурсы: `Объем`, `ДействуетДо`, `Активно`.

Новый справочник `АИС_ЧекЛисты`:

- `Наименование` — например, «Разработка новой должностной инструкции»;
- `Назначение` (`РазработкаДолжностнойИнструкции`; пока единственное значение);
- `Версия` (String);
- `Содержание` (String, полный текст чек-листа);
- `Активность` (Boolean).

Новый подчинённый справочник `АИС_ПунктыЧекЛиста`:

- владелец — `АИС_ЧекЛисты`;
- `Порядок` (Number);
- `Раздел` (String);
- `Текст` (String);
- `Обязательный` (Boolean);
- `Активность` (Boolean).

Начальное наполнение:

- один чек-лист `Разработка новой должностной инструкции`;
- источник — `ai-scrivener-enterprise-sim/config/checklists/ДолжностнаяИнструкция.md`;
- при импорте сохраняются полный текст и разобранные пункты с разделами и признаком обязательности;
- чек-лист доступен всем ДЛ без ACL.

Должностные инструкции:

- документ вида `Должностная инструкция` имеет ровно один ключ — `АИС_Должность`;
- привязки к сотруднику нет;
- на одну должность допускается одна активная (не помеченная на удаление, не `НеДействует`) инструкция;
- если должность занимают несколько ДЛ, все используют эту инструкцию;
- в документ добавить `АИС_ЧекЛист` и `АИС_ВерсияЧекЛиста` для трассировки;
- при создании/обновлении проверять уникальность по должности на сервере, а не только в UI;
- при найме на должность с существующей инструкцией новая задача на разработку не создаётся.

Права:

- администратор — полные;
- сервисный пользователь — чтение/запись;
- должностные лица — чтение своих черновиков, чтение образцов, вопросов, обязанностей и чек-листов;
- аудитор — чтение.

### Этап 3. HTTP API расширения

Файлы:
- `src/HTTPServices/АИС_Симулятор/АИС_Симулятор.mdo`
- `src/HTTPServices/АИС_Симулятор/Module.bsl`

Новые маршруты:

| Метод | Маршрут | Назначение |
|---|---|---|
| POST | `/examples/search` | `search_example` |
| POST | `/knowledge/search` | `search_knowledge_base` |
| POST | `/examples` | сохранить внешний образец с вопросами |
| GET | `/examples/{id}` | образец + вопросы |
| GET | `/job-duties` | публичные обязанности всех ДЛ |
| GET | `/checklists?purpose=...` | публичные чек-листы с пунктами |
| GET | `/job-descriptions?position_id=...` | действующая инструкция по должности |
| POST | `/documents/access` | проверка доступа |
| POST | `/drafts` | создать/обновить черновик |
| POST | `/drafts/send` | отправить после `approve_send` |
| POST | `/drafts/rework` | вернуть на доработку с замечаниями |
| POST | `/drafts/reject` | отклонить отправку |
| POST | `/drafts/approve-referenced` | утвердить связанный документ |
| POST | `/information-requests` | создать черновик запроса с учётом отношения |

Требования к ответам:

- `examples/search`:
  - `status`: `ok` | `empty`;
  - `results[]`: `example_id`, `title`, `document_kind`, `text`, `score`, `source_type="rag"`, `questions[]`;
  - вопросы берутся из `АИС_ВопросыПриСозданииДокументаПоОбразцу` по владельцу-образцу, сортировка по `Порядок`;
  - вопросы возвращаются без вариантов ответов и без рекомендаций.
- `knowledge/search`:
  - `status`: `ok` | `empty`;
  - `results[]`: `text`, `score`, `source`, `document_id`, `valid_until`, `last_verified_at`, `freshness_status`.
- `POST /examples`:
  - дедупликация по `ИсточникURL` + `ХешСодержимого`;
  - образец и вопросы сохраняются одной транзакцией;
  - варианты ответов не принимаются и не сохраняются;
  - статус нового образца — `unconfirmed`.
- `documents/access`:
  - использует `АИС_ПраваДоступа.ПроверитьДоступность`;
  - для смежника дополнительно проверяет `АИС_РазрешенияОбменаИнформацией`;
  - возвращает `allowed`, `basis`, `restricted`.
- `information-requests`:
  - вычисляет отношение по оргструктуре: `manager` | `subordinate` | `peer`;
  - применяет шаблон формулировки;
  - проверяет доступ к `ИсходныеДокументы`;
  - создаёт черновик в статусе `draft`.
- `GET /checklists`:
  - доступен любому аутентифицированному ДЛ без ACL документов;
  - возвращает `id`, `name`, `purpose`, `version`, `content`, `items[]` (`order`, `section`, `text`, `required`);
  - по умолчанию отдаёт чек-лист `РазработкаДолжностнойИнструкции`.
- `GET /job-descriptions`:
  - возвращает ровно одну действующую инструкцию по `position_id` или `404`;
  - не создаёт и не дублирует документ;
  - если найдено несколько активных, возвращает ошибку `duplicate_job_description` и список id для ручного разбора.

Свежесть НСИ:

- `outdated` — документ недействующий или `ДействуетДо < сейчас`;
- `requires_confirmation` — явный признак в документе/задаче;
- `actual` — действующий, утверждённый, без истёкшего срока;
- `unknown` — метаданных недостаточно.

Для `ДействуетДо` и `ДатаПроверкиАктуальности` добавить адаптированные реквизиты в `ВнутренниеДокументы` и включить их в payload индексатора.

| `search_example` | `query`, `document_kind?`, `limit?` | `status`, `results[]` с `questions[]` |

Изменение `search_internet`:

- `category` обязателен: `example` | `knowledge` | `materials`;
- `example` и `knowledge` разрешены только после пустого соответствующего RAG-результата в текущей задаче;
- `materials` разрешён только для задач наполнения корпуса (`requires_knowledge`);
- при нарушении инструмент возвращает ошибку `fallback_not_allowed`, а не выполняет поиск.

Состояние задачи:

```python
@dataclass
class SearchState:
    example_rag_empty: bool = False
    knowledge_rag_empty: bool = False
```

- `search_example` устанавливает `example_rag_empty = (status == "empty")`;
- `search_knowledge_base` устанавливает `knowledge_rag_empty = (status == "empty")`;
- любой непустой RAG-результат сбрасывает соответствующий флаг в `False`;
- состояние живёт в пределах одной задачи и не переносится между задачами.

Правила разработки должностной инструкции:

- `get_job_description(position)` вызывается ДО создания документа;
- если инструкция уже есть, агент ОБЯЗАН использовать её и не создавать новую;
- если инструкции нет, агент ОБЯЗАН получить чек-лист `get_checklist("РазработкаДолжностнойИнструкции")` и подготовить текст по его пунктам;
- в документе заполняется `АИС_Должность`, `АИС_ЧекЛист`, `АИС_ВерсияЧекЛиста`; поле сотрудника не заполняется;
- после утверждения инструкция действует для всех ДЛ на этой должности;
- при найме второго и последующих ДЛ на ту же должность задача на разработку инструкции не создаётся.

Валидация вопросов:

- 1–7 вариантов на вопрос;
- `allow_free_text` всегда `true`;
- `request_info` требует `addressee_login` и `addressee_position`;
- `multiple` требует `min_selected >= 1`;
- в каждом вопросе есть рекомендуемые варианты; они идут первыми;
- для `single` — ровно один `recommended=true`;
- для `multiple` — один или несколько `recommended=true`, все в начале списка;
- если модель не может обосновать рекомендацию, она рекомендует вариант запроса недостающей информации (если он есть) либо первый безопасный вариант;
- при нарушении — ошибка инструмента, вопрос не создаётся.

### Этап 5. Взаимодействие с пользователем и UI

Файлы:
- новый `ai-scrivener-enterprise-sim/src/enterprise_sim/interactions.py`
- `ai-scrivener-enterprise-sim/src/enterprise_sim/ui.py`

Хранилище:

- каталог `state/interactions/<task_id>/<interaction_id>.json`;
- атомарная запись через временный файл + `replace`;
- поля: `id`, `task_id`, `employee`, `kind` (`question` | `draft_review`), `payload`, `status` (`pending` | `answered` | `timeout`), `created_at`, `answered_at`, `answer`;
- блокирующее ожидание с интервалом опроса и таймаутом (по умолчанию 30 минут, настраивается).

UI:

- вкладка «Вопросы и черновики»;
- `GET /api/interactions?status=pending`;
- `POST /api/interactions/{id}/answer`;
- для вопроса: выбор одного/нескольких вариантов, свободный текст;
- для черновика: редактируемый текст, замечания, кнопки `approve_send`, `rework`, `approve_referenced`, `reject_send`;
- автообновление, пока идёт `/api/orders/process`;
- взаимодействия не захватывают `ORDER_LOCK`, чтобы не блокировать обработку приказа.

CLI:

- `--interaction-timeout` для headless-прогонов;
- `--auto-answer` только для тестов, с явным предупреждением в логе.

### Этап 6. Черновики и согласование

Поток:

1. Агент формирует текст и вызывает `create_draft`.
2. `create_draft` проверяет доступ к `source_document_ids`, сохраняет черновик, возвращает `draft_id`.
3. Агент вызывает `submit_draft_for_review`.
4. Пользователь выбирает действие:
   - `approve_send` — отредактированный текст отправляется адресату;
   - `rework` — замечания сохраняются, черновик переходит в `rework`;
   - `approve_referenced` — утверждается `referenced_document_id` без замечаний;
   - `reject_send` — черновик не отправляется.
5. При `reject_send` агент ОБЯЗАН вызвать `ask_decision` о судьбе черновика: `save_as_draft`, `delete_draft`, `rework_draft`, `change_addressee` + свободный ввод.

Правила:

- до `approve_send` у адресата нет задачи и входящего документа;
- `approve_send` создаёт `ВнутренниеДокументы`, проставляет адресата, связывает с основанием и запускает штатную подписку;
- `approve_referenced` доступен только при наличии `referenced_document_id` и только если черновик является ответом на просьбу согласовать/утвердить;
- замечания при `rework` сохраняются структурированно и передаются агенту;
- повторная отправка после доработки проходит тот же путь.

### Этап 7. Доступ, запросы информации и обязанности

Доступ:

- перед чтением чужого документа и перед передачей сведений — `check_document_access`;
- `create_draft` и `/drafts/send` повторно проверяют `source_document_ids`;
- при отказе отправка отклоняется сервером, агент не может обойти проверку;
- смежнику запрещено передавать ограниченные сведения;
- исключение — активная запись `АИС_РазрешенияОбменаИнформацией`, созданная по распоряжению общего начальника с явными категориями, объёмом и получателями.

Запрос информации:

- основания: пустой RAG-НСИ, `outdated`, `requires_confirmation`, истёкший срок, явное требование задачи, отсутствие обязательных данных;
- агент фиксирует основание и доказательство в черновике;
- адресат выбирается по `list_job_duties`: точное совпадение предметной области, затем ближайший по оргструктуре, при равенстве — вопрос пользователю;
- `create_information_request` вычисляет отношение и применяет шаблон:
  - руководителю — просьба;
  - подчинённому — поручение с сроком;
  - смежнику — просьба с обоснованием и ссылкой на общую задачу/распоряжение;
- запрос проходит `check_document_access` и `submit_draft_for_review`.

Обязанности:

- расширить `GET /obligations` или добавить `GET /job-duties`;
- возвращать логин, ФИО, должность, подразделение, руководителя, полный текст обязанностей;
- не применять ACL документов;
- если обязанности лежат в закрытом документе, публиковать только извлечённый текст обязанностей.

### Этап 7.1. Чек-листы и должностные инструкции по должностям

Справочник чек-листов:

- `АИС_ЧекЛисты` — перечень чек-листов; пока один: `Разработка новой должностной инструкции`;
- `АИС_ПунктыЧекЛиста` — пункты чек-листа (раздел, порядок, текст, обязательность);
- чек-лист — справочные данные, а не документ; доступен всем ДЛ без ACL;
- источник начального наполнения — `config/checklists/ДолжностнаяИнструкция.md`;
- предусмотреть версию чек-листа и хранение использованной версии в инструкции.

Правило одной инструкции на должность:

1. Ключ инструкции — `АИС_Должность`, не сотрудник.
2. На одну должность — одна действующая инструкция.
3. Несколько ДЛ на одной должности используют один и тот же документ.
4. Перед разработкой агент вызывает `get_job_description(position)`.
5. Если инструкция найдена — используется она; новая не создаётся.
6. Если инструкции нет:
   - агент получает чек-лист `get_checklist("РазработкаДолжностнойИнструкции")`;
   - готовит текст по пунктам чек-листа;
   - заполняет `АИС_Должность`, `АИС_ЧекЛист`, `АИС_ВерсияЧекЛиста`;
   - не заполняет поле сотрудника.
7. Заявка на найм проверяет наличие инструкции по каждой запрашиваемой должности, а не по каждому кандидату.
8. Если на должность уже есть инструкция, при найме второго и последующих ДЛ задача на разработку не создаётся.
9. Если инструкция обновляется, новая версия действует для всех ДЛ на должности; личные копии не создаются.
10. Серверная проверка уникальности:
    - при записи документа вида `Должностная инструкция` искать другую активную инструкцию по той же должности;
    - при наличии — отклонять запись с `duplicate_job_description`, кроме явной замены версии через штатную связь `Не действует в соответствии`;
    - найм и задачи используют только действующую инструкцию.

Миграция:

- существующий документ «Чек-лист общих требований к должностной инструкции (редакция 1)» переносится в `АИС_ЧекЛисты` и `АИС_ПунктыЧекЛиста`;
- `_seed_checklist` в симуляторе создаёт элемент справочника, а не документ;
- старый документ помечается как устаревший/недействующий после переноса;
- задачи, ссылавшиеся на документ, переводятся на `get_checklist`.

## 4. Обязательный порядок действий агента

1. Определить, нужны ли образец и/или НСИ.

3. При пустом результате — `search_internet(category=...)`.
4. Внешний образец сохранить через `save_external_example` вместе с вопросами, без вариантов ответов.
5. Получить ответы через `ask_example_changes`.
6. При недостающих/устаревших данных — выбрать адресата через `list_job_duties`, вызвать `create_information_request`, проверить доступ и согласовать отправку.
7. При разработке должностной инструкции:
   - вызвать `get_job_description(position)`;
   - если инструкция есть — использовать её и не создавать новую;
   - если нет — получить `get_checklist("РазработкаДолжностнойИнструкции")` и подготовить текст по пунктам.
8. Сформировать черновик через `create_draft`.
9. При необходимости задать `ask_decision`.
10. Вызвать `submit_draft_for_review`.
11. Обработать действие пользователя.
12. Зафиксировать результат и закрыть задачу.

## 5. Тесты и проверки

Simulator unit-тесты:

- `search_internet(example)` до пустого RAG → ошибка;
- после `search_example` с `empty` → разрешён;
- после непустого `search_example` → ошибка;
- аналогично для `knowledge`;
- `search_internet(materials)` в обычной задаче → ошибка;
- 0/8 вариантов вопроса → ошибка;
- свободный ввод не считается вариантом;
- рекомендуемый вариант стоит первым; для `single` он ровно один;
- для `multiple` все рекомендуемые варианты идут в начале списка;
- варианты ответов не сохраняются вместе с образцом и вопросами;
- `request_info` без адресата → ошибка;
- interaction store: создание, ответ, таймаут, атомарность;
- переходы черновика: `approve_send`, `rework`, `approve_referenced`, `reject_send` → `ask_decision`;
- шаблоны запроса: руководитель/подчинённый/смежник;
- доступ: смежник без распоряжения → отказ; с явным распоряжением → разрешено;
- `get_checklist` возвращает чек-лист с пунктами;
- инструкция по должности: два сотрудника на одной должности → одна инструкция, второго документа и второй задачи нет;
- попытка создать вторую активную инструкцию по той же должности → `duplicate_job_description`;
- инструкция без `АИС_ЧекЛист`/`АИС_ВерсияЧекЛиста` не проходит проверку готовности.

RAG-тесты:

- `scope=examples` возвращает образцы;
- `scope=knowledge` не возвращает `document_example`;
- дедупликация и повторная индексация;
- пустой результат без ошибки.

Интеграционные сценарии на stage2:

1. Пустой `search_example` → интернет → сохранение образца с вопросами → ответы → черновик → `approve_send` → входящий документ и задача у адресата.
2. `search_example` с результатом → интернет запрещён.
3. `rework`: замечания сохраняются, черновик возвращается, повторное согласование.
4. `reject_send`: черновик не отправлен, задан вопрос о судьбе.
5. `approve_referenced`: связанный документ утверждён без замечаний.
6. Смежник: ограниченный документ → отказ; с распоряжением общего начальника → разрешено.
7. `list_job_duties` доступен всем и возвращает полный перечень.
8. Чек-лист доступен всем; инструкция разрабатывается по его пунктам.
9. Два ДЛ на одной должности: создаётся одна инструкция, оба используют её; повторный найм не создаёт новую задачу.
10. Попытка создать личную инструкцию для сотрудника или вторую инструкцию на должность отклоняется.

Проверки:

- `ruff`, `pytest` в симуляторе;
- `python3 scripts/checks/no_hardcoded_parameters.py`, `no_stubs.py` в расширении;
- сборка и загрузка расширения в stage2;
- `rag-service` unit-тесты;
- golden set: добавить кейсы `examples` и fallback, не ломать `documents`.

## 7. Риски и ограничения

- Пустой корпус образцов приведёт к частому интернет-фолбэку; нужен стартовый набор образцов.
- Публичные обязанности сейчас берутся из `АИС_ДолжностныеОбязанности` (краткие записи из конфигурации сценария), а не из полных текстов должностных инструкций.
- Человек в цикле блокирует `process`; без открытого UI или с истёкшим таймаутом задача остаётся открытой.
- Контроль ограниченных сведений надёжен только для явно указанных `source_document_ids`; вставленный вручную текст сервер классифицировать не может.
- Качество вопросов, сгенерированных моделью, требует golden-кейсов и ручной проверки.
- `HTTPService.АИС_Симулятор` остаётся тестовым адаптером; новые маршруты не являются продуктовым API.
- Разделение `examples` и `knowledge` требует поддержки двух коллекций и бэкапа обеих.
- Разбор markdown-чек-листа на пункты может быть неполным; полный текст хранится как источник истины, пункты — для навигации и проверки.
- Автоматическая проверка полноты инструкции по пунктам чек-листа ограничена текстовым анализом; на первом этапе обязательна ручная проверка при согласовании.
- В существующих данных могут быть дубли должностных инструкций по одной должности; миграция должна оставить одну действующую и связать остальные связью «Не действует в соответствии».

## 9. Принятые уточнения

- Каноническое имя — `search_knowledge_base`.
- Свободный ввод не входит в лимит 7 вариантов.
- Модель обязана выбрать рекомендуемый вариант и поставить его первым; для одиночного выбора рекомендация ровно одна.
- Варианты ответов не сохраняются в справочнике образцов и вопросов: они формируются при задании вопроса.
- «Нет результатов» = `status = "empty"`; порог релевантности задаёт сервер RAG.
- Для локального образца без вопросов задаётся один свободный вопрос без выдуманных вариантов.
- Вопросы пользователю и запросы другому ДЛ — разные процессы.
- `search_internet` получает обязательный `category`; `materials` используется только для наполнения корпуса.
- Черновик хранится отдельно от `ВнутренниеДокументы`; реальный документ создаётся при `approve_send`.
- Свежесть НСИ определяется только явными метаданными; домысливать устаревание запрещено.
- Для смежников разрешение на обмен оформляется структурированным регистром, а не разбором текста распоряжения.
- Чек-лист — справочник, а не документ; пока в нём один чек-лист «Разработка новой должностной инструкции».
- Должностная инструкция разрабатывается на должность, а не на сотрудника; несколько ДЛ на одной должности используют один общий документ.
