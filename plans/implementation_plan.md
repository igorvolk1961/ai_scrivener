# План реализации ai_scrivener как расширения 1С:Документооборот 2.1.38.11

## 1. Цель и границы

Создать расширение `.cfe` к 1С:Документооборот 2.1.38.11 с ИИ-помощником должностного лица и внешним stateless RAG-сервисом:

- 1С:Документооборот хранит доменные данные, документы, задачи, пользователей и права.
- Расширение добавляет ИИ-оркестрацию, состояния, плейсхолдеры, аудит и интерфейс помощника.
- 1С вызывает DeepSeek для генерации и GigaChat Embeddings через RAG-сервис.
- Qdrant хранит векторы корпуса знаний; шаблоны и должностные обязанности индексируются после MVP.
- **MVP (пересмотрен 2026-11-05):** однократный вопрос пользователя по базе знаний организации → RAG-поиск → ответ LLM с цитатами из документов.
- Шаблоны, плейсхолдеры и генерация документов перенесены из MVP в post-MVP: качество формируемых шаблонов пока неудовлетворительное.
- MVP не привязан к отрасли или шляпному производству: корпус и golden set формируются по фактическим типам документов организации.

Вне MVP: многошаговый чат и история диалогов, tool-calling, выбор и заполнение шаблонов, генерация DOCX, электронная подпись, email/телефония, промышленный HA, индексация конфиденциальных документов, мобильный клиент, коммерческая эксплуатация демо-стенда.

### 1.1. Пересмотренный MVP: вопрос по базе знаний

| Входит в MVP | Вне MVP |
|---|---|
| Диалоговое окно «Спросить по базе знаний» в расширении | История диалогов и продолжение старых диалогов |
| Один вопрос — один ответ, без накопления контекста | Многошаговый чат, tool-calling, агентный цикл |
| RAG-поиск по корпусу знаний | Выбор шаблона и заполнение плейсхолдеров |
| Ответ LLM только по найденным фрагментам | Генерация DOCX и создание проекта документа |
| Ссылки на источник, раздел/пункт, страницу | Подписание и документный маршрут |
| Ответ «не найдено» при недостатке контекста | Внешние источники, лист ожидания, эскалация |
| Аудит вопроса, ответа и источников | ACL, если база знаний пока доступна всем |
| Golden set по типам документов и eval | Мастер шаблонов и вычитка как обязательные функции MVP |

### 1.2. Контур агента-имитатора ДЛ (2026-11-08)

Требования FR-047–FR-057 и NFR-033–NFR-034 добавляют отдельный контур для
агента-имитатора должностного лица в `ai-scrivener-enterprise-sim`:

- RAG-поиск образцов (`search_example`) и НСИ (`search_knowledge_base`) с
  обязательным интернет-фолбэком только после пустого RAG-результата;
- вопросы пользователю об изменениях образца и о решении (1–7 вариантов,
  свободный ввод, рекомендуемые варианты первыми);
- сохранение внешних образцов с вопросами, но без вариантов ответов;
- черновики, четыре действия согласования и запросы информации другому ДЛ;
- проверка доступа и публичные должностные обязанности;
- справочник чек-листов и одна общая должностная инструкция на должность.

Этот контур не отменяет ограничения MVP из §1.1 для продуктового UI 1С; он
развивает симулятор и тестовый HTTP-адаптер. Детали и порядок этапов —
`plans/2026-11-08-agent-rag-questions-drafts-access.md`.

### 2.1. Почему не RAG для всех значений

Qdrant возвращает текстовые фрагменты, а не транзакционные значения полей. Точные значения (`номер`, `дата`, `срок`, `адресат`) берутся из 1С. RAG используется для выбора шаблона, нормативного контекста и позже — для извлечения значений из неструктурированных текстов с обязательной проверкой ДЛ.

### 2.2. Инженерные правила

- Источник истины требований — `docs/requirements/requirements.yaml`; Markdown-документы и матрица генерируются.
- Все настраиваемые числовые параметры хранятся в `config/parameters.yaml` и проверяются по `config/parameters.schema.json`.
- Новые объекты расширения получают префикс `АИС_`; штатные объекты Документооборота не дублируются.
- Перед реализацией metadata выполняется инвентаризация базы: фактические имена, реквизиты, режим совместимости.
- В коде запрещены хардкод числовых параметров, `TODO`, `FIXME`, `NotImplementedError` и заглушки. Заглушка допускается только в крайнем случае, по согласованию с пользователем и с обязательной записью в `TODO.md` (`guides/development.md` §4) — без ссылки на существующую запись чекер блокирует коммит.
- Код покрывается поведенческими тестами; внешние сервисы изолируются mock/respx/локальным Qdrant.
- Пре-коммит запускает общие проверки, ruff, ruff-format, mypy, yamllint, валидацию конфига, проверку трассируемости, запрет заглушек и хардкода, BSL Language Server и быстрые тесты.
- Новые требования добавляются только после согласования и со статусом `approval: proposed`.
- Базовая конфигурация, `.dt`, `.cf`, `.cfe` и рабочая база в репозиторий не попадают.

```
        │

  │ АИС_ОркестраторЗадач                               │
  │ АИС_РазрешительПлейсхолдеров                       │
  │ АИС_ГенераторДокументов                            │
  │ АИС_РаботаСЛистомОжидания                          │
  │ АИС_АудитДействийИИ                                │
  │ АИС_ОтветПоБазеЗнаний ────────────▶ DeepSeek API    │
  │ АИС_ИнтеграцияСLLM ───────────────▶ DeepSeek API    │
  │ АИС_ИнтеграцияСRAG ───────────────▶ RAG-сервис      │
  └────────────────────────────────────────────────────┘
                                         │
                                         ▼
                                   RAG-сервис (FastAPI)
                                     ├── GigaChat OAuth + Embeddings
                                     └── Qdrant
```

Поток MVP Q&A:

1. ДЛ открывает диалоговое окно и задаёт вопрос.
2. `АИС_ИнтеграцияСRAG.Поиск` вызывает `/v1/retrieve` с фильтрами по доступным типам/статусам документов.
3. RAG возвращает top-k фрагментов с `source_id`, `title`, `section_path`, `clause`, `page_start/page_end`.
4. `АИС_ОтветПоБазеЗнаний` собирает контекст, вызывает DeepSeek с промптом `ОтветПоБазеЗнаний`, получает `{found, answer, citations}`.
5. Расширение проверяет, что все citations входят в найденные `source_id`/пункты; при недостатке контекста показывает «в базе знаний не найдено».
6. Вопрос, ответ, citations, длительность и ошибки пишутся в `АИС_ИсторияДействийИИ`.

Потоки post-MVP:

1. Регистрация входящего документа в Документообороте создаёт задачу расширения в состоянии `Инициация` без вызова LLM в транзакции документа.
2. Оркестратор выбирает шаблон: RAG top-k → LLM `ВыборШаблонаДокумента` → валидация ID и confidence.
3. Разрешитель заполняет плейсхолдеры: прямое поле, утверждённый запрос к БД, запрос другому ДЛ, расчётный сервис, внешний API, RAG-контекст.
4. Генератор формирует текст и создаёт проект исходящего документа в штатном `ИсходящийДокумент`.
5. ДЛ проверяет, редактирует и подписывает; задача завершается.
6. Все шаги, промпты, ответы, RAG-кандидаты и переходы состояний пишутся в аудит расширения.

Развёртывание: 1С-сервер + PostgreSQL; RAG-сервис и Qdrant — Docker Compose на том же или отдельном хосте; Qdrant не публикуется наружу; RAG-сервис за TLS/reverse proxy и с service-token.

## 5. Метаданные расширения

Актуальная дедуплицированная модель описана в `docs/data-model.md`. Ниже — краткая карта и правила.

### 5.1. Принцип переиспользования

Пользовательские сущности остаются штатными объектами Документооборота. Расширение добавляет только ИИ-специфичные данные и не создаёт параллельные справочники, документы и задачи.

| Штатный объект | Использование |
|---|---|
| `Справочник.Пользователи`, `ФизическиеЛица` | ДЛ, ФИО, контакты |
| `Справочник.Должности`, `СтруктураПредприятия` | должности и оргструктура |
| `InformationRegisters.СведенияОПользователяхДокументооборот` | постоянная должность и подразделение пользователя на дату (периодический регистр) |
| `Catalogs.ДелегированиеПрав` | кто кого замещает на период — вместе с предыдущим даёт объединённый набор действующих должностей |
| `Справочник.ВходящиеДокументы` | входящий триггер |
| `Справочник.ИсходящиеДокументы` | проект и результат |
| `Справочник.ВнутренниеДокументы` + `ВидыВнутреннихДокументов` | распоряжения, доклады, доклад о срыве сроков |
| `Задача.ЗадачаИсполнителя` | все пользовательские задачи, включая запросы к ДЛ |
| `БизнесПроцессы` (`Согласование`, `Утверждение`, `Исполнение`, `Поручение` и др.) | согласование, утверждение и исполнение |
| `Справочник.Файлы`, `ВерсииФайлов`, `ТомаХраненияФайлов` | файлы и версии |
| `ВидыВходящих/Исходящих/ВнутреннихДокументов` | типы документов |
| `ШаблоныВходящих/Исходящих/ВнутреннихДокументов` | шаблоны; расширяются ТЧ `АИС_Плейсхолдеры` |
| `ВидыКонтактнойИнформации`, `СпособыДоставки` | каналы связи; отдельный `АИС_КаналыСвязи` не создаётся |
| `Справочник.ИсточникиДанных` | источники; расширяется реквизитами/ТЧ для URL, схемы и таймаута |
| `Справочник.ШаблоныТекстов` | текст промптов; ИИ-параметры хранятся отдельно |
| `ВидыБизнесСобытий`, `ДетекторыБизнесСобытий` | детектирование триггеров, если покрывает сценарии |
| `ИсторияСобытийЗадач`, `ИсторияВыполненияЗадач`, `РезультатыВыполненияПроцессовИЗадач` | история и результаты пользовательских задач |
| `РегламентныеЗадания` | запуск расписаний и фоновых обработок |

Новые объекты создаются только там, где аналога нет:

- перечисления `АИС_СостоянияЗадач` (состояния ИИ-оркестрации), `АИС_СпособыЗаполнения`;
- справочники `АИС_ДолжностныеОбязанности`, `АИС_ТипыДействий`, `АИС_ПромптПараметры`, `АИС_РазделыДокумента`, `АИС_ЛистОжидания`, `АИС_РасписаниеТриггеров` (справочники, а не регистры — у регистра сведений нет ссылочного типа, а на запись в каждом из них нужно ссылаться извне);
- справочник `АИС_ТипыТриггеров` — только если `ВидыБизнесСобытий`/`ДетекторыБизнесСобытий` не покрывают нужные события;
- регистры `АИС_КонтекстЗадачИИ`, `АИС_СостоянияПлейсхолдеров`, `АИС_ИсторияДействийИИ`, `АИС_НормативыИИ` (настоящий композитный ключ или журнал — регистр обоснован);
- новые документы не создаются: все документные сущности выражаются штатными справочниками/документами и видами.

Правило: если объект базы отсутствует или его структура не подходит, создаётся `АИС_*`, но не дублируется существующий объект с тем же смыслом.

Фактическая база — ПРОФ 2.1.38.11. В ней нет `Справочник.Сотрудники` и `Справочник.Подразделения`: сотрудник представлен `Пользователи` + `ФизическиеЛица`, оргструктура — `СтруктураПредприятия`. Документы в 2.1 — это справочники (`ВходящиеДокументы`, `ИсходящиеДокументы`, `ВнутренниеДокументы`), а задачи — `Задача.ЗадачаИсполнителя`.

### 5.2. Перечисления

`АИС_СостоянияЗадач` — только состояния ИИ-оркестрации: `Инициация`, `ПоискШаблона`, `РазрешениеПлейсхолдеров`, `Ожидание`, `Генерация`, `ВерификацияДЛ`, `Завершена`, `Эскалация`.

`АИС_СпособыЗаполнения` — `ПрямоеПоле`, `ЗапросВБД`, `ЗапросКДЛ`, `РешениеДЛ`, `РасчетныйСервис`, `ВнешнийAPI`, `RAGКонтекст`, `РучнойВвод`.

`АИС_СостоянияРазделов` — `НеНачат`, `Черновик`, `НаПодтверждении`, `Подтвержден`, `Устарел`, `Отклонен`.

`АИС_СостоянияШаблонов` — `Черновик`, `НаПроверке`, `Утвержден`, `Устарел`, `Отклонен`.

`АИС_РекомендацииПоШаблонам` — `ОбновитьСуществующий`, `Объединить`, `СоздатьНовый`, `РучноеРешение`.

`АИС_РежимыПроверки` — `Быстрая`, `Глубокая`.

`АИС_ТипыЗамечаний` — `Орфография`, `Пунктуация`, `Грамматика`, `Смысл`, `Логика`, `Стиль`, `Оформление`.

`АИС_ВажностиЗамечаний` — `Низкая`, `Средняя`, `Высокая`, `Критическая`.

`АИС_ВидыПлейсхолдеров` — `Значение`, `Список`, `Раздел`.

`АИС_СтатусыПлейсхолдеров` — `ТребуетсяЗапрос`, `Запрошен`, `Ожидает`, `Заполнен`, `НеМожетБытьЗаполнен`.

`АИС_ТипыЗапросовЛистаОжидания` — `Значение`, `ПодтверждениеРаздела`.

`АИС_ТипыИсточниковОжидания` — `ДЛ`, `ВнешнийСервис`.

`АИС_СостоянияЗапросовОжидания` — `Отправлен`, `ПолученОтвет`, `СрокИстек`.

Состояние пользовательской задачи остаётся в `Задача.ЗадачаИсполнителя`; состояние ИИ хранится отдельно в `АИС_КонтекстЗадачИИ` и не подменяет состояние задачи.

### 5.3. Справочники

| Объект | Назначение |
|---|---|
| `АИС_ДолжностныеОбязанности` | обязанности по должности: текст, версия, дата утверждения, пара (`ТипТриггера`, `ТипДействия`), опциональная `Характеристика` (`CatalogRef.ВидыВходящихДокументов` — базовый объём, расширяется типом при появлении второго случая, не заранее) для выбора наиболее специфичной обязанности, опциональный `ТребуемыйВидДокумента` (`CatalogRef.ВидыИсходящихДокументов` / `CatalogRef.ВидыВнутреннихДокументов` — составной тип прямо на реквизите) для сужения выбора шаблона |
| `АИС_ТипыДействий` | классификация ИИ-действий: сформировать документ, запросить данные, эскалировать, подготовить доклад; реквизит `ТипОбъекта` (штатный `EnumRef.ТипыОбъектов`) связывает тип действия со справочником шаблонов для фильтрации кандидатов; новое перечисление не создаётся |
| `АИС_ПромптПараметры` | JSON-схема, модель, температура, максимум токенов, версия; текст промпта — в `ШаблоныТекстов` |
| `АИС_ТипыТриггеров` | только если бизнес-события не покрывают триггеры; иначе используется `ВидыБизнесСобытий` |
| `АИС_РазделыДокумента` | справочник, подчинён `ИсходящиеДокументы`; версия раздела — отдельный элемент (не регистр: у регистра сведений нет ссылочного типа, а ссылка на раздел нужна в других объектах) |
| `АИС_ЛистОжидания` | справочник (та же причина): `Задача`, `Плейсхолдер`, `ТипЗапроса`, `ТипИсточника`, `Адресат`, `Текст`, `ДатаОтправки`, `СрокОжидания`, `Состояние`, `Ответ`, `ДатаОтвета`, `ЧислоПопыток`, `ОжидаемаяВерсия`, `ОжидаемыйХеш`, `СсылкаНаРаздел` |
| `АИС_РасписаниеТриггеров` | справочник (та же причина — измерение было бы искусственным `ИдентификаторРасписания`): `ТипТриггера`, `ДЛ`, `Должность`, `Расписание`, `СледующийЗапуск`, `Активность`, `Распоряжение` (опционально — ссылка на породившее распоряжение) |

`АИС_ИсточникиДанных` и `АИС_КаналыСвязи` не создаются: используются штатные `ИсточникиДанных` и `ВидыКонтактнойИнформации`/`СпособыДоставки`.

`АИС_ШаблоныДокументов` не создаётся: используются три штатных справочника шаблонов. Если их структура не подходит, новый справочник допускается только для ИИ-специфичных шаблонов и не заменяет штатные.

Штатные шаблоны расширяются ТЧ `АИС_Плейсхолдеры`. Канонический состав полей — `docs/data-model.md` §14.1; в плане он не дублируется.

Особенности, важные для реализации:

- `Вид = Список`: значение хранится JSON-массивом строк в `АИС_СостоянияПлейсхолдеров.Значение`; порядок элементов задаёт порядок в документе.
- `Вид = Раздел`: значение хранится не строкой, а ссылкой `СсылкаНаРаздел` на `АИС_РазделыДокумента`.
- `ИсточникДанных` — ссылка на `Справочник.ИсточникиДанных`; `СпособЗаполнения` — значение `EnumRef.АИС_СпособыЗаполнения`. Это разные поля.
- `ПравилоАвтозаполнения` — ссылка на базовое правило автозаполнения; `ШаблонЗапроса` — утверждённый запрос для `ЗапросВБД`. Это разные поля, не дубли.

Создание шаблонов автоматизируется мастером шаблонов (`docs/template-factory.md`): импорт DOCX/текста, AI-анализ, проверка человеком, генерация `ПравилаАвтозаполненияФайлов` и ТЧ `АИС_Плейсхолдеры`, тестовое заполнение, публикация и индексация.

### 5.4. Документы

Новые документы не создаются.

- Входящий документ — `Справочник.ВходящиеДокументы`.
- Проект и результат — `Справочник.ИсходящиеДокументы`.
- Распоряжения, доклады и доклад о срыве сроков — `Справочник.ВнутренниеДокументы` + соответствующий `ВидВнутреннегоДокумента`.
- Запрос к ДЛ — `Задача.ЗадачаИсполнителя` с состоянием ожидания ответа; метаданные ожидания — в `АИС_ЛистОжидания`.
- Результат внешнего запроса — результат базовой задачи и запись в истории.
- Результат внешнего действия — результат базовой задачи или `ВнутреннийДокумент`, если нужен жизненный цикл документа.
- Расписание триггеров — справочник `АИС_РасписаниеТриггеров` + регламентное задание (Этап 4–5), без нового документа.

### 5.6. Определяемые типы

`АИС_ИсточникТриггера` — входящий документ, распоряжение, бизнес-событие, расписание, внешний запрос.

`АИС_РезультатЗадачи` — исходящий документ, внутренний документ, доклад, отсутствие результата.

`АИС_АдресатЗапроса` — `Пользователи`, `Должности`, `СтруктураПредприятия`; отдельный справочник адресатов не создаётся.

Поля `Характеристика` и `ТребуемыйВидДокумента` у `АИС_ДолжностныеОбязанности` (§5.3) типизируются прямо на реквизите (составной тип инлайн, без отдельного именованного определяемого типа) — у каждого ровно один потребитель, заводить именованный объект для него избыточно.

### 5.7. Константы и секреты

Константы: URL и модель DeepSeek, таймаут, максимум токенов, температуры, URL RAG-сервиса, URL/scope GigaChat, модель эмбеддингов, флаги отладки, даты последней индексации.

В безопасном хранилище 1С: API-ключ DeepSeek, service-token RAG, client_secret GigaChat. В коде и логах секретов нет.

### 5.8. Роли и доступ

- `АИС_АдминистраторСистемы` — справочники расширения, настройки, статистика; не видит содержание задач.
- `АИС_ДолжностноеЛицо` — только свои базовые задачи и связанный ИИ-контекст.
- `АИС_ВышестоящееДолжностноеЛицо` — свои задачи и доклады, адресованные ему.
- `АИС_Аудитор` — чтение аудита и отчётов без изменения.
- `АИС_СервисныйПользователь` — права для регламентных заданий и HTTP-сервисов.

Правила:

- В `УстановкаПараметровСеанса` определяется `ТекущееДЛ` через `Пользователи` (при необходимости — `Пользователи.ФизЛицо`).
- Для пользовательских задач используется штатная модель прав `Задача.ЗадачаИсполнителя`; расширение не дублирует RLS базовых задач.
- RLS на новых `АИС_*` объектах выполняется через ссылку на базовую задачу.
- Обязательные негативные тесты: ДЛ не видит чужую задачу, администратор не видит задачи, аудитор не может изменить запись.

### 5.9. Ограничения расширения

- Нельзя изменять состав измерений и ресурсов базовых регистров; для новых измерений создаётся регистр `АИС_*`.
- К базовым объектам можно добавлять реквизиты, табличные части, формы и команды в пределах возможностей расширения.
- Режим совместимости расширения равен режиму совместимости базы (8.3.27).
- Расширение не требует изменения базовой конфигурации; применение и снятие `.cfe` проверяются на копии демо-базы.

### 5.10. Мастер шаблонов

Ключевой элемент проекта: шаблоны не должны создаваться вручную по одному правилу. Подробная модель — `docs/template-factory.md`.

Мастер:

- принимает DOCX/текст или описание словами;
- извлекает структуру: разделы, списки, таблицы, повторяющиеся термины;
- предлагает плейсхолдеры, типы, источники, падежи;
- показывает таблицу на проверку человеку;
- даёт принять/отклонить каждый плейсхолдер, добавить/удалить его, изменить тип, источник, обязательность, падеж и формат;
- поддерживает отказ от всей ИИ-разметки и ручной режим;
- сравнивает кандидата с существующими шаблонами, показывает diff и рекомендацию;
- генерирует `ПравилаАвтозаполненияФайлов` и ТЧ `АИС_Плейсхолдеры`;
- выполняет тестовое заполнение;
- публикует шаблон только после подтверждения;
- переводит старую версию в `Устарел` и переиндексирует RAG.

Объекты:

- `АИС_МастерШаблонов` — обработка;
- `АИС_ГенераторПравилШаблона`, `АИС_ПроверкаШаблона`, `АИС_СравнениеШаблонов` — общие модули;
- ТЧ `АИС_Плейсхолдеры`, `АИС_СтатусыШаблонов`, `АИС_СравненияШаблонов`;
- `АИС_СостоянияШаблонов`, `АИС_РекомендацииПоШаблонам`;
- промпты `АнализШаблона`, `ПредложитьИсточник`, `ПроверитьШаблон`, `СравнитьШаблон`, `ТестовоеЗаполнение`.

Сравнение: текст + плейсхолдеры + структура + метаданные; веса и пороги в `config/parameters.yaml`. Высокая похожесть → предложить обновление, средняя → объединение, низкая → новый шаблон; окончательное решение принимает пользователь.

Post-MVP объём мастера: один тип исходящего документа, DOCX, скалярные плейсхолдеры, один простой список, один раздел, ручное подтверждение и редактирование, сравнение с одним наиболее похожим шаблоном, автогенерация правил.

### 5.11. Вычитка документов

Двухуровневая проверка проекта документа. Подробно — `docs/proofreading.md`.

- **Быстрая** — без LLM: плейсхолдеры, обязательные разделы, даты, суммы, номера, ссылки, формат, повторы, склонения.
- **Глубокая** — LLM: орфография, пунктуация, грамматика, стиль, смысл, логика, противоречия.

Правила:

- быстрая проверка автоматически после генерации и перед подписью;
- глубокая — по кнопке и с показом остатка квоты;
- пользователь видит страницы, не токены;
- быстрая проверка квоту не расходует;
- замечание содержит цитату, которая обязана существовать в тексте;
- замечания не применяются автоматически;
- принятые замечания применяются детерминированно и аудируются;
- локальная LLM предпочтительна для конфиденциальных документов.

Объекты:

- `АИС_ПроверкиДокументов`, `АИС_ЗамечанияПроверки`, `АИС_ЛимитыВычитки`;
- `АИС_РежимыПроверки`, `АИС_ТипыЗамечаний`, `АИС_ВажностиЗамечаний`;
- `АИС_ПроверкаДокумента` — общий модуль;
- `АИС_ПанельЗамечаний` — обработка.

Post-MVP объём: быстрая проверка, LLM-грамматика/пунктуация/стиль по кнопке, accept/reject, лимит страниц в день, локальная LLM, аудит.

## 6. Состояния и сценарии

Процессные диаграммы AS-IS и TO-BE — в `docs/process-diagrams.md`.

### 6.1. Состояния задачи

`Инициация` → `ПоискШаблона` → `РазрешениеПлейсхолдеров` → (`Ожидание` ↔ `РазрешениеПлейсхолдеров`) → `Генерация` → `ВерификацияДЛ` → `Завершена`.

В любое состояние (кроме `Завершена`) может быть выполнена `Эскалация`.

Правила:

- Переходы только через `АИС_ОркестраторЗадач.ПеревестиСостояние` с проверкой допустимости, версии и записью в аудит.
- `Ожидание` снимается ответом из листа ожидания, истечением срока или ручным вмешательством.
- `Завершена` только после подписи/ручного завершения ДЛ; автоматического завершения нет.
- При ошибке LLM/сети задача остаётся в текущем состоянии; повтор по таймеру или вручную.

#### Таблица допустимых переходов

Формальная матрица для `АИС_ОркестраторЗадач.ПеревестиСостояние`: строка — текущее состояние, столбцы — допустимое следующее состояние и инициатор перехода. Переход, не указанный в таблице, отклоняется с ошибкой и записью в аудит.

| Из | В | Инициатор |
|---|---|---|
| `Инициация` | `ПоискШаблона` | регламентное задание `АИС_ОркестрацияАктивныхЗадач` |
| `ПоискШаблона` | `РазрешениеПлейсхолдеров` | регламентное задание (после ответа RAG/LLM или ручного выбора шаблона) |
| `ПоискШаблона` | `Эскалация` | регламентное задание (RAG и ручной выбор недоступны) |
| `РазрешениеПлейсхолдеров` | `Ожидание` | регламентное задание (создан запрос в `АИС_ЛистОжидания`) |
| `РазрешениеПлейсхолдеров` | `Генерация` | регламентное задание (все обязательные плейсхолдеры заполнены) |
| `РазрешениеПлейсхолдеров` | `Эскалация` | регламентное задание (превышены глубина/число запросов) |
| `Ожидание` | `РазрешениеПлейсхолдеров` | внешний ответ (лист ожидания) или ручное вмешательство |
| `Ожидание` | `Эскалация` | `АИС_ОбработкаЛистаОжидания` (срок истёк) |
| `Генерация` | `ВерификацияДЛ` | регламентное задание (проект документа создан) |
| `Генерация` | `Эскалация` | регламентное задание (ошибка генерации после исчерпания попыток) |
| `ВерификацияДЛ` | `Завершена` | ДЛ (подпись/ручное завершение) |
| `ВерификацияДЛ` | `Генерация` | ДЛ (команда «Сгенерировать заново») |
| любое, кроме `Завершена` | `Эскалация` | регламентное задание `АИС_ПроверкаСроковЗадач` (истёк `СрокИсполнения` базовой задачи) или ручное вмешательство |
| `Эскалация` | `РазрешениеПлейсхолдеров`/`Ожидание` | ручное вмешательство (возобновление после эскалации) |

Правило конкуренции: любой переход требует совпадения `Версия` в `АИС_КонтекстЗадачИИ` с версией, прочитанной инициатором; при несовпадении переход отклоняется, инициатор перечитывает запись. Обязательные тестовые сценарии конкуренции для Этапа 7:

- два регламентных задания одновременно выбирают одну и ту же задачу из пакета — только одно выполняет переход;
- внешний ответ приходит в `АИС_ЛистОжидания` в момент, когда `АИС_ПроверкаСроковЗадач` переводит ту же задачу в `Эскалация` — порядок обработки не создаёт двух противоречащих переходов из одного состояния;
- ручное вмешательство (`Возобновить`/`Эскалация`/`Завершить вручную`) выполняется одновременно с регламентным заданием — переход, применённый позже по версии, отклоняется, а не перезаписывает более новый.

### 6.2. MVP: однократный вопрос по базе знаний

1. ДЛ открывает окно «Спросить по базе знаний» из подсистемы «АИС: Сервис».
2. Вводит вопрос; история предыдущих вопросов не передаётся и не сохраняется как контекст.
3. Расширение вызывает RAG `/v1/retrieve` с `top_k`, `candidate_k`, фильтрами по доступным типам/статусам документов; при необходимости передаёт `include_parent=true`.
4. RAG возвращает сгруппированные по источникам фрагменты с `source_id`, `title`, `doc_type`, `section_path`, `clause`, `page_start/page_end`, `text`.
5. `АИС_ОтветПоБазеЗнаний` собирает контекст с маркерами источников `[S1]`, `[S2]`, … и вызывает DeepSeek с промптом `ОтветПоБазеЗнаний`.
6. LLM возвращает JSON `{found, answer, citations}`; citations должны ссылаться только на переданные `source_id` и существующие пункты.
7. Если `found=false`, citations пусты или контекста недостаточно — показывается «в базе знаний не найдено»; LLM не добавляет ответ от себя.
8. Ответ показывается вместе со списком источников: документ, вид, раздел/пункт, страница. Пользователь может открыть исходный материал.
9. Вопрос, ответ, citations, длительность и ошибки пишутся в `АИС_ИсторияДействийИИ`.
10. Повторный вопрос создаёт новый независимый запрос; контекст прошлого ответа не используется.

**Ограничения MVP:** без истории, без tool-calling, без выбора шаблона, без генерации документа, без ACL сверх текущих прав на материалы.

### 6.2.1. Post-MVP: документный сценарий

1. ДЛ регистрирует и проводит `Справочник.ВходящиеДокументы`.
2. При проведении создаётся задача расширения с ключом идемпотентности; LLM не вызывается. Исполнитель задачи определяется детерминированно по `Виду` входящего документа через наиболее специфичную `АИС_ДолжностныеОбязанности` → её должность-владелец → действующий исполнитель этой должности (`docs/raw_specification.md` §4.1.5); без определённого исполнителя задача не создаётся.
3. Регламентное задание `АИС_ОркестрацияАктивныхЗадач` переводит задачу в `ПоискШаблона`.
4. Кандидаты шаблона сужаются детерминированно до запуска RAG: по `ТипДействия` выбирается нужный справочник шаблонов (входящих/исходящих/внутренних), а если найденная обязанность задаёт требуемый вид документа — кандидаты дополнительно ограничиваются этим видом. RAG-сервис возвращает top-10 шаблонов внутри этого отфильтрованного набора (не всего корпуса); DeepSeek выбирает один и возвращает JSON.
5. Проверяется, что ID входит в кандидаты, confidence выше порога; иначе — ручной выбор.
6. Создаются записи `АИС_СостоянияПлейсхолдеров`; для каждого плейсхолдера выполняется разрешение.
7. После заполнения всех обязательных плейсхолдеров — `Генерация`.
8. Детерминированная подстановка значений; при необходимости DeepSeek улучшает текст. Если LLM вернул текст без данных — используется детерминированный вариант.
9. Создаётся `Справочник.ИсходящиеДокументы` со статусом `Проект`; задача → `ВерификацияДЛ`.
10. ДЛ редактирует и подписывает; статус `Подписан`, задача → `Завершена`.
11. Все вызовы и переходы видны в `АИС_ЖурналЗадачи`.

### 6.3. Post-MVP: разрешение плейсхолдеров

- Парсер: regex `\{\{\s*([A-Za-zА-Яа-я0-9_]+)\s*\}\}`; синхронизация с ТЧ шаблона; ошибки при дублях, неизвестных именах, лишних описаниях.
- Лимиты: глубина 5, число запросов на задачу 50; при превышении — `Эскалация`.
- `ПрямоеПоле`: значение из источника триггера без LLM.
- `ЗапросВБД`: LLM выбирает утверждённый шаблон запроса и заполняет только параметры; параметры валидируются по именам и типам. Результат — 0 или >1 строки: плейсхолдер `НеМожетБытьЗаполнен`, ручное решение/эскалация.
- `ЗапросКДЛ`: создать базовую `Задача.ЗадачаИсполнителя` (если её ещё нет) и запись `АИС_ЛистОжидания`, плейсхолдер → `Ожидает`, ИИ-состояние → `Ожидание`.
- `РешениеДЛ`: показать ДЛ прецеденты (RAG top-k по похожим решениям) без автозаполнения; ответ — текст 1–2 предложения, при необходимости — развёрнутый `Раздел`. Срок ожидания настраивается отдельно; его истечение создаёт напоминание, а не эскалацию. Эскалация возможна только при истечении штатного `СрокИсполнения` задачи.
- `РасчетныйСервис`: рекурсивно разрешить аргументы, вызвать HTTP-сервис, проверить JSON-схему.
- `ВнешнийAPI`: запрос по схеме источника, таймаут, валидация ответа.
- `RAGКонтекст`: только для свободного текста; LLM извлекает значение с цитатой и confidence; ниже порога — ручной ввод. В документный MVP не включать.
- `РучнойВвод`: плейсхолдер ждёт ДЛ.

#### Параллелизм разрешения плейсхолдеров

В документном сценарии post-MVP плейсхолдеры одной задачи разрешаются последовательно; параллелизм допускается на уровне задач — несколько фоновых заданий обрабатывают разные задачи одновременно.

Причины последовательного разрешения:

- независимые плейсхолдеры могут зависеть друг от друга через параметры запросов и аргументы расчётных сервисов;
- общие счётчики задачи (`глубина`, `число запросов`) и переходы состояния требуют атомарного обновления;
- несколько одновременных запросов к DeepSeek/GigaChat проще уложить в rate limit;
- проще обеспечить воспроизводимый аудит и обработку ошибок.

Параллельное разрешение внутри задачи добавляется после первого релиза документного сценария:

- строится граф зависимостей плейсхолдеров; выполняются топологические слои;
- параллелятся только независимые плейсхолдеры типов `ПрямоеПоле`, `ЗапросВБД`, `РасчетныйСервис`, `ВнешнийAPI`;
- `ЗапросКДЛ` и `РучнойВвод` не блокируют другие плейсхолдеры, но переводят задачу в `Ожидание`;
- ограничение параллелизма — 2–4 операции на задачу, настраивается;
- записи `АИС_СостоянияПлейсхолдеров` обновляются независимо, счётчики задачи — атомарно, с блокировкой/версией;
- перед `Генерация` — барьер: ждём завершения всех веток и собираем ошибки;
- для 1С используется пул фоновых заданий, а не отдельное задание на каждый плейсхолдер.

### 6.4. Post-MVP: лист ожидания и эскалация

- `АИС_ОбработкаЛистаОжидания` каждую минуту: `Отправлен` + срок истёк → `СрокИстек` + триггер `ИстечениеСрокаОжидания`.
- Ответ по базовой задаче: найти запись `АИС_ЛистОжидания` по ID, проверить состояние, заполнить результат базовой задачи и историю, заполнить плейсхолдер, возобновить `АИС_КонтекстЗадачИИ`; при необходимости создать дочернюю базовую задачу для трассировки.
- `АИС_ПроверкаСроковЗадач` каждую минуту: задачи не в `Завершена` с истёкшим сроком → эскалация.
- Эскалация: собрать таймлайн, вызвать `АнализСрываСроков`, создать `ВнутреннийДокумент` с видом «Доклад о срыве сроков» со статусом `Проект`. Доклад подтверждается вышестоящим ДЛ или исполнителем (`docs/design-decisions.md` §14) **перед** фактической отправкой — автоматической отправки без подтверждения нет. После подтверждения — адресат вышестоящая должность, копия исполнитель; ИИ-состояние → `Эскалация`. При сбое LLM создать доклад с детерминированным таймлайном и пометкой «причина требует уточнения».
- Дочерние задачи имеют `РодительскаяЗадача`; циклы запрещены.

### 6.5. Идемпотентность и блокировки

- Ключ идемпотентности триггера: `ТипТриггера + ID источника + дата`; повторная регистрация не создаёт дубль.
- ID запроса в листе ожидания — UUID; повторный ответ не меняет состояние дважды.
- Регламентные задания захватывают пачку задач, ставят блокировку, обрабатывают, снимают; параллельная обработка одной задачи невозможна.
- Внешние вызовы выполняются вне транзакции; после ответа — новая транзакция с проверкой версии.

### 6.6. Интерфейс

MVP:

- общая форма/диалог `АИС_ВопросПоБазеЗнаний` в подсистеме «АИС: Сервис»: поле вопроса, ответ, список источников, кнопки «Спросить», «Очистить», «Открыть источник»;
- без истории и без продолжения прошлых диалогов.

Post-MVP:

- гибридная схема: команды и вкладка ИИ в штатных формах `Справочник.ВходящиеДокументы`, `Справочник.ИсходящиеДокументы`, `Задача.ЗадачаИсполнителя`;
- `АИС_РабочееМестоДЛ` — очередь ИИ-задач, фильтры, таймлайн, плейсхолдеры и лист ожидания;
- форма проекта исходящего документа — редактируемый текст и панель источников по плейсхолдерам;
- `АИС_АдминПанель` — справочники расширения, сроки, промпты, health RAG/LLM, переиндексация.

## 7. RAG-сервис

### 7.1. Стек

Python 3.12, FastAPI, pydantic-settings, httpx, qdrant-client, pytest, respx, ruff, mypy, uv. Docker-образ на python:3.12-slim.

### 7.2. API

`GET /health` — состояние сервиса, Qdrant, GigaChat, alias и target collection (без секретов).

MVP Q&A использует:

- `POST /v1/retrieve` — hybrid dense+sparse, rerank, group-by-source, parent expansion; ответ — документы с фрагментами, `source_id`, `title`, `doc_type`, `section_path`, `clause`, `page_start/page_end`, `text`, `score`, `score_type`;
- `POST /v1/index/chunks` — структурные чанки корпуса с `embedding_text`, `section_path`, `clause`, `page_*`, `parent_id`, `replace_existing`, `active`, `target_collection`;
- `POST /v1/index/activate` — включение staging-версии после батчевой индексации;
- `POST /v1/admin/collections` и `POST /v1/admin/alias` — создание версионированной коллекции и alias-swap;
- `POST /v1/index/cleanup` — очистка неактивных staging-точек.

Legacy `/v1/search`, `/v1/index/upsert`, `/v1/index/replace`, `DELETE /v1/index/{source_type}/{source_id}` сохраняются для шаблонов/обязанностей post-MVP.

Все методы, кроме `/health`, требуют `X-Service-Token`. Полные контракты и payload — `plans/2026-11-04-effective-rag.md` §6.

### 7.3. Qdrant

- Alias `ai_scrivener_knowledge_current`; физические коллекции `ai_scrivener_knowledge_v2_<timestamp>`.
- Named vectors: `dense` (2560, cosine) и `sparse` (BM25, `IDF`).
- Payload: `source_type`, `source_id`, `version`, `document_key`, `title`, `text`, `embedding_text`, `chunk_index`, `doc_type`, `authority`, `status`, `page_start/page_end`, `section_path`, `clause`, `parent_id`, `active`, `created_at`, `metadata`.
- Индексы payload: `source_type`, `source_id`, `document_key`, `doc_type`, `status`, `authority`, `active`, `page_start`, `parent_id`, `kind`, `published_at`, `effective_from`, `created_at`, `position_ids`, `metadata.folders/employees/purposes`.
- ID точки: UUIDv5 от `source_type:source_id:version:chunk_index`.
- Фильтрация по `active=true`; ACL по `position_ids` — post-MVP.
- Переиндексация: новая коллекция + alias-swap; staging-версии активируются после успешной загрузки.

### 7.4. GigaChat

- OAuth: `POST https://ngw.devices.sberbank.ru:9443/api/v2/oauth`, `scope=GIGACHAT_API_PERS`, `RqUID`, Basic auth из client_id/client_secret.
- Токен кэшировать в памяти, обновлять за 60 секунд до истечения; при 401 — одно обновление и повтор.
- Embeddings: `POST https://gigachat.devices.sberbank.ru/api/v1/embeddings`, модель `EmbeddingsGigaR`, подтверждённая размерность — 2560, батчи до 32 текстов, таймаут 30 с, retry на 429/5xx.
- Для GigaChat используется публичный корневой сертификат «Russian Trusted Root CA» (`config/russian_trusted_root_ca.pem`); TLS-проверка не отключается. Путь к CA задаётся в `RAG_GIGACHAT_CA_BUNDLE`.
- Размерность задаётся в `config/parameters.yaml` и сверяется при старте с пробным вектором; при несовпадении — понятная ошибка и инструкция пересоздать коллекцию.

### 7.5. Чанкинг и индексация

- Корпус индексируется `rag_indexer` из CAS-манифеста: текст/OCR → структура → clause-aware чанки → `/v1/index/chunks`.
- Для страниц без текстового слоя используется PaddleOCR с page-level fallback на Yandex OCR; для текстового слоя — без OCR.
- Чанки содержат `section_path`, `clause`, `page_start/page_end`, `parent_id`, `embedding_text`; таблицы режутся по группам строк с повтором шапки.
- Кэш extraction/chunks версионируется по extractor/OCR/chunker; повторная индексация идемпотентна.
- Полная переиндексация — в новую коллекцию с alias-swap; staging-батчи активируются после успешной загрузки.
- Шаблоны и должностные обязанности индексируются из 1С post-MVP; в MVP корпус знаний не требует прямого чтения 1С RAG-сервисом.

### 7.6. Отказоустойчивость

- При недоступности RAG окно Q&A показывает понятную ошибку и не подменяет ответ ответом LLM без источников.
- При недоступности LLM retrieval-результаты можно показать как список источников; вопрос не теряется.
- Ошибки индексации логируются и повторяются; state обновляется только после успешной активации.
- Сервис не логирует тексты документов; только ID, размеры, коды ошибок.

## 8. Интеграция с DeepSeek

Общий модуль `АИС_ИнтеграцияСLLM`:

- Модель и base URL берутся из локального `.env` (`DEEPSEEK_MODEL=deepseek-v4-flash`, `DEEPSEEK_BASE_URL=https://api.deepseek.com/v1`); ключ хранится в безопасном хранилище 1С.
- `ОтправитьПромпт(ТекстПромпта, ПараметрыМодели)`.
- `ОтправитьПромптСОжиданиемJSON(ТекстПромпта, ОжидаемаяСхема)`.
- `ВыбратьМодель(ТипЗадачи)`.
- HTTP-клиент: base URL, Bearer-ключ, таймаут, `response_format={"type":"json_object"}`, `temperature`.
- Retry: до 3 попыток при сетевых ошибках/5xx/невалидном JSON; пауза 1/2/4 с; каждая попытка в аудите.
- Валидация JSON — явные функции под каждую схему, не универсальный JSON Schema.
- При исчерпании попыток — ручное вмешательство/эскалация, задача сохраняется.
- Стоимость и токены считать по настройкам тарифа и писать в аудит.

Промпт-шаблоны:

| Код | Вход | Выход |
|---|---|---|
| `ОтветПоБазеЗнаний` | вопрос, RAG-фрагменты с `[S1]…[Sn]` | `{found: bool, answer: string, citations: [{source_id, clause}]}` |
| `ВыборШаблонаДокумента` | тип триггера, содержание, RAG-кандидаты | `{template_id, confidence, reason}` |
| `ФормированиеПоисковогоЗапроса` | описание плейсхолдера, контекст, допустимые параметры | `{query_template_id, parameters}` |
| `КлассификацияИсточника` | описание плейсхолдера | `{source_type}` |
| `КлассификацияПроизвольногоСобытия` | свободный текст из `Задача.Описание` | `{тип_триггера, характеристика, тип_действия}` либо `{тип_действия: НайтиИнформацию}` (`raw_specification.md` §4.4.3) |
| `ОпределениеПериодичностиРаспоряжения` | текст распоряжения | `{периодично: bool, предполагаемое_расписание}`; при `true` — фиксация расписания обязательна для закрытия задачи (`raw_specification.md` §4.3.4) |
| `ГенерацияТекстаДокумента` | шаблон, значения, RAG-контекст | `{document_text}` |
| `АнализСрываСроков` | таймлайн | `{reasons, immediate_actions, long_term_actions, summary}` |
| `ИзвлечениеПлейсхолдеров` | текст шаблона | `{placeholders:[...]}` (админ-операция) |
| `ИзвлечениеЗначенияИзКонтекста` | плейсхолдер + RAG-фрагменты | `{value, confidence, citations}` (позже) |

Защита от prompt injection: входящий текст передаётся в отдельных delimiters, system prompt запрещает следовать инструкциям из данных, LLM не имеет инструментов и не формирует исполняемый код/запросы.

## 9. Интерфейсы и отчёты

MVP:

- `АИС_ВопросПоБазеЗнаний` — диалог в «АИС: Сервис»: вопрос, ответ, источники, «Открыть источник», «Очистить»; без истории.
- `АИС_АдминПанель` — минимальные настройки: URL/токен RAG, промпт, health, переиндексация корпуса.

- Аудит Q&A — `АИС_ИсторияДействийИИ`.

Post-MVP:

- `АИС_РабочееМестоДЛ`: динамический список задач, фильтры, просрочка, быстрые действия.
- `АИС_ФормаЗадачи`: таймлайн, плейсхолдеры, лист ожидания, выбор шаблона.

- Отчёты: `АИС_СтатистикаЗадач`, `АИС_ЖурналЗадачи`, `АИС_АнализСрывовСроков`.

## 12. Риски и меры

| Риск | Мера |
|---|---|
| Демо-база окажется ПРОФ, а не КОРП | Маппинг строится по фактической базе; не использовать отсутствующие объекты |
| Ограничения демо-режима | Зафиксировать лимиты; RLS-тесты проводить в доступном режиме; не заявлять production-готовность |
| Конфигурация защищена от расширения | Проверить создание расширения до начала работ; при запрете — согласовать обходной путь |
| Режим совместимости базы ниже 8.3.27 | Установить режим расширения равным базе |
| Нельзя добавить RLS к базовым документам | RLS только на новых `АИС_*` объектах; базовые документы — штатные права Документооборота |
| Дублирование объектов базы | Обязательная инвентаризация и правило `reuse/extend/new` |
| Случайная фиксация `.dt`/`.cf`/`.cfe` | `.gitignore` и проверка `git status` перед коммитом |
| GigaChat: другая модель/размерность/лимиты | Модель и размерность в конфиге; проверка при старте; пересоздание коллекции |
| Невалидный JSON от DeepSeek | JSON-режим, 3 попытки, явные валидаторы, ручной fallback |
| Prompt injection из входящих документов | Delimiters, запрет инструкций из данных, отсутствие инструментов, валидация выхода |
| Произвольный запрос LLM к БД | Только утверждённые шаблоны + параметры |
| Устаревший индекс Qdrant | Версии, delete/replace, даты индексации, полная переиндексация |
| Утечка данных в облако | Минимизация, договор/политика, не индексировать конфиденциальные документы в MVP |
| Конкуренция задач | Блокировки, версия, короткие транзакции, идемпотентность |
| Сложность RLS | Отдельные роли, негативные тесты, запрет администратору видеть задачи |
| 1С не доверяет TLS-сертификатам GigaChat/DeepSeek | Установить корневые сертификаты, проверить `АИС_ТестИнтеграцииСLLM` |
| Зависание UI на LLM | Фоновые задания, состояния, ограничение таймаутов |
| Ручное создание шаблонов не масштабируется | Мастер шаблонов, автогенерация правил, проверка человеком |
| ИИ неверно размечает шаблон | Таблица проверки, тестовое заполнение, публикация только после подтверждения |
| Пользователь отклоняет предложение | Ручной режим, добавление/удаление/изменение плейсхолдеров, undo/redo |
| Дубли шаблонов | Сравнение с существующими, diff, обновление/объединение по решению пользователя |
| Ошибочное обновление существующего шаблона | Новая версия, сохранение старой, подтверждение пользователя, аудит |
| Дорогая ежедневная вычитка | Быстрая проверка, diff-only, кэш, квоты в страницах |
| Галлюцинации при вычитке | Обязательная цитата, confidence, accept/reject |
| Перегрузка локальной LLM | Очередь, приоритеты, деградация до быстрой проверки |
| Утечка документов во внешнюю LLM | Локальная LLM или политика организации |
| Потеря вёрстки DOCX | Детерминированный DOCX-движок, тестовый рендер, ограничения MVP |

## 13. Принятые решения и допущения

Проектирование завершено. Полный список решений — `docs/design-decisions.md`.

Ключевые решения:

- база — `ДокументооборотПРОФ 2.1.38.11`, режим совместимости 8.3.27;
- документы, задачи, файлы, права и бизнес-процессы — штатные;
- шаблоны — три штатных справочника + `ПравилаАвтозаполненияФайлов` + ТЧ `АИС_Плейсхолдеры`;
- новые документы не создаются; разделы — специализированные плейсхолдеры;
- мастер шаблонов — FR-044, сравнение — FR-045, вычитка — FR-046, квоты — NFR-032;
- маркеры шаблона: `{{...}}`, списки и разделы — повторяемые блоки;
- сравнение шаблонов: текст 0.4, плейсхолдеры 0.3, структура 0.2, метаданные 0.1; пороги 0.90/0.70;
- вычитка: быстрая без LLM, глубокая по кнопке; квота по умолчанию 30 страниц/день;
- локальная LLM через OpenAI-совместимый endpoint; DeepSeek — генерация, GigaChat — эмбеддинги;
- квоты и RLS проверяются на сервере 1С.

Допущения:

- локальная LLM доступна в контуре организации или есть внешний fallback;
- точные веса/пороги и модель уточняются на прототипе через конфигурацию;
- коммерческая лицензия на Документооборот и production-топология — вне учебного проекта.
