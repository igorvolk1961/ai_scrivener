## 1. Цель

Перевести агентов из режима «симулятор ДЛ» в режим полноценного ИИ-помощника:

1. Каждая сессия агента обязана запросить у пользователя одобрение изменяющих действий.
2. Инструмент одобрения имеет строго два варианта: одобрение и свободный текст (отклонение).
3. Свободный текст всегда означает отклонение и содержит указания, что изменить.
4. Оркестратор может автоматически выдать одобрение по настройкам текущего пользователя и типу документа.
5. Агент не знает об автоодобрении и не получает его признаков.
6. Управление автоодобрением — в форме «Вопросы по базе знаний» → «Пользовательские настройки».

## 2. Контракт инструмента `request_action_approval`

### 2.1 Вход

```json
{
  "completed": "Что агент уже сделал",
  "intended": "Что агент собирается сделать",
  "documents": [
    {
      "document_id": "uuid или null",
      "title": "Заголовок",
      "document_type": "Вид документа",
      "text": "Полный текст",
      "author": "Логин автора или null",
      "counterparty": "UUID контрагента или null"
    }
  ],
  "question": "Вопрос пользователю",
  "options": [
    {"kind": "approve", "text": "Одобряю. Действуй"},
    {"kind": "free_text", "text": "Отклонить и указать, что изменить"}
  ]
}
```

Правила:

- `options` — ровно два элемента;
- первый: `kind="approve"`, текст строго `"Одобряю. Действуй"`;
- последний: `kind="free_text"`;
- других вариантов нет;
- `documents` содержит все документы сессии с полными текстами;
- `completed` и `intended` непустые.

### 2.2 Выход

```json
{"decision": "approved", "answer_text": ""}
```

```json
{"decision": "rejected", "answer_text": "Непустые указания пользователя"}
```

Правила:

- `approved` — `answer_text` пустой;
- `rejected` — `answer_text` непустой;
- агент не получает полей автоодобрения и не знает о нём.

### 2.3 Обязательность

- каждая сессия агента вызывает инструмент до первого изменяющего действия;
- после одобрения разрешены только перечисленные намерения;
- новые изменяющие действия требуют нового вызова;
- после доработки по замечаниям — повторный вызов перед отправкой/фиксацией.

## 3. Обработка результата агентом

### 3.1 `approved`

Агент выполняет первоначальные намерения.

### 3.2 `rejected`

1. Первоначальные намерения считаются отменёнными.
2. `answer_text` — единственный источник дальнейших действий.
3. Агент извлекает конкретные указания.
4. Проверяет:
   - понятность и выполнимость;
   - непротиворечивость указаний между собой;
   - права и ограничения доступа.
5. Проверка «противоречит ли указание первоначальным намерениям» НЕ выполняется: первоначальные намерения уже отменены.
6. Если указаний нет, они неоднозначны, противоречат друг другу или недопустимы — `ask_clarifying_question`.
7. Если указания выполнимы — агент выполняет их.
8. Перед дальнейшими изменениями или отправкой — новый `request_action_approval`.
9. Любые дополнительные изменения, не указанные пользователем, требуют отдельного одобрения.

### 3.3 Свободный текст, похожий на одобрение

Примеры: «Одобряю», «Хорошо. Молодец», «Действуй как считаешь правильным».

Правило:

- свободный текст всегда отклонение, даже если содержит слова одобрения;
- если в нём нет конкретных указаний — агент вызывает `ask_clarifying_question`;
- оркестратор/UI может дополнительно переспросить: «Вы имели в виду одобрение? Нажмите „Одобряю. Действуй“ или опишите изменения»;
- автоматически превращать такой текст в `approved` запрещено.

## 4. Инструмент `ask_clarifying_question`

Вход: контекст, вопрос, варианты ответа.

Выход:

```json
{"answer_text": "Ответ пользователя"}
```

Правила:

- используется при отсутствии/неоднозначности/противоречии указаний;
- автоодобрение к нему не применяется;
- изменяющие действия до ответа запрещены;
- после ответа агент при необходимости снова вызывает `request_action_approval`.

## 5. Автоодобрение (только оркестратор)

### 5.1 Принципы

1. Агент не знает об автоодобрении.
2. Оркестратор проверяет условия до обращения к UI.
3. Если условия выполнены — UI не вызывается, агенту возвращается `approved` с пустым `answer_text`.
4. Если условия не выполнены — обычный вопрос в UI.
5. При ошибке/неполноте настроек автоодобрение выключено (fail closed).
6. Межсессионный кеш настроек запрещён.

### 5.2 Настройки текущего пользователя

1. Настройки всегда относятся к текущему пользователю.
2. Поля выбора пользователя в форме нет.
3. Оркестратор запрашивает настройки перед каждой сессией:

```http
GET /hs/ais-sim/auto-approval
```

4. Ответ:

```json
{
  "enabled": false,
  "default_mode": "off",
  "document_types": [
    {
      "document_type": "Устав",
      "mode": "off",
      "allowed_users": [],
      "allowed_counterparties": []
    }
  ]
}
```

5. `mode`: `off` | `on` | `depends_on_author`.
6. Неизвестный режим = `off`.
7. Если тип не указан — `default_mode`.
8. По умолчанию `enabled=false`, `default_mode=off`.

### 5.3 Режим `depends_on_author`

- автоодобрение разрешено, если автор документа входит в `allowed_users` ИЛИ контрагент входит в `allowed_counterparties`;
- если оба списка пусты — запрещено;
- для остальных — запрещено.

### 5.4 Условия автоодобрения

Автоодобрение выполняется, только если:

1. `enabled=true`;
2. в сессии есть хотя бы один документ;
3. тип каждого документа известен;
4. для каждого документа режим `on` или `depends_on_author` с подходящим автором/контрагентом;
5. все документы сессии удовлетворяют условиям.

Если хотя бы один документ не проходит — UI вызывается.

### 5.5 Аудит

Оркестратор пишет в журнал:

- пользователя;
- тип решения (`auto`/`manual`);
- режим и причину;
- типы документов;
- выбранный вариант.

Полные тексты документов в журнал не писать.

## 6. Модель данных расширения

Предлагаемые объекты:

1. `Справочник.АИС_НастройкиАвтоодобрения`
   - `Пользователь` (Пользователи);
   - `Включено` (Boolean);
   - `РежимПоУмолчанию` (String: `off/on/depends_on_author`);
   - `Активность`.
2. Подчинённый `Справочник.АИС_ПравилаАвтоодобренияПоТипам`
   - владелец — настройки;
   - `ВидДокумента` (ВидыВнутреннихДокументов);
   - `Режим`.
3. Подчинённый `Справочник.АИС_РазрешенныеАвторыАвтоодобрения`
   - владелец — правило;
   - `Пользователь`.
4. Подчинённый `Справочник.АИС_РазрешенныеКонтрагентыАвтоодобрения`
   - владелец — правило;
   - `Контрагент`.

Альтернатива: хранить списки в JSON-реквизитах правила. Выбрать подчинённые справочники — они проще для проверки прав и отчётности.

Права:

- текущий пользователь — чтение/изменение своих настроек;
- администратор — полные;
- сервисный пользователь — чтение для оркестратора.

## 7. HTTP-API расширения

Новые методы:

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/hs/ais-sim/auto-approval` | настройки текущего пользователя для оркестратора |
| GET | `/hs/ais-sim/auto-approval/types` | список типов документов и режимов для формы |
| POST | `/hs/ais-sim/auto-approval/set-all` | выставить режим всем типам одной операцией |

`GET /auto-approval`:

- определяет пользователя по текущей сессии;
- возвращает `enabled`, `default_mode`, `document_types`;
- не принимает `user` в параметрах;
- не раскрывает данные других пользователей.

`POST /set-all`:

- тело `{"mode":"off|on|depends_on_author"}`;
- обновляет `РежимПоУмолчанию` и все явные правила текущего пользователя;
- доступно только текущему пользователю/администратору.

## 8. Форма управления автоодобрением

Расположение:

- форма «Вопросы по базе знаний»;
- панель «Пользовательские настройки»;
- команда «Автоматическое одобрение».

Состав формы:

- переключатель «Автоодобрение включено» (по умолчанию выключен);
- режим по умолчанию;
- таблица типов документов: тип, режим, разрешённые пользователи, разрешённые контрагенты;
- кнопка «Установить для всех типов»;
- сохранение.

Ограничения:

- нет поля выбора пользователя;
- настройки всегда текущего пользователя;
- изменения применяются со следующей сессии агента.

## 10. UI вопросов

1. Для `action_approval` показывать:
   - `completed`;
   - `intended`;
   - документы сессии (заголовки и тексты);
   - вопрос;
   - ровно две кнопки/варианта.
2. Первый вариант: «Одобряю. Действуй».
3. Последний: «Отклонить и указать, что изменить» с полем текста.
4. Если выбран свободный текст с пустым значением — не отправлять ответ, попросить текст.
5. Если текст похож на чистое одобрение без указаний — показать уточнение:
   - «Одобрить действия»;
   - «Указать изменения».
6. Не показывать агенту признак автоодобрения.

## 11. Тесты

Юнит-тесты оркестратора:

- ровно два варианта, первый/последний корректны;
- `approved` → пустой `answer_text`;
- `rejected` → непустой `answer_text`;
- пустой rejected-текст → повторный вопрос;
- свободный текст «Одобряю» не превращается в approved;
- `rejected` отменяет первоначальные намерения;
- проверка указаний: понятность, непротиворечивость, права;
- отсутствие проверки конфликта с первоначальными намерениями;
- повторное одобрение после доработки;
- автоодобрение: матрица режимов, все документы, нет документов, ошибка настроек, текущий пользователь;
- при автоодобрении UI не вызывается;
- агент не получает полей автоодобрения.

Тесты расширения:

- настройки текущего пользователя без параметра `user`;
- set-all;
- режимы `off/on/depends_on_author`;
- разрешённые авторы/контрагенты;
- права доступа к настройкам;
- форма без выбора пользователя.

Интеграционные сценарии:

1. Автоодобрение выключено → вопрос в UI → approve → действие.
2. Автоодобрение выключено → free text с изменениями → отклонение → изменения → повторное одобрение.
3. Автоодобрение включено для типа → UI не вызывается → approved.
4. `depends_on_author`: автор разрешён → auto; другой автор → UI.
5. Смешанная сессия: один документ не проходит → UI.
6. «Одобряю» в свободном тексте → уточняющий вопрос.
7. Ошибка HTTP настроек → UI, не auto.

## 14. Принятые уточнения

- «Каждый вызов агента» = каждая сессия агента.
- Изменяющие действия без одобрения запрещены; чтение/подготовка разрешены.
- Вариантов ровно два: `Одобряю. Действуй` и свободный текст.
- Свободный текст всегда отклонение, даже со словами одобрения.
- При отказе первоначальные намерения отменяются; проверка противоречия с ними не выполняется.
- Проверяются понятность, непротиворечивость и допустимость указаний.
- После доработки — повторное одобрение.
- Автоодобрение — только оркестратор; агент о нём не знает.
- Настройки всегда текущего пользователя, без выбора пользователя.
- По умолчанию автоодобрение выключено; при ошибке — выключено.
- Автоодобрение применяется только если все документы сессии соответствуют условиям.
