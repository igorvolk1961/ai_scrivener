# Перенос ИИ-помощника из симулятора в расширение 1С

## 1. Цель

Перенести функциональность ИИ-агентов из `ai-scrivener-enterprise-sim` в расширение `ai_scrivener`, сохранив 1С:Документооборот источником истины:

- документы и задачи создаются штатным путем;
- агент обрабатывает только явно помеченные задачи;
- LLM-цикл выполняет внешний stateless `agent-service`;
- все инструменты и изменения выполняет 1С;
- запросы к живому пользователю отображаются в форме 1С;
- каждая группа возможностей включается отдельно из формы администрирования ИИ.

Не переносить:

- `owner_orders.py`, `scenario_bootstrap.py` и сценарные конфиги симулятора;
- файловый `state/interactions` и UI симулятора;
- шаблонные approval-инструменты `technical_approve_template`, `approve_template`;
- автоматическое создание демонстрационных сотрудников, должностей и приказов.

## 2. Зафиксированные решения

| Решение | Значение |
|---|---|
| Где работает агент | Внешний `agent-service`, как RAG |
| Состояние агента | Stateless; 1С хранит run и историю шагов |
| Кто выполняет инструменты | 1С |
| Кто хранит interactions | 1С, `АИС_ВзаимодействияИИ` |
| Кто видит запрос | Только исполнитель задачи |
| Отбор задач | Только явно помеченные задачи |
| Запуск | Очередь в 1С + регламентное задание |
| Уведомление | Служебная задача-указатель + форма «Мои запросы ИИ» |
| Таймаут | 24 часа, затем `Истек`, без автоматических действий |
| Approval | Как сейчас: approval + автоодобрение только для документов |
| Автоодобрение опасных групп | Запрещено: найм, оргструктура, зарплата, разделы, замечания, корпус знаний |
| Настройки агента | `АИС_НастройкиАгента`, автоматически всем, по умолчанию выключен |
| Роль-промпт | Генерируется сразу в фоне из должностной инструкции/должности |
| Автовключение | Управляется настройкой админ-формы; по умолчанию выключено до проверки |
| Группы функций | Только глобальные флаги; персональных переключателей групп нет |
| Группы | Документы; Поиск/знания; Интернет; Персонал и оргструктура; Разделы; Замечания; Корпус знаний |
| Исключено из агента | `technical_approve_template`, `approve_template`; эти задачи остаются людям |
| Интернет-поиск | Отдельный `search-service`; 1С вызывает его по tool_call |
| Ключ LLM | В env `agent-service` только `LLM_API_KEY`; модель, температура, лимит токенов и параметры подключения — в константах 1С |
| RAG | Не меняется; инструменты RAG выполняет 1С через существующий клиент |

## 3. Целевая архитектура

```text
1С: задача + АИС_КонтекстЗадачИИ
        │
        ▼
АИС_ЗапускиАгентов (очередь/состояние)
        │  регламентное задание
        ▼
АИС_АгентИИ.ВыполнитьОдинШаг
        │  снимок: задача, сотрудник, контекст, история, allowed_tools
        ▼
agent-service /v1/agent/step  (LLM, без записи в 1С)
        │  tool_call | final | error
        ▼
АИС_ИнструментыАгента
        ├─ проверка группы, ACL, approval
        ├─ RAG → rag-service
        ├─ поиск → search-service
        ├─ документы/задачи → модули расширения
        └─ approval/вопрос → АИС_ВзаимодействияИИ + задача-указатель
        │
        ▼
результат инструмента → история run → следующий шаг
```

Ключевые ограничения:

- `agent-service` не имеет учетных данных 1С и не вызывает API 1С.
- `search-service` не имеет доступа к 1С.
- 1С не ждет ответа пользователя внутри фонового задания. Один шаг — один запуск задания.
- После создания interaction run переходит в `ОжидаетОтвета` и завершает шаг. Ответ пользователя создает новый запуск.

### 3.1. Кто именно исполняет инструменты

- `agent-service` исполняет только LLM-вызов. Он возвращает `tool_call`, но не имеет доступа к 1С и не выполняет действие.
- `АИС_АгентОчередь` — регламентное задание 1С. Оно запускает `АИС_АгентИИ.ВыполнитьОдинШаг` под служебной учетной записью/серверным контекстом.
- `АИС_ИнструментыАгента` — dispatcher в 1С. Он проверяет группу, имя инструмента, аргументы, исполнителя, ACL и approval.
- Профильный BSL-модуль (`АИС_АгентДокументы`, `АИС_АгентКадры` и т.д.) выполняет действие и пишет объекты 1С.
- Для RAG 1С вызывает `rag-service` через `АИС_ИнтеграцияСRAG`; для интернета — `search-service` через `АИС_ИнтеграцияСПоиском`. Оба сервиса только возвращают данные.
- Служебный контекст не означает «действовать от имени администратора». Модуль явно получает сотрудника-исполнителя, проверяет его права и только затем при необходимости включает привилегированный режим для технической записи.
- Автор документа/задачи, исполнитель и запись аудита всегда относятся к сотруднику-агенту, а не к служебной учетной записи.

## 5. Администрирование и формы

### 5.1. `АИС_АдминистрированиеИИ`

Дополнить существующую форму:

- группа «ИИ-агент»: мастер-флаг, автовключение, ссылки на монитор запусков;
- `АИС_МодельАгента`, `АИС_ТемператураАгента`, `АИС_МаксимумТокеновАгента`;
- адрес/токен/таймаут/повторы `agent-service`, кнопка «Проверить агент»;
- адрес/токен/таймаут/повторы `search-service`, кнопка «Проверить поиск»;
- кнопка «Группы функций ИИ-агента»;
- кнопка «Агенты сотрудников»;
- кнопка «Запуски агентов»;
- существующие LLM/RAG-настройки остаются; поле LLM-ключа явно подписать «для внутренних вызовов 1С».

### 5.2. Форма групп

Новая обработка `АИС_ГруппыФункцийИИ` с формой:

- мастер-флаг `АИС_АгентВключен`;
- 7 глобальных флагов групп;
- описание состава каждой группы и риска;
- сохранение только администратором;
- предупреждение, если включается группа с мутирующими действиями.

### 5.3. Агенты сотрудников

Список `АИС_НастройкиАгента` и карточка:

- сотрудник, включен, роль-промпт, статус промпта, лимит шагов;
- кнопка «Сформировать промпт»;
- кнопка «Включить/Выключить»;
- генерация автоматически при создании сотрудника и при backfill;
- по умолчанию агент выключен; автовключение только если `АИС_АвтоВключениеАгентов = Истина` и промпт успешно сформирован.

### 5.4. Мои запросы ИИ

Новая обработка `АИС_МоиЗапросыИИ`:

- список только своих `АИС_ВзаимодействияИИ`;
- фильтры «Ожидают / История»;
- карточка динамически отображает payload:
  - approval: что сделано, что планируется, документы, вопрос, кнопки «Одобряю. Действуй» и «Отклонить и указать, что изменить»;
  - уточнение: текст вопроса и поле ответа;
  - вопросы образца/решение: таблица вопросов и вариантов;
  - согласование черновика: текст, замечания и действия;
- ответ пишется в `ОтветJSON`, статус → `Отвечен`, задача-указатель закрывается, run ставится в очередь на продолжение;
- истекший запрос только для чтения.

### 5.5. Передача задачи агенту

Новая обработка `АИС_ПередатьЗадачуИИ`:

- выбор открытой задачи текущего пользователя или задачи, доступной администратору;
- проверка, что исполнитель имеет `АИС_НастройкиАгента` и агент включен;
- создание `АИС_КонтекстЗадачИИ`, если его нет;
- постановка run в очередь;
- повторная передача уже обработанной задачи запрещена без явного сброса run.

### 5.6. Запуски агентов

Админ-монитор `АИС_ЗапускиАгентов`:

- состояние, задача, сотрудник, шаг, попытки, ошибка, время;
- кнопки «Повторить», «Отменить», «Открыть задачу»;
- содержимое payload не показывать администратору без отдельного аудиторского доступа.

### 5.7. Права и интерфейс

- `АИС_АдминистраторСистемы` и `ПолныеПрава`: админ-формы, группы, настройки агентов, монитор запусков.
- `АИС_ДолжностноеЛицо`: только `АИС_МоиЗапросыИИ`, чтение/запись своего ответа, чтение своей задачи.
- `АИС_СервисныйПользователь`: очередь, запуски, история, служебные записи.
- `АИС_МоиЗапросыИИ` добавить в подсистему `АИС_Сервис`; админ-формы скрыть через `CommandInterface.cmi`.

## 6. Внешние сервисы

### 6.1. `agent-service`

Новый stateless Python/FastAPI сервис по образцу `rag-service`.

Env (только секреты и техническая аутентификация):

- `LLM_API_KEY` — ключ LLM, единственная настройка провайдера в env;
- `AGENT_SERVICE_TOKEN` — service-token для запросов от 1С (не ключ LLM).

Все бизнес-параметры LLM приходят из 1С в запросе:

- `model`, `temperature`, `max_tokens`;
- `provider` фиксирован в коде сервиса (DeepSeek-совместимый endpoint); смена провайдера — отдельный релиз сервиса.

Ограничения шагов и tool-call задаются в 1С (`МаксШагов` и политика run), а не в env.

API:

`GET /health` — версия, провайдер, наличие ключа, доступность провайдера; модель в health не фиксируется, потому что приходит в запросе.

`POST /v1/agent/step`

Запрос:

```json
{
  "run_version": 7,
  "task": {
    "id": "uuid",
    "title": "...",
    "description": "...",
    "executor": "login",
    "author": "login",
    "due_at": "...",
    "subject": {"type": "ВнутреннийДокумент", "id": "uuid", "title": "..."}
  },
  "agent": {
    "login": "login",
    "position": "...",
    "role_prompt": "..."
  },
  "context": {
    "trigger": "...",
    "action": "...",
    "candidates": [],
    "approval": {}
  },
  "messages": [],
  "llm": {
    "model": "deepseek-chat",
    "temperature": 0.2,
    "max_tokens": 2000
  },
  "allowed_tools": ["search_example", "create_draft", "..."],
  "policy": {
    "approval_gate": true,
    "allowed_addressees": [],
    "web_search": true,
    "knowledge": true
  }
}
```

Ответ:

```json
{"type": "tool_call", "tool": "search_example", "arguments": {}, "run_version": 7}
```

или:

```json
{"type": "final", "content": "...", "run_version": 7}
```

или:

```json
{"type": "error", "code": "llm_error", "message": "...", "run_version": 7}
```

Правила:

- только один tool_call за шаг;
- сервис проверяет имя инструмента по `allowed_tools` и JSON-схему аргументов;
- сервис не выполняет инструменты и не обращается к 1С;
- итоговый ответ не закрывает задачу; это делает `complete_task`;
- при неизвестном инструменте или неверных аргументах возвращается `error`, 1С пишет аудит и завершает run с `ТребуетВнимания`;
- ключ не логируется; модель и параметры генерации можно писать в аудит;
- модель и параметры валидируются по allowlist сервиса;
- сервис не хранит историю между запросами.

Инструменты в `agent-service`:

- схемы всех перенесенных инструментов, кроме `technical_approve_template` и `approve_template`;
- базовый системный промпт + роль-промпт из 1С;
- явный запрет выполнять инструкции из документов/веб-страниц;
- запрет выдумывать UUID, логины и документы;
- требование сначала искать основание, затем готовить документ.

### 6.2. `search-service`

Новый FastAPI сервис:

- `GET /health`;
- `POST /v1/search` с `{query, limit, locale, safe_search}`;
- ответ: `{results: [{title, url, snippet, source, rank}], provider, latency_ms}`;
- провайдер и его ключ — собственные секреты `search-service` в env; это не настройки LLM агента;
- таймаут, лимит результатов, нормализация, user-agent;
- без доступа к 1С;
- результаты считаются недоверенными; 1С передает их агенту как данные.

### 6.3. RAG

Не менять. Инструменты `search_example` и `search_knowledge_base` выполняет 1С через `АИС_ИнтеграцияСRAG`, чтобы сохранить ACL и текущую индексацию.

## 8. Реализация в 1С

### 8.1. Клиенты сервисов

`АИС_ИнтеграцияСАгентом`:

- `ВыполнитьШаг(Снимок)`;
- `ПроверитьДоступность()`;
- `X-Service-Token`, таймаут, повторы, разбор JSON;
- 4xx — фатально, 5xx/сеть — повтор;
- не передавать ключ LLM.

`АИС_ИнтеграцияСПоиском`:

- `Поиск(Запрос, Лимит)`;
- `ПроверитьДоступность()`;
- те же правила токена/повторов.

### 8.2. Очередь и run

`АИС_АгентИИ`:

- `ОбеспечитьНастройкиАгента(Сотрудник)`;
- `СформироватьРольПромпт(Настройка)`;
- `ПоставитьЗадачуВОчередь(Задача, Причина)`;
- `ВыполнитьОдинШаг(Запуск)`;
- `ПродолжитьПослеОтвета(Взаимодействие)`;
- `ИстечьПросроченныеВзаимодействия()`;
- `ОбработатьОчередь(Предел)`.

Планировщик:

- `АИС_АгентОчередь` каждую минуту;
- `АИС_АгентТаймауты` каждые 5 минут;
- максимум один активный run на задачу;
- блокировка run через `Заблокирован/КлючБлокировки` и версию;
- повтор с backoff при 5xx/сети;
- после `tool_call` результат сразу ставит run в очередь на следующий шаг;
- при `ОжидаетОтвета` run не занимает очередь;
- при ручном завершении/отмене задачи run переводится в `Отменен`, interaction закрывается;
- при выключении мастера, группы или агента новые шаги не запускаются, текущий шаг завершается, run переводится в `Отменен`;
- перед каждым изменяющим инструментом перечитываются задача, контекст и версия; устаревшая версия не применяется.

### 8.3. Снимок

`АИС_АгентСнимок.Построить(Запуск)`:

- задача, исполнитель, автор, срок, предмет;
- `АИС_КонтекстЗадачИИ`;
- роль-промпт и лимиты;
- история `messages`;
- approval state;
- разрешенные группы/инструменты;
- ACL-фильтр документов и адресатов;
- версия контекста.

Не включать:

- пароли, токены, ключи;
- документы, недоступные исполнителю;
- лишние персональные данные;
- полные тексты, если достаточно ID и фрагмента.

### 8.4. Инструменты

`АИС_ИнструментыАгента` — единый dispatcher:

- проверка группы по глобальному флагу;
- проверка имени по allowlist;
- проверка аргументов;
- проверка исполнителя/задачи/ACL;
- проверка актуальной версии задачи и контекста;
- проверка idempotency key `run + step + tool + hash(args)`;
- вызов профильного модуля;
- запись в `АИС_ИсторияДействийИИ`;
- возврат JSON-результата.

Мутирующие инструменты обязаны быть идемпотентными: повторный вызов после сетевого сбоя не должен создать второй документ/задачу/пользователя. Для этого используется `КлючИдемпотентности` в `АИС_ЗапускиАгентов` и проверка уже созданного результата перед записью.

Профильные модули:

- `АИС_АгентДокументы`;
- `АИС_АгентПоиск`;
- `АИС_АгентКадры`;
- `АИС_АгентОргструктура`;
- `АИС_АгентРазделы`;
- `АИС_АгентЗамечания`;
- `АИС_АгентКорпус`.

Логику брать из `src/HTTPServices/АИС_Симулятор/Module.bsl`, но не вызывать HTTP-адаптер из агента. Общие операции вынести в модули и оставить адаптер для regression-тестов.

### 8.5. Approval

Перенести `_auto_approval_allows` в BSL:

`АИС_АвтоодобрениеСервер.МожноАвтоодобрить(Сотрудник, ДокументыJSON)`:

- fail closed;
- учитывать `Включено`, `РежимПоУмолчанию`, правила по типу, авторов и контрагентов;
- применять только к `create_document`, `approve_document`, `cancel_document`;
- для остальных мутирующих инструментов всегда создавать interaction.

Guard:

- мутирующий инструмент без approval, совпадающего с инструментом и аргументами, → `approval_required`;
- `request_action_approval` — единственный способ установить approval; в state хранятся `subject_kind`, `tool`, `hash(args)`, `decision`, `answer_text`;
- для `subject_kind = action` автоодобрение всегда запрещено; interaction создается вручную;
- `approved` → пустой `answer_text`; `rejected` → непустой;
- повторный вызов того же инструмента с другими аргументами требует нового approval;
- для high-risk групп автоодобрение запрещено.

### 8.6. Interactions

- `request_action_approval` создает `АИС_ВзаимодействияИИ` и служебную задачу;
- `ask_clarifying_question` — interaction без автоодобрения;
- `submit_draft_for_review` — interaction с текстом и действиями;
- `ask_example_changes` / `ask_decision` — multi-question payload;
- после ответа: `ОтветJSON`, `Отвечен`, закрыть задачу-указатель, поставить run в очередь;
- после 24 часов: `Истек`, run `Истек`, задача остается открытой;
- повторный ответ идемпотентно отклоняется по версии.

### 8.7. Автосоздание агентов

- `АИС_Сотрудники.СоздатьСотрудника` вызывает `ОбеспечитьНастройкиАгента`;
- backfill существующих пользователей отдельной обработкой;
- `Включен = Ложь`;
- сразу после создания ставится фоновая генерация промпта по действующей должностной инструкции; если ее нет — по должности и шаблону; создание сотрудника не блокируется;
- при ошибке `СтатусПромпта = Ошибка`, агент не включается;
- `АИС_АвтоВключениеАгентов` по умолчанию `Ложь`; если включено, агент включается только после успешной генерации.

### 8.8. Постановка задач

- `АИС_КонтекстЗадачИИ` — маркер допустимости;
- агент берет только задачи, где `ЗадачаИсполнителя.Исполнитель` — конкретный `CatalogRef.Пользователи`; задачи, адресованные через роль/объект адресации, не берутся;
- задачи из `АИС_Уведомления` ставятся в очередь после сохранения контекста;
- ручная команда/обработка `АИС_ПередатьЗадачуИИ` создает контекст, если его нет, и ставит run;
- автоматические триггеры для входящих/исходящих документов добавляются только после инвентаризации их штатных полей адресации; до этого используется ручная передача;
- задачи без контекста не обрабатываются;
- задачи согласования/утверждения шаблонов не ставить в очередь: для них инструменты исключены.

## 10. Проверка

### Python

- `agent-service`: контракт `/v1/agent/step`, один tool_call, фильтрация allowed_tools, ошибки LLM, таймауты, отсутствие записи в 1С.
- `search-service`: токен, лимиты, таймаут, нормализация, пустые результаты, провайдерные ошибки.
- Контрактные тесты снимка и tool_result.

### 1С

- автосоздание настроек для нового и существующего сотрудника;
- агент выключен по умолчанию; автовключение только по флагу;
- задача без контекста не берется;
- задача с контекстом проходит полный цикл;
- выключенная группа запрещает инструмент;
- неизвестный инструмент отклоняется;
- approval: manual, auto, rejected, timeout;
- high-risk группы не автоодобряются;
- interaction отвечен, закрыт, run продолжен;
- повторный ответ идемпотентен;
- отмена задачи отменяет run;
- падение сервиса: retry/backoff, затем `Ошибка`, задача открыта;
- перезапуск 1С не теряет run;
- параллельные задачи одного агента не выполняются одновременно;
- шаблонные approval-задачи не попадают агенту;
- ACL: чужой документ не попадает в снимок;
- не-администратор не видит админ-формы и чужие interactions.

### Общие

- `uv run pytest`;
- `scripts/precommit/bsl_lint.sh`;
- EDT build/export;
- `CheckConfig`;
- сценарий обычного приказа: документ → задача → контекст → агент → approval → документ-результат → завершение задачи.

## 11. Rollout и откат

1. Выключить `АИС_АгентВключен`; все группы выключены.
2. Развернуть `agent-service`, `search-service`, проверить `/health`.
3. Загрузить расширение, выполнить backfill настроек агентов.
4. Включить пилотному сотруднику «Документы» и «Поиск/знания»; агент проверить вручную.
5. Включить «Интернет».
6. Включать «Персонал и оргструктура», «Разделы», «Замечания», «Корпус знаний» по одной.
7. Для отката выключить мастер-флаг или группу: новые run не создаются, текущие останавливаются после шага, interactions остаются видимыми, данные не удаляются.

## 12. Риски и допущения

- Провайдер интернет-поиска и его лимиты определяются env `search-service`; по умолчанию нужен адаптер, не прямой API из 1С.
- Управление агентами — только администратор в MVP; HR-доступ можно добавить позже.
- Ролевые и подразделенческие задачи не автоматизируются: агент привязан к конкретному пользователю.
- Автоматический контекст создается для существующего триггера внутреннего документа; для остальных задач используется ручная команда «Передать ИИ».
- Задачи согласования/утверждения шаблонов остаются людям.
- Срок хранения запусков и interactions — 90 дней по умолчанию; аудит — 1 год; вынести в константы.
- `agent-service` не хранит данные и не логирует промпты/ключи; ключ LLM живет только в env, модель и параметры генерации — в 1С.
- `AGENT_SERVICE_TOKEN` остается в env как секрет аутентификации; это не пользовательская настройка LLM.
- Содержимое документов и интернета считается недоверенным; агент не выполняет инструкции из него.
- `АИС_Симулятор` не используется production-агентом; его handlers служат источником логики и regression-тестов до удаления.
- Существующие предупреждения `CheckConfig` по базовой конфигурации не являются ошибками расширения.
