## 0. Резюме

ИИ-помощник не является отдельной привилегированной учётной записью в бизнес-смысле: он действует в рамках задачи сотрудника, а создаваемые объекты и кастомный аудит привязываются к сотруднику. Технически исполнение идёт регламентным заданием 1С, а значительная часть записи выполняется в привилегированном режиме. Поэтому реальная граница привилегий проходит не по ролям 1С, а по проверкам в коде.

План закрывает четыре класса проблем:

1. **Approval не гарантирует, что выполнено именно одобренное действие.** Для `documents` одобрение не привязано к инструменту и аргументам, а автоодобрение доверяет массиву документов, который прислала LLM.
2. **Инструменты выполняют действия без проверки полномочий исполнителя.** Это касается кадров, оргструктуры, разделов, замечаний, утверждения/отмены документов и шаблонов.
3. **Привилегированный режим и run-as регламентного задания не ограничены платформой.** Пропущенная проверка в любом модуле даёт агенту полный доступ привилегированного процесса.
4. **Данные и сервисы недостаточно защищены.** Внешняя LLM, отсутствие auth у сервисов, аудит и хранение payload требуют отдельных мер.

## 1. Цель и границы

### 1.1. Цель

Сделать так, чтобы ИИ-помощник мог выполнять только те действия, которые:

- входят в явно включённую функцию;
- разрешены конкретному сотруднику по его роли, должности и правам на объект;
- были показаны пользователю и одобрены именно для этого инструмента и этих аргументов;
- оставляют воспроизводимый аудит с привязкой к сотруднику;
- не приводят к утечке данных за пределы разрешённого контура.

### 1.2. Вне цели

- Полноценный DLP/классификатор секретов и юридически значимая маскировка.
- Промышленная HA-топология, SIEM и круглосуточный SOC.
- Замена штатной модели прав 1С:Документооборот.
- Автоматизация найма, оргструктуры и зарплатных решений без человека.
- Полный red-team всего расширения; в плане — только агентский контур.

### 1.3. Рабочие допущения

Анкета с развилками была отклонена, поэтому план фиксирует рекомендуемые варианты. Их нужно подтвердить при приёмке; на структуру работ это не влияет, меняется только объём.

| Решение | Принятый вариант | Комментарий |
|---|---|---|
| Объём | P0 + P1 до пилота, P2 после | Пилот на реальных документах без P0/P1 не допускается |
| Approval | Точный `tool + hash(args)` для всех изменяющих инструментов | Автоодобрение — только по точным аргументам |
| Кадровые инструменты | Проверка полномочий + запрет выдачи admin/service-ролей | При необходимости — второй approval администратора |
| Техническое исполнение | Выделенный least-privilege служебный пользователь | Привилегированный режим убирается или сужается |
| LLM в проде | Локальная/внутренняя LLM | DeepSeek — только для разработки; внешний провайдер по умолчанию выключен |
| Маскирование | Опция, настраиваемая при конфигурировании | `off` для локальной LLM, `basic`/`strict` для внешней |
| Auth сервисов | `X-Service-Token` + bind `127.0.0.1` | Требует пересмотра NFR-036 или mTLS-альтернативы |
| Совместимость | Активных промышленных запусков нет | Формат approval можно менять без миграции |
| Шаблоны | Убрать `technical_approve_template` и `approve_template` из allowlist | Вернуть к исходному плану |
| Формат | Отдельный plan-файл + чек-лист | Этот документ |

## 2. Модель угроз и границы привилегий

### 2.1. Кто исполняет действия

- `agent-service` вызывает LLM и возвращает **один** `tool_call` или `final`.
- `agent-service` не имеет учётных данных 1С и не обращается к API 1С.
- `АИС_АгентОчередь` — регламентное задание 1С. Оно запускает `АИС_АгентИИ.ВыполнитьОдинШаг`.
- `АИС_ИнструментыАгента` — dispatcher. Он проверяет allowlist, группу, approval, идемпотентность и аудит.
- Профильные модули (`АИС_АгентКадры`, `АИС_АгентРазделы`, `АИС_АгентЗамечания`, `АИС_АгентКорпус`, `АИС_АгентШаблоны`, `АИС_АгентЗнания`, `АИС_АгентОбразцы`) выполняют действия.

### 2.2. Где включается привилегированный режим

Привилегированный режим обходит RLS и штатные права 1С. Сейчас он включается, в частности, в:

- `src/CommonModules/АИС_Уведомления/Module.bsl:26,113` — подписки на запись документов; обратного вызова нет;
- `src/CommonModules/АИС_АвтоодобрениеСервер/Module.bsl:4` — проверка чужих правил; обратного вызова нет;
- `src/CommonModules/АИС_РазделыДокументов/Module.bsl` — большинство операций с разделами;
- `src/CommonModules/АИС_ОбщегоНазначения/Module.bsl:314,336` — отмена и утверждение документа;
- `src/CommonModules/АИС_Сотрудники/Module.bsl:246` — выдача прав запуска клиентов;
- `src/CommonModules/АИС_АгентИИ/Module.bsl:474` — привилегированная передача задачи (единственное место, где привилегированность оформлена явно и с проверками).

Если привилегированный режим не восстановлен, сессия пользователя может остаться привилегированной. Это нужно проверить на платформе и устранить независимо от остальных мер.

### 2.3. Что считается границей

Граница должна проверяться на четырёх уровнях:

1. **Функция включена**: мастер-флаг, персональный агент, группа.
2. **Инструмент разрешён**: allowlist пересечён с реализациями.
3. **Сотрудник имеет право**: роль, должность, авторство, ответственность, ACL объекта.
4. **Пользователь одобрил**: точный инструмент и точные аргументы, а не общее намерение.

Сейчас третий уровень для многих инструментов отсутствует, а четвёртый для `documents` не привязан к аргументам.

### 2.4. Критерии успеха

- Ни один изменяющий инструмент не выполняется без `approved`, совпадающего с `tool` и `hash(args)`.
- Ни один high-risk инструмент не выполняется, если у сотрудника нет соответствующей роли/должности/ответственности.
- Агент не может выдать другому пользователю `АдминистраторСистемы` или `СервисныйПользователь`.
- Агент не может утвердить/отменить документ, который он не вправе утверждать/отменять, даже если он его читает.
- Агент не может писать в чужой раздел или создавать замечания к чужому документу.
- Шаблонные approval-инструменты недоступны агенту.
- После обработки подписки `ПривилегированныйРежим()` возвращается в исходное состояние.
- Внешняя LLM получает только разрешённые и, при необходимости, замаскированные данные; при запрете — запрос блокируется.
- Аудитор видит промпт/ответ, администратор не видит payload задач и взаимодействий.
- Параллельные запуски не выполняют одну задачу дважды; переназначенная задача не завершается старым агентом.

### 2.5. Как отличать локального провайдера от внешнего

OpenAI-совместимый API **не является признаком доверия**: и локальные vLLM/Ollama/TGI/LM Studio, и внешние DeepSeek/OpenAI/OpenRouter используют один и тот же протокол. Нельзя определять «внешний» провайдер по URL, имени модели, наличию API-ключа или заголовкам ответа. `provider_kind` — это явная security-классификация, которую администратор задаёт при конфигурировании, а система проверяет техническими средствами.

Классификация должна опираться на три независимых признака.

#### 1. Владение и контроль inference

- **`local`** — модель и inference-сервис развёрнуты в контуре организации; организация контролирует хост, веса, логи, бэкапы, доступ и сетевой периметр; промпты и ответы не покидают контролируемую зону.
- **`external`** — inference выполняет сторонняя организация; даже если endpoint находится в частной сети или за корпоративным прокси, это `external`, если модель, логи и инфраструктура контролируются не организацией.
- **`unknown`** — классификация не подтверждена. В этом состоянии запросы к LLM запрещены (fail closed).

#### 2. Сетевой путь и периметр

- **`local`**: endpoint в loopback/private network/выделенной trust zone; у хоста нет маршрута к внешним LLM; egress к публичным inference-сервисам запрещён.
- **`external`**: endpoint в публичном интернете или доступен только через egress-прокси с DLP/allowlist; прямые запросы из 1С/агентского хоста к произвольным внешним адресам запрещены.
- Проверка выполняется при старте и периодически/перед запросом: DNS-резолв, классификация IP (loopback, RFC1918, link-local, ULA, публичный), запрет редиректов, запрет подмены через `HTTP_PROXY`/`HTTPS_PROXY`, TLS-проверка.

#### 3. Явная декларация и аттестация

- `provider_kind` задаётся администратором в `АИС_ПолитикаLLMJSON` и/или env `agent-service`; по умолчанию — `unknown`, `external_allowed=false` (система не работает, пока администратор явно не выберет `local` или не разрешит внешний провайдер).
- Для каждого вида задаётся allowlist endpoint'ов: точная схема, хост, порт, путь. Для `local` — только адреса из private/loopback диапазонов; для `external` — только явно разрешённые хосты через прокси.
- Смена `provider_kind`, allowlist и `external_allowed` — административное действие с аудитом; конфигурация версионируется.
- Для `external` дополнительно фиксируются: договор/DPA, запрет обучения на данных, срок хранения, регион, список субпроцессоров. Для `local` — инвентаризация хоста, доступ, патчи, резервное копирование.

#### Что не является признаком внешнего провайдера

- OpenAI-совместимый протокол и путь `/v1/chat/completions`.
- Схема `http/https`, доменное имя или IP-адрес без проверки сети.
- Название модели (`gpt-*`, `deepseek-*`, `local-*`) и ответ `/v1/models`.
- Наличие или отсутствие API-ключа.
- Заголовки `Server`, `Via`, `X-*` и время ответа.
- Issuer TLS-сертификата: внутренний CA может обслуживать и внешний прокси, публичный CA — и локальный хост.

#### Проверки, которые нужно реализовать

- В `agent-service` и в 1С: `ПроверитьКлассификациюПровайдера(Политика)`:
  - `provider_kind` заполнен и не `unknown`;
  - endpoint входит в allowlist;
  - резолв IP соответствует классу (`local` → private/loopback; `external` → публичный или адрес прокси);
  - при `local` нет публичного IP и нет egress-маршрута к внешним LLM;
  - при `external` `external_allowed=true`;
  - при `external` и `masking_mode=off` запрос блокируется, если нет явного административного override с аудитом;
  - при ошибке проверки — fail closed, запись в аудит, `ТребуетВнимания`.
- В `agent-service`: `LLM_PROVIDER_KIND`, `LLM_EXTERNAL_ALLOWED`, `LLM_ENDPOINT_ALLOWLIST`, `LLM_LOCAL_CIDRS`, `LLM_EXTERNAL_CIDRS`; `httpx` с `trust_env=False`; периодическая повторная проверка DNS; запрет редиректов.
- В `/health` показывать `provider_kind` и результат проверки, но не секреты и не внутренние адреса.

### Этап 1. P0: approval, полномочия, high-risk инструменты

#### 1.1. Approval state v2

Изменить `АИС_ЗапускиАгентов.ОдобрениеJSON`:

```json
{
  "version": 2,
  "subject_kind": "documents | action",
  "tool": "create_document",
  "args_hash": "sha256",
  "args_json": "{...}",
  "target_ids": ["uuid"],
  "decision": "approved | rejected",
  "answer_text": "",
  "interaction_id": "uuid",
  "consumed": false,
  "created_at": "..."
}
```

Правила:

- Для **всех** изменяющих инструментов `tool` и `args_hash` обязательны.
- `ПроверитьОдобрение` требует точного совпадения `tool` и `hash(args)`; ветка `documents` больше не разрешает произвольный документный инструмент.
- Для `documents` дополнительно проверяется, что все целевые ID (`document_id`, `basis_id`, `addressee`, `section_id`, `remark_id`) входят в `target_ids`.
- `request_action_approval` для `documents` обязан передать `tool` и `arguments`; без них — `invalid_arguments`.
- `АвтоОдобрениеРазрешено` получает `tool`, `arguments`, `documents` и проверяет:
  - тип каждого документа;
  - автора/контрагента;
  - что цель действия входит в `documents`;
  - что адресат входит в разрешённый список.
- Автоодобрение остаётся только для `create_document`, `approve_document`, `cancel_document` и только при точном совпадении аргументов.
- После успешного изменяющего действия approval расходуется.

UI:

- Показывать `completed`, `intended`, инструмент, краткое описание аргументов и целевые документы.
- Для `documents` показывать полный текст документа из 1С по ID, а не из payload LLM.
- Свободный текст — всегда отклонение; кнопка «Одобряю. Действуй» — единственный approve.

#### 2.2. Маскирование как настраиваемая опция

Добавить константу `АИС_ПолитикаLLMJSON` (или `АИС_НастройкиМаскированияJSON`) и форму в `АИС_АдминистрированиеИИ`:

```json
{
  "provider_kind": "local",
  "external_allowed": false,
  "classification_checked": true,
  "masking_mode": "off",
  "mask_contacts": true,
  "mask_bank_details": true,
  "mask_addresses": true,
  "mask_names": false,
  "mask_positions": false,
  "mask_organizations": false,
  "fail_closed": true,
  "allowed_external_document_types": []
}
```

Правила:

- До настройки `provider_kind = unknown`, `external_allowed = false`; запросы к LLM запрещены.
- В проде `provider_kind = local`; `external_allowed = false`.
- DeepSeek — только в dev-конфигурации; в проде внешний провайдер выключен.
- `provider_kind` не выводится из URL, имени модели или протокола. Классификация и проверки — по §2.5.
- Для внешнего провайдера:
  - `masking_mode = basic` или `strict`;
  - `masking_mode = off` допускается только при явном `external_allowed = true` и административном подтверждении;
  - при ошибке маскирования — блокировать запрос (`fail_closed`).
- `basic`: телефоны, email, адреса, банковские реквизиты, номера документов.
- `strict`: дополнительно ФИО, должности, организации.
- Маскирование выполняется **до** отправки в LLM. Обратное восстановление — в памяти 1С, mapping не сохраняется.
- Если LLM возвращает замаскированные токены в аргументах инструмента, dispatcher восстанавливает их перед выполнением.
- Аудит хранит режим маскирования и количество замен, но не исходные значения.

Модуль:

- новый `src/CommonModules/АИС_МаскированиеДанных/`
- функции `ЗамаскироватьТекст`, `ЗамаскироватьСнимок`, `ВосстановитьТекст`, `ВосстановитьАргументы`.
- проверка классификации провайдера — по §2.5, до маскирования и до отправки.

- При `provider_kind = external` и `masking_mode = off` запрос блокируется.
- При `masking_mode = basic` в отправляемом тексте нет телефонов/email/реквизитов.

## 6. Rollout и откат

1. `АИС_АгентВключен = Ложь`, все группы выключены.
2. Задеплоить сервисы с токеном и loopback.
3. Загрузить расширение, выполнить backfill настроек.
4. Настроить run-as регламентных заданий на least-privilege пользователя.
5. Включить пилотному сотруднику «Документы» и «Поиск/знания».

## 8. Открытые решения

Ниже — развилки, которые нужно подтвердить до реализации соответствующего этапа. Для каждой первая опция рекомендована.

### 8.1. Auth сервисов

- **A. `X-Service-Token` + bind `127.0.0.1` (Recommended).** Просто, совместимо с текущим клиентом 1С; требует пересмотра NFR-036 и хранения токена в защищённом хранилище 1С.
- **B. mTLS.** Сильнее, но сложнее эксплуатация, ротация сертификатов и настройка 1С.
- **C. Только loopback/firewall, без токена.** Минимум изменений; подходит, если сервисы гарантированно не выходят за пределы хоста и доступ ограничен ОС-пользователями.

### 8.2. Второй approval для high-risk

- **A. Проверка полномочий + аудит, без второго approval (Recommended).** Меньше трения; риск снижается тем, что инструмент доступен только соответствующей роли.
- **B. Второй approval администратора для найма, оргструктуры и зарплаты.** Сильнее, но замедляет сценарии и требует отдельного UI/маршрута.
- **C. Убрать high-risk инструменты из агента.** Максимально безопасно, но теряется автоматизация кадрового контура.

### 8.3. Глубина маскирования

- **A. `basic` для всех внешних запросов, `strict` — для чувствительных типов (Recommended).** Нужен перечень чувствительных типов документов.
- **B. `basic` для всех внешних запросов.** Проще, но ФИО/должности/организации уходят во внешнюю LLM.
- **C. `strict` для всех внешних запросов.** Максимальная защита, но выше риск потери смысла и качества генерации.

### 8.4. Сроки хранения

- **A. 90 дней для запусков/взаимодействий, 365 дней для аудита (Recommended).** Соответствует текущему плану миграции.
- **B. 30/180 дней.** Меньше данных, но сложнее расследования.
- **C. Бессрочно до отдельного решения.** Не рекомендую: растёт объём ПДн и риск утечки.

## 9. Чек-лист готовности

- [ ] Approval v2: точный `tool + hash(args)` для всех изменяющих инструментов.
- [ ] Автоодобрение проверяет цель действия, а не только список документов.
- [ ] Проверка полномочий для кадров, оргструктуры, зарплаты, промптов.
- [ ] Запрет выдачи `АдминистраторСистемы`/`СервисныйПользователь` агентом.
- [ ] Проверка права утверждения/отмены документа.
- [ ] ACL/ownership для разделов и замечаний.
- [ ] Шаблонные approval-инструменты убраны из allowlist.
- [ ] Привилегированный режим восстанавливается во всех обработчиках.
- [ ] Run-as регламентных заданий — least-privilege пользователь.
- [ ] `allowed_addressees` заполняется и проверяется.
- [ ] `provider_kind` явно задан; `local` проверяется по сети, `external` требует `external_allowed=true`.
- [ ] Маскирование настраивается и работает fail closed.
- [ ] Сервисы проверяют токен и слушают loopback.
- [ ] Администратор не видит payload; аудитор видит промпт/ответ.
- [ ] Атомарная блокировка run и проверка исполнителя задачи.
- [ ] Prompt injection сценарии закрыты.
- [ ] Квоты/лимиты LLM и мониторинг.
- [ ] Все security-тесты пройдены, `CheckConfig` без ошибок расширения.
