# Отчёт о проблеме: сбой платформы 1С при загрузке расширения (Этап B3/B4)

Дата: 2026-10-24
Коммит с исправлением: `d604fe3` — «Fix extension load crash: move task RLS out of role rights»

## 1. Краткое резюме для руководителя

Расширение `ai_scrivener` **не загружалось** в демо-базу 1С:Документооборот — платформа аварийно завершалась (segmentation fault) при любой попытке загрузки через файлы. Причина — **баг платформы 1С:Предприятие 8.3.27.2342**, а не ошибка в нашем коде: платформа падает при обработке ограничений доступа (RLS, строковые условия безопасности на уровне строк) в правах роли расширения, независимо от содержимого условия.

Проблема диагностирована и обойдена: RLS убран из метаданных ролей и перенесён в прикладной код (общий модуль). Расширение теперь **полностью загружается** в демо-базу. По пути исправлено ещё два самостоятельных дефекта в наших метаданных, обнаруженных в процессе диагностики.

Работа над Этапами B4 (демоданные) и B5 (проверки доступа) может продолжаться — технический блокер снят.

## 2. Контекст

Предыдущая диагностика зафиксировала три внешне не связанных симптома при попытке загрузить расширение в демо-базу:

1. полная загрузка через `LoadConfigFromFiles` либо падала с segfault, либо (при частичной загрузке) выдавала ошибку «Недопустимый тип»;
2. роли, по сообщениям, загружались «пустыми»;
3. регламентное задание демоданных не отображалось в списке заданий.

Эта диагностика предполагала, что причины — в правах доступа к базе, в формате выгрузки EDT и в регистрации задания. Дальнейшее расследование показало, что реальные причины другие.

## 3. Что оказалось на самом деле

### 3.1. Главная причина падения — баг платформы, не наш код

При полной загрузке расширения под `strace` было установлено: платформа падает (`SIGSEGV`, разыменование нулевого указателя в `basic.so`, один и тот же адрес во всех случаях) **ровно в момент чтения файла прав роли, содержащего ограничение доступа по условию** (`restrictionByCondition`).

Проверено экспериментально, многократно и воспроизводимо:

| Вариант условия | Результат |
|---|---|
| Условие с ошибкой в тексте (ссылка на несуществующее поле) | Падение |
| Синтаксически и семантически корректное условие | Падение — на том же месте |
| Условие без ссылок на объекты основной конфигурации (чистая строка) | Падение — на том же месте |
| Условие убрано полностью | Загрузка проходит успешно |

Падение воспроизводится **и** при автоматической загрузке через CLI/EDT, **и** при интерактивной загрузке через Конфигуратор, **и** (отдельный, но аналогичный баг) просто при открытии панели прав для некоторых объектов в редакторе ролей Конфигуратора — без какого-либо отношения к тексту условия.

**Вывод: это дефект платформы 1С:Предприятие 8.3.27.2342 в обработке ограничений доступа для ролей расширений, а не ошибка в содержимом нашей конфигурации.** Он не лечится правкой текста условия, типов полей или способа загрузки.

### 3.2. Два самостоятельных дефекта, найденных по пути

В процессе диагностики (в т.ч. ручного воспроизведения в Конфигураторе) вскрылись два реальных дефекта в наших метаданных — независимых от бага платформы, но маскировавшихся под него:

1. **Невалидное условие доступа.** Одно и то же RLS-условие («доступ только к своим задачам») было механически скопировано на 10 объектов роли, хотя поле «Задача», к которому оно обращается, реально существует только у 5 из них. На оставшихся 5 (справочники типов действий/триггеров, обязанностей, расписания триггеров) условие было синтаксически некорректным — подтверждено вручную в Конфигураторе («синтаксическая ошибка»).
2. **Тип `TaskRef` ломал редактор ролей.** Реквизит «Задача» на части объектов был ссылкой на объект `Задача` (бизнес-процесс) основной конфигурации. Простой выбор такого объекта в редакторе прав роли в Конфигураторе также приводил к падению платформы — независимо от наличия RLS.
3. **(Дополнительно, не связано с RLS) `DefinedType` с типами основной конфигурации.** Отдельно обнаружена и исправлена ошибка «Недопустимый тип»: именованный `ОпределяемыйТип` расширения не может включать ссылочные типы на справочники основной конфигурации (`CatalogRef.*`) — платформа отвергает такую связку при загрузке. Исправлено переносом составного типа непосредственно на реквизит.

## 4. Исправления, внесённые в код (коммит `d604fe3`)

- Реквизит «Задача» на 5 объектах (`АИС_РазделыДокумента`, `АИС_ЛистОжидания`, `АИС_КонтекстЗадачИИ`, `АИС_СостоянияПлейсхолдеров`, `АИС_ИсторияДействийИИ`) переведён с `TaskRef.ЗадачаИсполнителя` на строку (GUID задачи, 36 символов).
- Удалены два неиспользуемых `ОпределяемыйТип` (`АИС_РезультатЗадачи`, `АИС_ИсточникТриггера`); составной тип реквизита «Адресат» задан прямо на реквизите вместо третьего (`АИС_АдресатЗапроса`).
- Регламентное задание демоданных включено (`Использование = Истина`).
- **Ограничения доступа (RLS) убраны из прав ролей** и реализованы в прикладном коде:
  - новый общий модуль `АИС_ПроверкаДоступа` с функцией `ЕстьДоступПоЗадаче()`;
  - новый параметр сеанса `АИС_GUIDЗадачИсполнителя` — список GUID задач текущего исполнителя, вычисляется в `УстановкаПараметровСеанса`.

Результат проверен: расширение полностью загружается в демо-базу (`Extension loaded successfully`), все роли и права присутствуют и не пустые, регламентное задание активно. EDT-валидация и 32 автотеста проходят без ошибок.

## 5. Что осталось сделать / риски

1. **RLS больше не работает на уровне платформы для этого расширения.** Проверка «доступ только к своим задачам» теперь зона ответственности прикладного кода (вызов `АИС_ПроверкаДоступа.ЕстьДоступПоЗадаче()`) — её нужно будет подключать во всех будущих формах/отчётах/списках по этим 5 объектам на Этапах 4–6. Это не автоматическая защита уровня платформы, а значит требует дисциплины при написании кода в дальнейшем.
2. **Баг редактора ролей не исправлен, только обойдён.** Если в будущем понадобится вручную открыть панель прав для `АИС_РазделыДокумента` (или похожих объектов) в Конфигураторе — Конфигуратор может упасть. Делать это не нужно, но стоит иметь в виду.
3. **Стоит проверить обновление платформы.** Баг воспроизведён на сборке 8.3.27.2342. Не проверялось, исправлен ли он в более свежих сборках 8.3.27.x — если точка доступа к обновлениям платформы есть, имеет смысл свериться.
4. **Доступ администратора к демо-базе** (вопрос из предыдущего отчёта — отсутствие профиля доступа 1С:ДО у пользователя «Администратор») **не исследован** в рамках этой работы — фокус был на технической загрузке расширения.

## 6. Как это проверить самостоятельно

```bash
scripts/build/export_extension.sh        # выгрузка из EDT
scripts/build/load_extension.sh file     # загрузка в файловую демо-базу
scripts/build/dump_extension.sh file     # контрольный дамп из базы
```

Ожидаемый результат последней команды — `Extension loaded successfully` без ошибок и падений.
